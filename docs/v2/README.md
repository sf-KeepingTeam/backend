# v2 — 현재 진행 중 (최신 유지)

> **이 폴더는 살아있다.** 작업이 진행되면 계속 갱신한다.
> 이전 버전의 맥락은 `docs/v1/README.md` 하나에 정리되어 있다.

시작: 2026-08 · 상태: **작업 1·2 코드 수정 진행 중 (무인 모드)**

---

## 1. v2의 목표

v1은 "분리 목적은 부하 격리"라는 전제 위에 서 있는데, **그 격리가 실제로 달성됐다는 증거가 없다.** 그리고 검토 과정에서 확정 결함 하나가 발견됐다.

v2는 세 가지를 한다.

1. **확정 결함을 고친다** — LOT 만료 미처리로 인한 이중 장부 불일치
2. **격리가 됐는지 측정으로 답한다** — 분리 전/후, 병목의 정체
3. **남은 결합을 끊는다** — monolith 서버 측 자원 격리, PIN 검증 토큰화

**리팩토링 단계는 여기서 종료한다.** 이후는 Kafka 도입(기능 추가) 단계다.

## 2. 하지 않기로 한 것 (재론 금지)

외부 상담에서 **"잔액 소유권을 결제 서비스(qr)로 옮겨라"**는 제안을 받았다. 검토했고 **채택하지 않는다.**

- 일반 원칙(소유권 = write authority)상으로는 옳다.
- **그러나 이 도메인에서 잔액을 변경하는 주체는 7개이고 그중 6개가 monolith에 있다** — 결제 차감(qr 트리거), 충전, 환불, 충전보너스, 포인트공유, 정산, LOT만료.
- `WalletStoreLot`은 `Transaction`·`Store`·`Wallet`과 JPA 연관으로 묶여 있고 `Transaction`은 다시 `Customer`·`Store`를 참조한다. **잔액만 떼어낼 수 없다.**
- 원칙대로 밀면 결론은 "결제 서비스로 이전"이 아니라 "독립 포인트 원장 서비스(제3 서비스)"인데, 이 규모에서는 과설계다.

**→ 소유권 이전 없이, 결합만 끊고 정합성만 확보한다.**

상세 근거: [`구조검토_잔액소유권과_격리.md`](./구조검토_잔액소유권과_격리.md)

## 3. 작업 목록

### 작업 1 ★ LOT 만료 처리 + 이중 장부 정합성 — 확정 결함

포인트 잔액이 두 군데 기록된다. 성립해야 할 불변식:

```
SUM(wallet_store_lot.amount_remaining WHERE 미만료 AND ACTIVE) == wallet_store_balances.balance
```

깨지는 경로 두 개가 확인됐다.

**(1) LOT 만료 배치가 없다.** monolith의 `@Scheduled` 4개는 전부 충전예약 정리·정산이다. 조회 쿼리가 `expiredAt > :now`로 런타임에 거르기만 하고, `balance`를 줄이는 주체가 없다. → **만료 발생 순간부터 `balance > SUM(lot)`.** 만료 기한은 충전 후 1년(`PrepaymentConfirmService`의 `now.plusYears(1)`).

**(2) 차감 시 LOT 부족을 로그만 찍고 커밋한다.** `InternalWalletService.capture()`:

```java
if (lotLeft != 0) {
    log.warn("LOT 차감 불완전: ... unmatched={}", lotLeft);   // 예외 없음, 롤백 없음
}
```

(1)+(2) → **없는 돈으로 결제가 성립한다. 매장이 손해를 본다.**

**함정:** 단순히 예외를 던져 롤백하면 안 된다. `lotLeft != 0`은 "이미 어긋나 있다"는 신호이므로, 롤백하면 데이터가 어긋난 고객 **전원의 결제가 차단**된다. 앱에는 잔액이 보이는데 결제만 안 되는 장애가 된다.

**만료의 구조적 특성:** 다른 write 경로는 전부 "사건"(버튼 클릭, API 호출)이 있어 한 트랜잭션에 묶을 수 있다. 만료만 트리거가 시계뿐이라 **배치가 불가피하고, 배치 주기와 실제 만료 시각 사이에 갭이 반드시 생긴다.** 이 판단은 ADR로 남길 값어치가 있다.

### 작업 2 ★ 대사(reconciliation) 배치

작업 1이 "안 깨지게 하는" 장치라면, 대사는 **"깨진 걸 발견하는"** 장치다. 층위가 다르다. 코드가 완벽해도 어긋나는 경로(운영자 직접 SQL, 마이그레이션, 버그 배포 후 롤백)가 있다.

**2단 구성:**
1. **실시간 신호** — `capture()`의 `lotLeft != 0`을 로그가 아니라 알림으로 (`SlackAlertService` 활용). 좁지만 즉시.
2. **일일 전수 대사** — 새벽 배치로 전 지갑 대조. 쓰이지 않는 지갑의 조용한 불일치까지.

**대조 기준: `lot`이 정답, `balance`가 파생값.** lot에는 근거가 붙어 있고(언제 얼마 충전, 어떤 거래로 얼마 사용, 만료 언제) balance는 숫자 하나다. 회계에서 잔액과 원장이 다르면 원장을 믿는 것과 같다.

**자동 보정은 신중히:**

| 상황 | 의미 | 대응 |
|---|---|---|
| `balance > SUM(lot)` | 고객이 못 받을 돈을 보유 | 깎으면 컴플레인. 원인 규명 먼저 |
| `balance < SUM(lot)` | 고객이 손해 중 | 올려주는 건 상대적으로 안전 |

기본은 **탐지 + 알림**까지. 자동 보정은 원인이 명확하고 고객에게 유리한 케이스로 한정.

**부가 목적:** k6는 HTTP 응답까지만 본다. 대사가 **부하테스트의 정합성 판정 도구**가 된다. 단독 실행 가능한 형태로 만들 것. → **측정보다 먼저 완료해야 한다.**

### 작업 3 monolith `/internal` 자원 격리

qr→monolith 호출에는 이미 용도별 커넥션풀 분리(읽기 50 / 쓰기 30)가 적용·검증됐다. **그런데 그건 보내는 쪽 격리다.**

```
qr:        [읽기풀 50] [쓰기풀 30]      ← 나뉨 ✅
                  ↓
monolith:  [톰캣 스레드 한 줄]           ← 안 나뉨 ❌
              ↑ 프론트 트래픽도 여기로
```

**출구는 둘인데 입구가 하나다.** 프론트의 지갑조회·매장목록·통계 요청과 qr의 `/internal/*` 요청이 같은 톰캣 스레드풀·같은 Hikari 풀을 공유한다. 분리의 목적이 여기서 무너진다.

**단, 측정 결과를 보고 착수한다.** 병목이 DB 커넥션인지 톰캣 스레드인지 CPU인지에 따라 무엇을 격리할지가 달라진다. CPU가 병목이면 풀을 나눠도 소용없다.

### 작업 4 PIN 검증 토큰화

`approve()`가 monolith를 두 번 연달아 부른다 — PIN 검증, 그다음 차감. v1 매트릭스에서 **Intent p95 134ms vs Approve p95 530ms**로 4배 차이가 났고, Intent는 캐시에서 끝나지만 Approve만 monolith를 두 번 왕복한다.

**채택안 — 단기 서명 토큰:**

```
1~3. (변경 없음) QR 스캔 → 주문서 생성 → 금액 표시
4. 손님 PIN 입력 → 프론트가 qr이 아니라 monolith로 직접 전송
5. monolith가 PIN 대조 → 성공 시 단기(~60초) 서명 토큰 발급
6. 프론트 → qr /approve (PIN 대신 토큰)
7. qr이 토큰 서명을 로컬 검증 → monolith 호출 0
8. qr → monolith 차감 ← 이것만 남음
```

두 서비스가 이미 `JWT_SECRET`을 공유하므로 인프라 추가가 없다. 손님 화면·클릭 수는 그대로.

**반드시:** 토큰에 주문서 ID 포함(없으면 토큰 재사용으로 다른 주문서 결제 가능), 1회용(jti를 Redis에 기록), 수명 짧게.

**기각한 안:** PIN 해시를 qr에 복제 — 인증 크리덴셜 복제라 유출 표면이 2배가 되고 PIN 변경 전파 지연 동안 옛 PIN이 통한다.

**정직하게 인정할 것:** (c)를 해도 monolith가 죽으면 결제는 안 된다. 없애는 것은 **"qr 스레드가 monolith를 기다리며 붙잡혀 있는 시간"**이지 monolith 의존 자체가 아니다.

## 4. 측정 계획

이번 측정은 성능 자랑이 아니라 **두 질문에 답하기 위한 것**이다.

> **Q1. monolith가 포화될 때 병목이 DB 커넥션인가, 톰캣 스레드인가, CPU인가?**
> **Q2. 서버를 분리한 것이 결제 지연을 실제로 막아줬는가?**

### 구성

| ID | 구성 | 방법 |
|---|---|---|
| A | 올인원 1대 ("분리 전" 근사) | `docker-compose.msa.yml`을 한 EC2에서 |
| B | 2대 분리 + 캐시 없음 | 2-EC2 + `CACHE_MODE=NONE` |
| C | 2대 분리 + 캐시 (현재) | 2-EC2 + `CACHE_MODE=WRITE_THROUGH` |

**"분리 전"을 코드 병합(qr을 monolith에 합치기)으로 재현하지 않기로 했다.** `IdempotencyKey` 클래스·테이블 충돌, ACL 5개 제거, 빈 충돌, 스키마 재설계, 의존성 버전 충돌로 2~3일이 들고, 그 과정의 버그가 측정값을 오염시킨다. 그리고 만들어봐야 "과거의 모놀리식"이 아니라 "현재 코드의 단일 프로세스 버전"이라 원래 목적을 못 채운다.

**A로 충분한 이유:** 구성 A에서도 monolith 톰캣 풀은 여전히 공유된다(프론트 트래픽 + qr의 `/internal` 호출). CPU·DB·스레드풀 경합이 모두 재현된다.

### 부하 설계

```
배경 부하(monolith 대상): 0 → 50 → 150 → 300 → 500 VU   ← 점이 아니라 곡선
톰캣 스레드 통제:         threads.max 200 / 20
측정:                     결제 플로우 p50/p95/p99
```

스레드 20은 스레드풀 포화를 강제하는 통제변인이다. v1에서 임시포트를 1,000개로 좁혀 포트 고갈을 재현한 것과 같은 기법.

### ★ 포화 증명 필수

**monolith를 실제로 무릎 꿇렸다는 증거가 없으면 v1 매트릭스와 똑같이 무효다.** 각 러닝마다 함께 수집:

| 지표 | 메트릭 | 의미 |
|---|---|---|
| DB 커넥션 대기 | `hikaricp_connections_pending` | >0이면 DB 경합 |
| 톰캣 busy | `tomcat_threads_busy_threads` / `_config_max` | max에 붙으면 스레드 경합 |
| CPU | `process_cpu_usage` | 100% 근처면 연산 부족 |
| 힙 | `jvm_memory_used_bytes{area="heap"}` | GC 압박 |
| URI별 지연 | `http_server_requests_seconds` p95 by URI | `/internal/*` vs 나머지 |

**Q1의 답은 이 표에서 나온다** — 무엇이 먼저 천장을 치는가.

### 추가 항목

- **Approve 구간 분해** — PIN 검증 / capture 각각 몇 ms (작업 4의 근거)
- **실패 모드** — monolith 정지 시 몇 초 만에 실패하나, CB가 여는가
- **복구 지표** — `UNCERTAIN` 건이 몇 초 만에 정리되나
- **정합성 판정** — 부하 후 `SUM(lot) == balance` (작업 2의 대사 활용)

## 7. Kafka 사전 경고 (8단계)

알림을 Kafka로 비동기화할 계획이다. 미리 알아둘 것:

- **알림만을 위해서라면 오버엔지니어링이다.** 알림은 이미 CB + fallback으로 격리돼 있다.
- **정당화되려면 "결제 이벤트 버스"여야 한다** — 통계·정산·포인트 적립 소비자를 붙일 수 있어야 값어치가 생긴다.
- **Kafka를 넣는 순간 새 이중 쓰기 문제가 생긴다.** DB 커밋 후 발행 직전에 죽으면 이벤트 유실. → **Transactional Outbox가 세트로 따라온다.**
- v1은 "캐시 동기화는 self-healing이라 Outbox는 오버엔지니어링"이라 판단했다. **결제 이벤트는 성격이 다르다**(유실 시 복구 불가). 이 구분을 유지할 것.

## 8. 지켜야 할 원칙

1. **정직하게 쓴다.** v1 문서의 미덕이 그거다 — "처리량은 개선 안 됐다", "포트 고갈은 실제로 발생하지 않았다(예방적 개선)". 포장하지 않는다.
2. **포화 못 시켰으면 그렇게 적는다.** 포화 없는 "격리됐다"는 결론은 쓰지 않는다.
3. **한 번에 한 변수만 바꾼다.**
4. **각 러닝 3회 이상 반복하고 편차를 기록한다.**
5. **선택하지 않은 안의 이유도 남긴다.** "안 했다"가 아니라 "검토하고 근거를 갖고 안 했다"가 되도록.
