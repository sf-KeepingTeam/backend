## ⛔ 0. 절대 제약 — 이번 단계는 코드 작성만 한다

| 금지 | |
|---|---|
| **빌드 실행** | **네가** `gradlew`·`docker build`·`docker compose` 를 부르는 것 금지 (훅이 자동으로 도는 건 예외 — 바로 아래 참조) |
| **테스트 실행** | 단위·통합·컨트랙트 **돌리지 마라.** Testcontainers가 Docker를 깨워 세션이 멎는다 |
| **서버 접근** | EC2, k6, Prometheus, DB 접속 금지 |
| **측정** | 성능 검증을 시도하지 마라 |
| **`git` 쓰기** | 커밋·브랜치·푸시 금지. `.git/` 수정은 권한 프롬프트를 띄운다 |

**검증은 인프라 담당이 재측정으로 한다.** 코드AI는 **파일 편집만** 하고 끝낸다.
테스트 *코드*를 새로 쓰는 것은 괜찮다 — **실행하지만 마라.**

읽기 전용은 허용: `grep` `find` `cat` `sed` `git --no-pager log/blame/diff`

**사람에게 질문하고 기다리지 마라.** 판단이 갈리면 가장 안전한 쪽으로 쓰고 워크로그에 남긴다.


### ⚠️ 훅이 자동으로 컴파일한다 — 네가 한 게 아니다

이 저장소에는 **`PostToolUse` 훅**이 걸려 있다 (`.claude/settings.json`, `.claude/settings.local.json`).
**`.java` 파일을 편집할 때마다 훅이 자동으로 `./gradlew compileJava` 를 돌린다.**

```
.claude/hooks/post-edit.sh    .java 편집 시 해당 모듈 compileJava (timeout 90s, 실패 시 exit 1)
.claude/hooks/smoke-build.sh  같은 일 (항상 exit 0)
.claude/hooks/check-env.sh    .env / application*.yml 저장 시 필수 변수 경고
```

**그래서 이런 출력이 보인다:**

```
🔨 [qr-service] Java 파일 변경 감지 → 컴파일 체크 중...
✅ [qr-service] 컴파일 성공
```

**이건 네가 빌드를 실행한 게 아니다. 훅이 한 것이고 §0 위반이 아니다.**

| 해야 할 것 | 하지 말 것 |
|---|---|
| 훅이 **컴파일 실패**를 뱉으면 **즉시 고쳐라.** 이게 이번 작업의 유일한 컴파일 안전망이다 | 훅이 돌았다고 해서 **너도 `./gradlew` 를 직접 불러도 된다고 착각하지 마라** |
| 훅 출력을 워크로그에 "훅 컴파일 결과"로 인용해도 된다 | **`./gradlew test` 는 절대 금지.** 훅은 `compileJava` 만 돌린다. 테스트는 Testcontainers(Docker)를 깨워서 세션이 멎는다 |
| 편집 후 훅 출력을 **반드시 확인하고 넘어가라** | 훅 결과를 "테스트 통과"로 부풀리지 마라. **컴파일과 테스트는 다르다** |

**훅 때문에 편집 하나마다 수 초가 붙는다.** 조급해하지 말고, 대신 **불필요한 재편집을 줄여라** —
한 파일을 여러 번 찔끔찔끔 고치지 말고 한 번에 제대로 써라.

## 1. 배경 — 왜 이걸 고치나

부하측정으로 **코드로만 고칠 수 있는 병목 3건**이 근거와 함께 확정됐다.

| | 구성 1 (합침) | 구성 2 (분리) |
|---|---|---|
| 조회 부하 500 하 결제 성공률 | 31.7% | **99.1%** |
| approve p95 | 7,700 ms | **6,687 ms** |

**서버 분리는 "붕괴"는 막았으나 "지연"은 못 막았다.** SLO(1,000 ms)의 6.7배다.
남은 지연의 정체가 아래 3건이고, **인프라로는 더 못 줄인다.**

| 항목 | 근거 | approve 내 비중 |
|---|---|---|
| 알림이 결제 트랜잭션 안 | 결제당 monolith INSERT 2건. 누적 44,921건 | 196.7 ms (9%) |
| HTTP 호출이 `@Transactional` 안 | qr Hikari **15/15 포화**, pending 12, **CPU는 4.4%** | — (처리량·안정성) |
| PIN 검증이 결제마다 Argon2 | monolith 왕복 3회 중 1회 | 627.3 ms (29%) |

**병목은 MySQL이다** (Hikari 20→60 실험에서 처리량 −3.2%로 확정).
그래서 **"쓰기를 줄이고, 커넥션 점유 시간을 줄이는"** 방향이 전부다.

## 2. 내가 코드를 읽고 확인한 것 (설계의 전제)

인프라 문서에 없는, **코드를 직접 열어 확인한 사실들**이다. 각 세트 프롬프트에 반영돼 있다.

### 2-1. ✅ 트랜잭션 분리 인프라가 이미 있다

`IntentStatusUpdater` 가 `@Transactional(propagation = REQUIRES_NEW)` 로 이미 존재한다.
`FundsService` 가 UNCERTAIN 마킹에 쓰고 있다. **패턴을 새로 만들 필요가 없다.**

### 2-2. ✅ 복구 스케줄러가 오래된 `PENDING` 도 스윕한다

```java
findRecoveryTargets(uncertainStatus, pendingStatus, now, since)   // + retryCount <= 10 가드
```

인덱스 `idx_recovery(status, expires_at, created_at)` 도 이미 있다.

**→ 트랜잭션을 쪼갰을 때 "TX 사이에서 프로세스가 죽는" 시나리오가 기존 복구 경로로 커버된다.**
이게 이번 재설계를 안전하게 만드는 핵심 근거다.

### 2-3. ⚠️ `PaymentIntent` 에 `@Version` 낙관적 락이 있다

트랜잭션을 쪼개면 **TX-A에서 읽은 엔티티를 TX-B에서 그대로 저장하면 `OptimisticLockException`** 이 난다.
TX-B는 **반드시 재조회**해야 한다. 세트 #31 프롬프트에 명시했다.

### 2-4. 🔴 현재 코드에 잠재 버그가 있어 보인다 — 확인 필요

`approve()` 의 PIN 실패 경로:

```java
if (!pinOk) {
  intent.markDeclined(now);
  intentRepository.save(intent);
  throw new CustomException(ErrorCode.PIN_INVALID);   // ← 같은 @Transactional 안
}
```

`CustomException` 이 `RuntimeException` 을 상속하면 **`@Transactional` 기본 롤백 정책에 걸려
`markDeclined` 가 되돌아간다.** intent는 `PENDING` 으로 남고 멱등 슬롯도 `IN_PROGRESS` 로 남는다.
그러면 복구 스케줄러가 "오래된 PENDING" 으로 잡아 개입하게 된다.

**단정하지 않는다 — 세트 #31에서 확인시킨다.**
사실이라면 **트랜잭션을 쪼개는 것이 이 버그를 부수적으로 고친다** (TX-B 커밋 후 예외를 던지면 되므로).
`markDeclined`(자금 미차감)와 `markApproved`(자금 차감됨)는 성격이 다르니 구분해서 다뤄야 한다.

### 2-5. ⚠️ 작업 3은 백엔드만으로 완결되지 않는다

PIN 토큰화의 핵심은 **프론트가 PIN을 qr이 아니라 monolith로 직접 보내는 것**이다.
프론트는 이 저장소 밖(`C:/keeping/frontend`)에 있다.

**→ 백엔드는 "PIN 경로와 토큰 경로를 병행 지원"하게 만들고, 프론트가 준비되면 전환한다.**
병행 지원이 아니면 프론트 배포와 백엔드 배포 사이에 결제가 끊긴다. 세트 #32·#33에 반영했다.

## 3. 세트 분할과 순서

### ★ "한 번에 하나만 바꾼다" 와 "1·2는 같이 하면 효율적" 을 어떻게 화해시키나

인프라 문서가 두 가지를 동시에 말한다:

- §4 원칙: **"한 번에 하나만 바꾼다"** — 원인 분해가 가능했던 이유
- §0: **"1·2는 같은 파일이라 함께 하면 효율적"**

**해결: 코드 세트는 나누고, 각 개선을 설정 플래그로 켜고 끌 수 있게 만든다.**

```yaml
payment:
  notification:
    async: true          # 세트 #30 — 끄면 기존 동기 경로
  approve:
    split-transaction: true   # 세트 #31 — 끄면 기존 단일 트랜잭션
  pin:
    token-enabled: true       # 세트 #33 — 끄면 기존 PIN 직접 검증
```

이러면 **배포는 한 번, 측정은 조건별로** 할 수 있다. 원칙을 지키면서 배포 횟수를 줄인다.
그리고 개선이 오히려 악화시키면 **코드 롤백 없이 플래그 한 줄로 되돌린다.**

**플래그 기본값은 전부 `true`** 로 둔다. 인프라가 before를 재려면 `false` 로 내리면 된다.

### 세트 목록

| 세트 | 내용 | 소유 | 선행 | 난이도 |
|---|---|---|---|---|
| **#30** | 알림을 커밋 이후 비동기로 | qr-service | – | 낮음 |
| **#31** | `approve()` 트랜잭션 경계 재설계 | qr-service | #30 | **높음** |
| **#32** | PIN 검증 토큰 **발급** + `PinAuthService` 쓰기 감소 | monolith | – | 중간 |
| **#33** | PIN 토큰 **검증** 경로 (PIN 경로와 병행) | qr-service | #31, #32 | 중간 |
| **#34** | 정적 검증 | – (읽기 전용) | 전부 | – |

### 실행 순서

```
Wave 1  (병렬)   #30 알림 비동기화 (qr)   │   #32 PIN 토큰 발급 (monolith)
                        ↓
Wave 2           #31 approve 트랜잭션 경계 재설계 (qr)        ← 단독. 가장 위험
                        ↓
Wave 3           #33 PIN 토큰 검증 (qr)
                        ↓
Wave 4           #34 정적 검증  →  사람이 판정  →  인프라에 인계
```

**#31을 단독으로 두는 이유**: `approve()` 전체를 재구성하는 작업이라 다른 편집과 겹치면
diff를 읽을 수 없게 된다. #30이 같은 파일을 건드리므로 **먼저 끝내고 시작**한다.

**#30과 #32가 병렬 가능한 이유**: 서로 다른 저장소 영역(qr / monolith)이고 의존이 없다.

## 4. 공유 계약 — 세트 간 어긋나면 안 되는 것

각 세트 프롬프트에 §2로 복사되어 들어간다. **원본은 이 절이다.**

### V-1. 설정 키

```yaml
payment:
  notification:
    async: true
  approve:
    split-transaction: true
  pin:
    token-enabled: true
    token-ttl-seconds: 60
```

`@ConfigurationProperties(prefix = "payment")` 로 **`PaymentTuningProperties` 하나**에 묶는다.
`@Value` 를 흩뿌리지 마라. **이 클래스는 세트 #30이 만들고 #31·#33이 필드를 추가한다.**

### V-2. `PaymentStatus` enum 을 건드리지 않는다

새 중간 상태(`PROCESSING`/`AUTHORIZING` 등)를 **추가하지 마라.**

- DB ENUM 컬럼이라 마이그레이션이 따라온다 (v2에서 배포 순서로 고생한 그 문제)
- **복구 스케줄러가 이미 오래된 `PENDING` 을 스윕하므로 필요가 없다** (§2-2)

### V-3. 트랜잭션 경계 규약 (세트 #31의 핵심)

```
[TX-A]  멱등 슬롯 선점 · intent 검증 · items 스냅샷 로드     → 커밋
[NO-TX] PIN 검증 (HTTP) · 자금 캡처 (HTTP)                  ← 커넥션 안 쥔다
[TX-B]  intent 재조회 · 상태 전이 · 멱등 complete            → 커밋
[AFTER] 알림 (세트 #30)
```

**절대 규칙**
1. **`[NO-TX]` 구간에서 어떤 리포지토리도 호출하지 마라.** 하나라도 부르면 커넥션을 다시 쥔다
2. **TX-B는 intent를 재조회한다.** `@Version` 낙관적 락 때문 (§2-3)
3. **TX-A/TX-B는 별도 빈의 `REQUIRES_NEW`** — self-invocation은 프록시를 우회한다
4. **`IntentStatusUpdater` 패턴을 따르라.** 이미 있는 것을 새로 만들지 마라

### V-4. 관측 — 인프라가 검증에 쓴다

이 지표들이 **재측정의 판정 기준**이다. 코드가 이걸 바꾸면 안 된다.

| 지표 | 기대 |
|---|---|
| `hikaricp_connections_active{qr}` 최대 | 15 → **15 미만** |
| `hikaricp_connections_pending{qr}` 최대 | 12 → **0** |
| `/actuator/health` | 424 ms → **수십 ms** |

**`/actuator/health` 가 가장 명확한 지표다.** DB 검증 쿼리 + Redis ping 뿐인데 424 ms 였다는 건
커넥션 풀에서 대기했다는 뜻이다. **이게 수십 ms로 돌아오면 세트 #31이 성공한 것이다.**

로그 규약 (grep 가능해야 한다):

```
log.info("[APPROVE_PHASE] phase={} intentId={} elapsedMs={}", ...)   // TX-A / HTTP / TX-B 구간별
log.warn("[APPROVE_ORPHAN] intentId={} reason={}", ...)              // TX-A 후 실패
```

### V-5. 하지 말아야 할 것 (측정으로 배제됨)

| | 이유 |
|---|---|
| **Argon2 파라미터 약화** | OWASP 1순위. 알고리즘 선택은 옳다. 측정용 도구였고 원복됐다 |
| **Hikari 풀만 키우기** | 20→60 실험에서 처리량 **−3.2%**. 병목이 아니다 |
| **톰캣 스레드만 키우기** | 200 포화는 원인이 아니라 결과다 |
| **캐싱 확대** | HTTP 호출은 없애도 같은 MySQL·CPU 경합은 못 막는다 |
| **PIN 잠금 정책 완화** | PIN은 6자리라 경우의 수가 10⁶. 실질 1차 방어선은 해시가 아니라 잠금이다 |

### V-6. 산출물 3종 (전부 파일)

1. 코드·테스트 파일 수정 (테스트는 **작성만**)
2. `docs/v3/worklog/<세트번호>_<이름>.md`
3. `docs/v3/worklog/인프라_인계.md` 에 append — **인프라가 재측정 전에 알아야 할 것**
   (플래그 기본값, 배포 순서 제약, 새로 생긴 설정, 관측 지점)

## 6. 완료 기준 — "코드가 이렇게 바뀌었다" 로 정의한다

실행이 금지되므로 **테스트 통과로 정의하지 않는다.**

| 세트 | 완료 기준 |
|---|---|

## 7. 사람이 판단해야 할 것 (AI가 결정하지 않는다)

| # | 항목 | 왜 |
|---|---|---|
| 1 | **§2-4 의 `markDeclined` 롤백이 실제 버그인가** | 사실이면 별건으로 다뤄야 할 수도 있다. #31이 부수적으로 고치지만, 기존 데이터에 영향이 있는지는 사람이 본다 |
| 2 | **작업 3의 프론트 전환 시점** | 백엔드는 병행 지원까지만 만든다. 프론트 배포 조율은 사람 몫 |
| 3 | **플래그를 언제 `true` 로 올릴지** | 기본값은 `true` 지만, 인프라가 before/after를 재는 순서는 사람이 정한다 |
| 4 | **SLO 미달을 받아들일지** | 셋을 다 해도 `2,177.8 − 196.7 − 627.3 ≈ 1,354 ms`. **SLO 1,000 ms 는 여전히 미달일 가능성이 높다** |

**4번을 특히 정직하게 다뤄라.** 인프라 문서 §5가 이미 인정한 것이고,

> 그래도 이 셋은 해야 한다. 처리량과 커넥션 포화 해소만으로도 값어치가 충분하고,
> 무엇보다 **"측정으로 근거를 확보하고 고쳤다"** 는 서사가 성립한다.
