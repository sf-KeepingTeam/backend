## ⛔ 0. 절대 제약 — 코드 작성만 한다 (다른 모든 지시보다 우선)

| 금지 | |
|---|---|
| **빌드 실행** | **네가** `gradlew`·`docker build`·`docker compose` 를 부르는 것 금지 (훅이 자동으로 도는 건 예외 — 바로 아래 참조) |
| **테스트 실행** | 단위·통합·컨트랙트 **돌리지 마라.** Testcontainers가 Docker를 깨워 세션이 멎는다 |
| **서버 접근** | EC2, k6, Prometheus, DB 접속 금지 |
| **측정** | 성능 검증을 시도하지 마라 |
| **`git` 쓰기** | 커밋·브랜치·푸시 금지. `.git/` 수정은 권한 프롬프트를 띄운다 |

**검증은 인프라 담당이 재측정으로 한다.** 너는 **파일 편집만** 하고 끝낸다.
테스트 *코드*를 새로 쓰는 것은 괜찮다 — **실행하지만 마라.**

허용: 저장소 안 파일 읽기/쓰기, `grep` `rg` `find` `cat` `sed` `wc`,
`git --no-pager log/blame/diff/status` (읽기 전용).

**멈추지 마라.** 사람에게 질문하고 기다리지 마라. 판단이 갈리면 **가장 안전한 쪽으로 쓰고
그 가정을 워크로그에 명시**하라. 확인할 수 없는 것은 "확인 불가"로 적고 넘어가라.

**컴파일을 못 돌린다.** 그래서 반드시:
- 참조하는 클래스·메서드는 **실제 파일을 열어 시그니처를 확인**하고 쓴다. 기억으로 쓰지 마라
- `import` 를 빠짐없이, 정확한 패키지 경로로
- 새로 만든 필드·메서드를 쓰는 쪽과 만드는 쪽이 **같은 이름**인지 저장 직전에 재대조
- `@RequiredArgsConstructor` 에 의존하는 주입은 `private final` 선언을 빠뜨리지 않는다


### ⚠️ 훅이 자동으로 컴파일한다 — 네가 한 게 아니다

이 저장소에는 **`PostToolUse` 훅**이 걸려 있다 (`.claude/settings.json`, `.claude/settings.local.json`).
**`.java` 파일을 편집할 때마다 훅이 자동으로 `./gradlew compileJava` 를 돌린다.**

```
.claude/hooks/post-edit.sh    .java 편집 시 해당 모듈 compileJava (timeout 90s, 실패 시 exit 1)
.claude/hooks/smoke-build.sh  같은 일 (항상 exit 0)
.claude/hooks/check-env.sh    .env / application*.yml 저장 시 필수 변수 경고
```

**그래서 이런 출력이 보인다:**

```
🔨 [qr-service] Java 파일 변경 감지 → 컴파일 체크 중...
✅ [qr-service] 컴파일 성공
```

**이건 네가 빌드를 실행한 게 아니다. 훅이 한 것이고 §0 위반이 아니다.**

| 해야 할 것 | 하지 말 것 |
|---|---|
| 훅이 **컴파일 실패**를 뱉으면 **즉시 고쳐라.** 이게 이번 작업의 유일한 컴파일 안전망이다 | 훅이 돌았다고 해서 **너도 `./gradlew` 를 직접 불러도 된다고 착각하지 마라** |
| 훅 출력을 워크로그에 "훅 컴파일 결과"로 인용해도 된다 | **`./gradlew test` 는 절대 금지.** 훅은 `compileJava` 만 돌린다. 테스트는 Testcontainers(Docker)를 깨워서 세션이 멎는다 |
| 편집 후 훅 출력을 **반드시 확인하고 넘어가라** | 훅 결과를 "테스트 통과"로 부풀리지 마라. **컴파일과 테스트는 다르다** |

**훅 때문에 편집 하나마다 수 초가 붙는다.** 조급해하지 말고, 대신 **불필요한 재편집을 줄여라** —
한 파일을 여러 번 찔끔찔끔 고치지 말고 한 번에 제대로 써라.

## 1. 배경 — 왜 이걸 고치나 (30초)

Keeping은 선결제 포인트 결제 플랫폼이다. monolith(8080) + qr-service(8081), 별도 DB·Redis,
REST + Webhook(`X-Internal-Auth`) 통신.

부하측정으로 확정된 것:

| | 구성 1 (합침) | 구성 2 (분리) |
|---|---|---|
| 조회 부하 500 하 결제 성공률 | 31.7% | **99.1%** |
| approve p95 | 7,700 ms | **6,687 ms** |

**서버 분리는 "붕괴"는 막았으나 "지연"은 못 막았다.** SLO(1,000 ms)의 6.7배다.

**병목은 MySQL이다** — Hikari 풀을 20→60으로 3배 늘렸는데 처리량이 **−3.2%** 였고
CPU는 평균 42%로 여유였다. 커넥션이 부족했던 게 아니라 **커넥션 뒤의 MySQL이 한계**였다.

그래서 방향은 둘뿐이다: **쓰기를 줄인다 / 커넥션 점유 시간을 줄인다.**

상세 근거·수치: `docs/v3/요청_코드개선_측정근거.md`
전체 측정 기록: `docs/측정결과_부하격리/result.md`

## 2. 공유 계약 (임의 변경 금지 — 원본은 `docs/v3/오케스트레이션.md` §4)

### V-1. 설정 키

```yaml
payment:
  notification:
    async: true
  approve:
    split-transaction: true
  pin:
    token-enabled: true
    token-ttl-seconds: 60
```

`@ConfigurationProperties(prefix = "payment")` 로 **`PaymentTuningProperties` 하나**에 묶는다.
`@Value` 를 흩뿌리지 마라. **세트 #30이 이 클래스를 만들고 #31·#33이 필드를 추가한다.**

**플래그를 두는 이유**: 인프라 원칙이 "한 번에 하나만 바꾼다"인데 개선이 3건이다.
플래그가 있으면 **배포는 한 번, 측정은 조건별로** 할 수 있고,
개선이 오히려 악화시키면 **코드 롤백 없이 플래그 한 줄로 되돌린다.**
기본값은 전부 `true`.

### V-2. `PaymentStatus` enum 을 건드리지 않는다

새 중간 상태(`PROCESSING`/`AUTHORIZING` 등)를 **추가하지 마라.**
DB ENUM 컬럼이라 마이그레이션이 따라오고, **복구 스케줄러가 이미 오래된 `PENDING` 을
스윕하므로 필요가 없다.**

### V-3. 트랜잭션 경계 규약

```
[TX-A]  멱등 슬롯 선점 · intent 검증 · items 스냅샷 로드     → 커밋
[NO-TX] PIN 검증 (HTTP) · 자금 캡처 (HTTP)                  ← 커넥션 안 쥔다
[TX-B]  intent 재조회 · 상태 전이 · 멱등 complete            → 커밋
[AFTER] 알림
```

1. **`[NO-TX]` 구간에서 어떤 리포지토리도 호출하지 마라.** 하나라도 부르면 커넥션을 다시 쥔다
2. **TX-B는 intent를 재조회한다** — `PaymentIntent` 에 `@Version` 낙관적 락이 있다
3. **TX-A/TX-B는 별도 빈의 `REQUIRES_NEW`** — self-invocation은 프록시를 우회한다
4. **`IntentStatusUpdater` 패턴을 따르라.** 이미 있는 것을 새로 만들지 마라

### V-4. 관측 — 인프라가 재측정 판정에 쓴다. 바꾸지 마라

| 지표 | 기대 |
|---|---|
| `hikaricp_connections_active{qr}` 최대 | 15 → **15 미만** |
| `hikaricp_connections_pending{qr}` 최대 | 12 → **0** |
| `/actuator/health` | 424 ms → **수십 ms** ← **가장 명확한 지표** |

```
log.info("[APPROVE_PHASE] phase={} intentId={} elapsedMs={}", ...)
log.warn("[APPROVE_ORPHAN] intentId={} reason={}", ...)
```

### V-5. 하지 말아야 할 것 (측정으로 배제됨)

| | 이유 |
|---|---|
| **Argon2 파라미터 약화** | OWASP 1순위. 알고리즘 선택은 옳다. 측정용 도구였고 원복됐다 |
| **Hikari 풀만 키우기** | 20→60 실험에서 처리량 **−3.2%**. 병목이 아니다 |
| **톰캣 스레드만 키우기** | 200 포화는 원인이 아니라 결과다 |
| **캐싱 확대** | HTTP 호출은 없애도 같은 MySQL·CPU 경합은 못 막는다 |
| **PIN 잠금 정책 완화** | PIN은 6자리라 경우의 수가 10⁶. 실질 1차 방어선은 해시가 아니라 잠금이다 |

## 4. 고칠 것

### 4-1. 현상

`PaymentIntentService` 가 알림을 **동기 HTTP로** 보낸다. 두 군데다.

| 위치 | 알림 |
|---|---|
| `initiate()` 끝부분 (약 225~235행) | `PAYMENT_REQUEST` — 고객에게 |
| `approve()` → `sendApprovalNotifications()` | `PAYMENT_APPROVED` — 점주 + 고객 **2건** |

`sendApprovalNotifications()` 안에는 `storeClient.getStore()` 도 있다(매장명·ownerId 조회).

### 4-2. 왜 문제인가

부하 중 `keeping-main` 이 멎기 직전 로그가 알림으로 도배돼 있었다.

```
고객 알림 DB 저장 완료 - 고객ID: 26, 알림ID: 44914, 타입: PAYMENT_APPROVED
로그아웃 상태 감지 - 알림 전송 차단: customer:26
```

- **결제 1건당 monolith MySQL INSERT 2건**, 알림 ID가 44,921까지 갔다
- 그리고 전부 "로그아웃 상태 감지 → 전송 차단" 으로 끝났다
- **MySQL이 병목인데** 결제마다 쓰기가 2건 더 얹힌다
- 게다가 `approve()` 의 `@Transactional` 안이라 **커넥션 점유 시간까지 늘린다**

서버측 실측: 알림 구간 **196.7 ms** = approve 전체 2,177.8 ms 의 **9%**

> **⚠️ 근거의 한계를 정직하게 알고 가라.** 부하테스트 계정은 로그인 상태가 아니라서
> "전송 차단"까지 동일하다고 단정하지 않는다. 실서비스에서는 수신자가 로그인 상태일 수 있다.
> **근거로 쓰는 것은 "INSERT가 결제 임계 경로 안에 있다"는 사실 하나다.**

### 4-3. 요청

**알림 발행을 결제 커밋 이후로 미뤄라.** 알림은 결제 성립과 무관하다.

권장 형태 (설계 세부는 네 판단):

```java
// 1) 도메인 이벤트 발행 — 트랜잭션 안, DB 쓰기 없음
applicationEventPublisher.publishEvent(new PaymentApprovedEvent(...));

// 2) 커밋 이후 처리
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
@Async("notificationExecutor")
public void onPaymentApproved(PaymentApprovedEvent e) { ... }
```

**반드시 지킬 것**

1. **알림 실패가 결제에 영향을 주면 안 된다.** `AFTER_COMMIT` 이면 구조적으로 보장되지만,
   리스너 안에서도 try/catch로 삼키고 로그를 남겨라
2. **이벤트에 엔티티를 담지 마라.** `intentId`, `customerId`, `storeId`, `amount` 같은
   **값만** 담아라. 커밋 이후에는 영속성 컨텍스트가 닫혀 있어 lazy 로딩이 터진다
3. **`storeClient.getStore()` 도 리스너 안으로 옮겨라.** 이것도 HTTP다
4. **`@Async` 스레드풀을 명시적으로 만들어라.** 기본 `SimpleAsyncTaskExecutor` 는
   요청마다 스레드를 새로 만든다. 부하 상황에서 스레드 폭발한다.
   **큐가 차면 버리는 정책**(`CallerRunsPolicy` 말고 `DiscardPolicy` 또는 로그 후 버림)을 써라 —
   알림 때문에 결제 스레드가 막히면 개선이 아니라 개악이다
5. **`initiate()` 의 `PAYMENT_REQUEST` 도 같이 처리하라.** 거기도 결제당 INSERT 1건이다

### 4-4. 플래그 (V-1)

`payment.notification.async` 로 켜고 끌 수 있어야 한다. `false` 면 **기존 동기 경로 그대로.**
인프라가 before/after를 같은 빌드로 재기 위한 것이다.

`PaymentTuningProperties` 클래스를 **네가 만든다.** #31·#33이 여기에 필드를 추가한다.
확장을 염두에 두고 중첩 구조로 짜라:

```java
@ConfigurationProperties(prefix = "payment")
public class PaymentTuningProperties {
  private Notification notification = new Notification();
  private Approve approve = new Approve();        // #31이 채운다
  private Pin pin = new Pin();                    // #33이 채운다
  // ... 중첩 클래스
}
```

## 5. 완료 기준 — "코드가 이렇게 바뀌었다"

- [ ] `approve()` 본문에 `notificationClient` 직접 호출 **0건**
- [ ] `initiate()` 본문에 `notificationClient` 직접 호출 **0건**
- [ ] 알림이 `AFTER_COMMIT` 리스너(또는 동등 경로)로만 나감
- [ ] 이벤트 객체에 JPA 엔티티가 담기지 않음 (값만)
- [ ] `storeClient.getStore()` 도 리스너 안으로 이동
- [ ] 전용 스레드풀 + **큐 포화 시 버리는 정책** 명시
- [ ] `payment.notification.async=false` 면 기존 동기 경로로 되돌아감
- [ ] `PaymentTuningProperties` 생성 + `application.yml` 기본값

## 8. 하지 말 것

1. **`monolith/` 를 건드리지 마라.** 알림 수신 쪽은 세트 #32·별건이다
2. **`@Async` 를 기본 executor로 쓰지 마라.** 스레드 폭발한다
