## ⛔ 0. 절대 제약 — 코드 작성만 한다 (다른 모든 지시보다 우선)

| 금지 | |
|---|---|
| **빌드 실행** | **네가** `gradlew`·`docker build`·`docker compose` 를 부르는 것 금지 (훅이 자동으로 도는 건 예외 — 바로 아래 참조) |
| **테스트 실행** | 단위·통합·컨트랙트 **돌리지 마라.** Testcontainers가 Docker를 깨워 세션이 멎는다 |
| **서버 접근** | EC2, k6, Prometheus, DB 접속 금지 |
| **측정** | 성능 검증을 시도하지 마라 |
| **`git` 쓰기** | 커밋·브랜치·푸시 금지. `.git/` 수정은 권한 프롬프트를 띄운다 |

**검증은 인프라 담당이 재측정으로 한다.** 너는 **파일 편집만** 하고 끝낸다.
테스트 *코드*를 새로 쓰는 것은 괜찮다 — **실행하지만 마라.**

허용: 저장소 안 파일 읽기/쓰기, `grep` `rg` `find` `cat` `sed` `wc`,
`git --no-pager log/blame/diff/status` (읽기 전용).

**멈추지 마라.** 사람에게 질문하고 기다리지 마라. 판단이 갈리면 **가장 안전한 쪽으로 쓰고
그 가정을 워크로그에 명시**하라. 확인할 수 없는 것은 "확인 불가"로 적고 넘어가라.

**컴파일을 못 돌린다.** 그래서 반드시:
- 참조하는 클래스·메서드는 **실제 파일을 열어 시그니처를 확인**하고 쓴다. 기억으로 쓰지 마라
- `import` 를 빠짐없이, 정확한 패키지 경로로
- 새로 만든 필드·메서드를 쓰는 쪽과 만드는 쪽이 **같은 이름**인지 저장 직전에 재대조
- `@RequiredArgsConstructor` 에 의존하는 주입은 `private final` 선언을 빠뜨리지 않는다


### ⚠️ 훅이 자동으로 컴파일한다 — 네가 한 게 아니다

이 저장소에는 **`PostToolUse` 훅**이 걸려 있다 (`.claude/settings.json`, `.claude/settings.local.json`).
**`.java` 파일을 편집할 때마다 훅이 자동으로 `./gradlew compileJava` 를 돌린다.**

```
.claude/hooks/post-edit.sh    .java 편집 시 해당 모듈 compileJava (timeout 90s, 실패 시 exit 1)
.claude/hooks/smoke-build.sh  같은 일 (항상 exit 0)
.claude/hooks/check-env.sh    .env / application*.yml 저장 시 필수 변수 경고
```

**그래서 이런 출력이 보인다:**

```
🔨 [qr-service] Java 파일 변경 감지 → 컴파일 체크 중...
✅ [qr-service] 컴파일 성공
```

**이건 네가 빌드를 실행한 게 아니다. 훅이 한 것이고 §0 위반이 아니다.**

| 해야 할 것 | 하지 말 것 |
|---|---|
| 훅이 **컴파일 실패**를 뱉으면 **즉시 고쳐라.** 이게 이번 작업의 유일한 컴파일 안전망이다 | 훅이 돌았다고 해서 **너도 `./gradlew` 를 직접 불러도 된다고 착각하지 마라** |
| 훅 출력을 워크로그에 "훅 컴파일 결과"로 인용해도 된다 | **`./gradlew test` 는 절대 금지.** 훅은 `compileJava` 만 돌린다. 테스트는 Testcontainers(Docker)를 깨워서 세션이 멎는다 |
| 편집 후 훅 출력을 **반드시 확인하고 넘어가라** | 훅 결과를 "테스트 통과"로 부풀리지 마라. **컴파일과 테스트는 다르다** |

**훅 때문에 편집 하나마다 수 초가 붙는다.** 조급해하지 말고, 대신 **불필요한 재편집을 줄여라** —
한 파일을 여러 번 찔끔찔끔 고치지 말고 한 번에 제대로 써라.

## 1. 배경 — 왜 이걸 고치나 (30초)

Keeping은 선결제 포인트 결제 플랫폼이다. monolith(8080) + qr-service(8081), 별도 DB·Redis,
REST + Webhook(`X-Internal-Auth`) 통신.

부하측정으로 확정된 것:

| | 구성 1 (합침) | 구성 2 (분리) |
|---|---|---|
| 조회 부하 500 하 결제 성공률 | 31.7% | **99.1%** |
| approve p95 | 7,700 ms | **6,687 ms** |

**서버 분리는 "붕괴"는 막았으나 "지연"은 못 막았다.** SLO(1,000 ms)의 6.7배다.

**병목은 MySQL이다** — Hikari 풀을 20→60으로 3배 늘렸는데 처리량이 **−3.2%** 였고
CPU는 평균 42%로 여유였다. 커넥션이 부족했던 게 아니라 **커넥션 뒤의 MySQL이 한계**였다.

그래서 방향은 둘뿐이다: **쓰기를 줄인다 / 커넥션 점유 시간을 줄인다.**

상세 근거·수치: `docs/v3/요청_코드개선_측정근거.md`
전체 측정 기록: `docs/측정결과_부하격리/result.md`

## 2. 공유 계약 (임의 변경 금지 — 원본은 `docs/v3/오케스트레이션.md` §4)

### V-1. 설정 키

```yaml

  notification:
    async: true
  approve:
    split-transaction: true
  pin:
    token-enabled: true
    token-ttl-seconds: 60
```

`@ConfigurationProperties(prefix = "payment")` 로 **`PaymentTuningProperties` 하나**에 묶는다.
`@Value` 를 흩뿌리지 마라. **세트 #30이 이 클래스를 만들고 #31·#33이 필드를 추가한다.**

**플래그를 두는 이유**: 인프라 원칙이 "한 번에 하나만 바꾼다"인데 개선이 3건이다.
플래그가 있으면 **배포는 한 번, 측정은 조건별로** 할 수 있고,
개선이 오히려 악화시키면 **코드 롤백 없이 플래그 한 줄로 되돌린다.**
기본값은 전부 `true`.

### V-2. `PaymentStatus` enum 을 건드리지 않는다

새 중간 상태(`PROCESSING`/`AUTHORIZING` 등)를 **추가하지 마라.**
DB ENUM 컬럼이라 마이그레이션이 따라오고, **복구 스케줄러가 이미 오래된 `PENDING` 을
스윕하므로 필요가 없다.**

### V-3. 트랜잭션 경계 규약

```
[TX-A]  멱등 슬롯 선점 · intent 검증 · items 스냅샷 로드     → 커밋
[NO-TX] PIN 검증 (HTTP) · 자금 캡처 (HTTP)                  ← 커넥션 안 쥔다
[TX-B]  intent 재조회 · 상태 전이 · 멱등 complete            → 커밋
[AFTER] 알림
```

1. **`[NO-TX]` 구간에서 어떤 리포지토리도 호출하지 마라.** 하나라도 부르면 커넥션을 다시 쥔다
2. **TX-B는 intent를 재조회한다** — `PaymentIntent` 에 `@Version` 낙관적 락이 있다
3. **TX-A/TX-B는 별도 빈의 `REQUIRES_NEW`** — self-invocation은 프록시를 우회한다
4. **`IntentStatusUpdater` 패턴을 따르라.** 이미 있는 것을 새로 만들지 마라

### V-4. 관측 — 인프라가 재측정 판정에 쓴다. 바꾸지 마라

## 4. 고칠 것

### 4-1. 현상

`qr-service/domain/intent/service/PaymentIntentService.java` 의 `approve()`

```java
@Transactional                                    // ← 트랜잭션 시작 = DB 커넥션 획득
public IdempotentResult<PaymentIntentDetailResponse> approve(...) {
  ... 멱등 슬롯 선점 / 본문 충돌 / DONE 재생 / IN_PROGRESS 분기 ...
  ... intent 조회 + 상태·만료·소유자 검증 ...

  boolean pinOk = customerClient.verifyPin(customerId, req.getPin());   // HTTP → monolith
  ...
  FundsService.FundsResult funds = fundsService.capture(intent, items); // HTTP → monolith
  ...
  intent.markApproved(now);
  sendApprovalNotifications(intent, customerId);                        // HTTP (세트 #30이 제거)
  idempotencyService.completeStrict(...);
}                                                 // ← 여기서야 커넥션 반납
```

**외부 HTTP 호출이 전부 트랜잭션 경계 안에 있다.** monolith를 기다리는 내내
**qr-service의 DB 커넥션을 쥐고 있다.**

### 4-2. 측정 증거 (B1 · 구성 2 · 조회 부하 500 · 결제 30 VU)

| | 값 |
|---|---|
| `hikaricp_connections_max` (qr) | 15 |
| `hikaricp_connections_active` 최대 | **15 (포화)** |
| `hikaricp_connections_pending` 최대 | **12** |
| `process_cpu_usage` (qr) 평균 | **0.044 — 한산하다** |

**CPU가 4.4%로 노는데 커넥션이 다 찼다.** 그 여파로 결제와 무관한 엔드포인트까지 느려졌다.

```
/actuator/health       424 ms   ← DB 검증 쿼리 + Redis ping 뿐인데
/actuator/prometheus   909 ms
/cpqr/{s}/initiate     732 ms
```

리틀의 법칙 검산: `3.72 건/초 × 2.178 초 ≈ 8.1 개` (풀 15개 중 절반 이상).
여기에 `initiate` 의 INSERT가 겹치면 15개가 찬다.

### 4-3. 내가 코드를 읽고 확인한 것 — 이게 설계의 전제다

#### ✅ 트랜잭션 분리 인프라가 이미 있다

`domain/intent/service/IntentStatusUpdater.java`

```java
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void markUncertain(Long intentId, String reason) { ... }
```

`FundsService` 가 이미 쓰고 있다. **패턴을 새로 만들지 마라. 이걸 따르라.**

#### ✅ 복구 스케줄러가 오래된 `PENDING` 도 스윕한다

`PaymentIntentRepository.findRecoveryTargets(uncertainStatus, pendingStatus, now, since)`
+ `retryCount <= 10` 가드. 인덱스 `idx_recovery(status, expires_at, created_at)` 도 있다.

**→ TX-A 커밋 후 HTTP 단계에서 프로세스가 죽어도 기존 복구 경로가 잡는다.**
**이게 트랜잭션을 쪼개도 안전한 근거다.** 설계에서 이 사실에 기대라.

#### ⚠️ `PaymentIntent` 에 `@Version` 낙관적 락이 있다

**TX-A에서 읽은 엔티티를 TX-B에서 그대로 저장하면 `OptimisticLockException` 이 난다.**
TX-B는 **반드시 재조회**하라.

#### 🔴 현재 코드에 잠재 버그가 있어 보인다 — **네가 확인하라**

```java
if (!pinOk) {
  intent.markDeclined(now);
  intentRepository.save(intent);
  throw new CustomException(ErrorCode.PIN_INVALID);   // ← 같은 @Transactional 안
}
```

`CustomException` 이 `RuntimeException` 을 상속하면 **`@Transactional` 기본 롤백 정책에 걸려
`markDeclined` 가 되돌아간다.** intent는 `PENDING` 으로 남고 멱등 슬롯도 `IN_PROGRESS` 로 남는다.

**확인 절차**
1. `CustomException` 의 상속 계층을 열어봐라
2. `markDeclined` 를 하는 다른 경로(잔액 부족 등)도 같은 구조인지 봐라
3. 사실이면 **워크로그에 크게 적어라.** 그리고 **트랜잭션을 쪼개는 것이 이걸 부수적으로 고친다** —
   TX-B를 커밋한 뒤 예외를 던지면 되므로
4. **단, `markDeclined`(자금 미차감)와 `markApproved`(자금 차감됨)는 성격이 다르다.**
   전자는 되돌아가도 손해가 없지만 후자는 **돈이 빠졌는데 상태가 안 남는** 상황이다. 구분해서 다뤄라

### 4-4. 목표 구조 (계약 V-3)

```
[TX-A]  (REQUIRES_NEW, 별도 빈)
   - 멱등 슬롯 선점/로드 (beginOrLoad)
   - 본문 충돌 / DONE 재생 / IN_PROGRESS 분기
   - intent 조회 + 상태·만료·소유자 검증
   - items 조회 → 값 스냅샷으로 메모리에 (엔티티 들고 나가지 마라)
   → 커밋. 커넥션 반납

[NO-TX]
   - PIN 검증 (HTTP)            ← 세트 #33이 토큰 검증으로 대체하면 사라진다
   - 자금 캡처 (HTTP)
   ※ 이 구간에서 리포지토리를 하나라도 부르면 커넥션을 다시 쥔다. 절대 금지

[TX-B]  (REQUIRES_NEW, 별도 빈)
   - intent 재조회 (@Version 때문)
   - markApproved / markDeclined
   - 멱등 complete (스냅샷)
   → 커밋

[AFTER_COMMIT]
   - 알림 (세트 #30이 이미 처리)
```

### 4-5. 반드시 다뤄야 할 것들 — 설계에 포함하라

| # | 문제 | 힌트 |
|---|---|---|
| 1 | **TX-A와 TX-B 사이 사망** | 기존 복구 스케줄러(오래된 PENDING 스윕)가 커버. **설계 문서에 이 근거를 명시하라** |
| 2 | **멱등 슬롯 `IN_PROGRESS` 고아** | `IdempotencyService.cleanupStalledInProgress()` 가 이미 있다. **주기와 임계값을 확인하고 충분한지 판단하라** |
| 3 | **TX-B에서 intent 상태가 이미 바뀌어 있음** | 다른 요청이 먼저 처리했거나 복구가 개입한 경우. 멱등 재생으로 응답할지 충돌로 처리할지 결정하라 |
| 4 | **`FundsService.capture()` 가 내부에서 `IntentStatusUpdater` 호출** | UNCERTAIN 마킹이 `REQUIRES_NEW` 라 `[NO-TX]` 구간에서도 동작한다. **단 이때 커넥션을 잠깐 쥔다** — 예외 경로라 빈도가 낮으니 허용. 워크로그에 명시 |
| 5 | **`initiate()` 는 어떻게 할 것인가** | `initiate()` 도 `@Transactional` 안에서 `menuClient`·`storeClient` 를 부를 수 있다. **읽어보고 같은 문제가 있으면 함께 처리하되, 범위를 넘는다고 판단되면 워크로그에 올리고 넘어가라** |
| 6 | **`@Version` 충돌 시 재시도할 것인가** | 재시도하면 HTTP를 또 부를 위험이 있다. **재시도하지 말고 멱등 경로로 흡수하는 쪽을 권한다** |

### 4-6. 플래그 (V-1)

`payment.approve.split-transaction` 로 켜고 끌 수 있어야 한다.
`false` 면 **기존 단일 트랜잭션 경로 그대로.**

**이게 이번 세트에서 가장 중요한 안전장치다.** 재설계가 정합성 문제를 일으키면
인프라가 코드 롤백 없이 플래그로 되돌린다.

구현 힌트: 두 경로를 `if/else` 로 늘어놓지 말고 **전략을 분리**해서 기존 경로를 그대로 보존하라.
기존 메서드를 `approveLegacy()` 로 남기고 새 경로를 `approveSplit()` 로 두는 식이면
diff가 읽히고 롤백이 확실하다.

## 5. 완료 기준 — "코드가 이렇게 바뀌었다"

- [ ] 새 경로의 `approve()` 에 HTTP 호출을 감싸는 `@Transactional` 이 **없다**
- [ ] `customerClient.verifyPin` / `fundsService.capture` 호출 지점의 **위아래로 트랜잭션 경계가 닫혀 있다**

- [ ] TX-A / TX-B가 **별도 빈의 `REQUIRES_NEW`** (self-invocation 아님)
- [ ] TX-B가 intent를 **재조회**한다
- [ ] `PaymentStatus` enum 변경 **없음**
- [ ] `payment.approve.split-transaction=false` 면 기존 경로로 되돌아감

## 8. 하지 말 것

1. **`PaymentStatus` 에 새 상태를 추가하지 마라.** DB ENUM 마이그레이션이 따라온다
2. **`[NO-TX]` 구간에서 리포지토리를 부르지 마라.** 하나라도 부르면 이 작업의 의미가 사라진다
3. **self-invocation으로 `REQUIRES_NEW` 를 쓰지 마라.** 프록시를 우회해서 아무 효과가 없다
4. **TX-B에서 TX-A의 엔티티를 재사용하지 마라.** `@Version` 충돌이 난다
5. **`@Version` 충돌 시 HTTP를 다시 부르는 재시도를 만들지 마라.** 이중 결제 위험
6. **기존 경로를 지우지 마라.** 플래그로 되돌아갈 수 있어야 한다
7. **`monolith/` 를 건드리지 마라**
8. **Hikari 풀 크기·톰캣 스레드를 조정하지 마라.** 측정으로 배제됐다 (V-5)
9. **`gradlew`·`docker`·`git` 쓰기를 실행하지 마라**
10. **"커넥션 점유가 줄었습니다"를 측정 없이 쓰지 마라.** 판정은 인프라의 `/actuator/health` 재측정이다
