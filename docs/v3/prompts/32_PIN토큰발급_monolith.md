## ⛔ 0. 절대 제약 — 코드 작성만 한다 (다른 모든 지시보다 우선)

| 금지 | |
|---|---|
| **빌드 실행** | **네가** `gradlew`·`docker build`·`docker compose` 를 부르는 것 금지 (훅이 자동으로 도는 건 예외 — 바로 아래 참조) |
| **테스트 실행** | 단위·통합·컨트랙트 **돌리지 마라.** Testcontainers가 Docker를 깨워 세션이 멎는다 |
| **서버 접근** | EC2, k6, Prometheus, DB 접속 금지 |
| **측정** | 성능 검증을 시도하지 마라 |
| **`git` 쓰기** | 커밋·브랜치·푸시 금지. `.git/` 수정은 권한 프롬프트를 띄운다 |

**검증은 인프라 담당이 재측정으로 한다.** 너는 **파일 편집만** 하고 끝낸다.
테스트 *코드*를 새로 쓰는 것은 괜찮다 — **실행하지만 마라.**

허용: 저장소 안 파일 읽기/쓰기, `grep` `rg` `find` `cat` `sed` `wc`,
`git --no-pager log/blame/diff/status` (읽기 전용).

**멈추지 마라.** 사람에게 질문하고 기다리지 마라. 판단이 갈리면 **가장 안전한 쪽으로 쓰고
그 가정을 워크로그에 명시**하라. 확인할 수 없는 것은 "확인 불가"로 적고 넘어가라.

**컴파일을 못 돌린다.** 그래서 반드시:
- 참조하는 클래스·메서드는 **실제 파일을 열어 시그니처를 확인**하고 쓴다. 기억으로 쓰지 마라
- `import` 를 빠짐없이, 정확한 패키지 경로로
- 새로 만든 필드·메서드를 쓰는 쪽과 만드는 쪽이 **같은 이름**인지 저장 직전에 재대조
- `@RequiredArgsConstructor` 에 의존하는 주입은 `private final` 선언을 빠뜨리지 않는다


### ⚠️ 훅이 자동으로 컴파일한다 — 네가 한 게 아니다

이 저장소에는 **`PostToolUse` 훅**이 걸려 있다 (`.claude/settings.json`, `.claude/settings.local.json`).
**`.java` 파일을 편집할 때마다 훅이 자동으로 `./gradlew compileJava` 를 돌린다.**

```
.claude/hooks/post-edit.sh    .java 편집 시 해당 모듈 compileJava (timeout 90s, 실패 시 exit 1)
.claude/hooks/smoke-build.sh  같은 일 (항상 exit 0)
.claude/hooks/check-env.sh    .env / application*.yml 저장 시 필수 변수 경고
```

**그래서 이런 출력이 보인다:**

```
🔨 [qr-service] Java 파일 변경 감지 → 컴파일 체크 중...
✅ [qr-service] 컴파일 성공
```

**이건 네가 빌드를 실행한 게 아니다. 훅이 한 것이고 §0 위반이 아니다.**

| 해야 할 것 | 하지 말 것 |
|---|---|
| 훅이 **컴파일 실패**를 뱉으면 **즉시 고쳐라.** 이게 이번 작업의 유일한 컴파일 안전망이다 | 훅이 돌았다고 해서 **너도 `./gradlew` 를 직접 불러도 된다고 착각하지 마라** |
| 훅 출력을 워크로그에 "훅 컴파일 결과"로 인용해도 된다 | **`./gradlew test` 는 절대 금지.** 훅은 `compileJava` 만 돌린다. 테스트는 Testcontainers(Docker)를 깨워서 세션이 멎는다 |
| 편집 후 훅 출력을 **반드시 확인하고 넘어가라** | 훅 결과를 "테스트 통과"로 부풀리지 마라. **컴파일과 테스트는 다르다** |

**훅 때문에 편집 하나마다 수 초가 붙는다.** 조급해하지 말고, 대신 **불필요한 재편집을 줄여라** —
한 파일을 여러 번 찔끔찔끔 고치지 말고 한 번에 제대로 써라.

## 1. 배경 — 왜 이걸 고치나 (30초)

Keeping은 선결제 포인트 결제 플랫폼이다. monolith(8080) + qr-service(8081), 별도 DB·Redis,
REST + Webhook(`X-Internal-Auth`) 통신.

부하측정으로 확정된 것:

| | 구성 1 (합침) | 구성 2 (분리) |
|---|---|---|
| 조회 부하 500 하 결제 성공률 | 31.7% | **99.1%** |
| approve p95 | 7,700 ms | **6,687 ms** |

**서버 분리는 "붕괴"는 막았으나 "지연"은 못 막았다.** SLO(1,000 ms)의 6.7배다.

**병목은 MySQL이다** — Hikari 풀을 20→60으로 3배 늘렸는데 처리량이 **−3.2%** 였고
CPU는 평균 42%로 여유였다. 커넥션이 부족했던 게 아니라 **커넥션 뒤의 MySQL이 한계**였다.

그래서 방향은 둘뿐이다: **쓰기를 줄인다 / 커넥션 점유 시간을 줄인다.**

상세 근거·수치: `docs/v3/요청_코드개선_측정근거.md`
전체 측정 기록: `docs/측정결과_부하격리/result.md`

## 2. 공유 계약 (임의 변경 금지 — 원본은 `docs/v3/오케스트레이션.md` §4)

### V-1. 설정 키

```yaml
payment:
  notification:
    async: true
  approve:
    split-transaction: true
  pin:
    token-enabled: true
    token-ttl-seconds: 60
```

`@ConfigurationProperties(prefix = "payment")` 로 **`PaymentTuningProperties` 하나**에 묶는다.
`@Value` 를 흩뿌리지 마라. **세트 #30이 이 클래스를 만들고 #31·#33이 필드를 추가한다.**

**플래그를 두는 이유**: 인프라 원칙이 "한 번에 하나만 바꾼다"인데 개선이 3건이다.
플래그가 있으면 **배포는 한 번, 측정은 조건별로** 할 수 있고,
개선이 오히려 악화시키면 **코드 롤백 없이 플래그 한 줄로 되돌린다.**
기본값은 전부 `true`.

### V-2. `PaymentStatus` enum 을 건드리지 않는다

새 중간 상태(`PROCESSING`/`AUTHORIZING` 등)를 **추가하지 마라.**
DB ENUM 컬럼이라 마이그레이션이 따라오고, **복구 스케줄러가 이미 오래된 `PENDING` 을
스윕하므로 필요가 없다.**

### V-3. 트랜잭션 경계 규약

```
[TX-A]  멱등 슬롯 선점 · intent 검증 · items 스냅샷 로드     → 커밋
[NO-TX] PIN 검증 (HTTP) · 자금 캡처 (HTTP)                  ← 커넥션 안 쥔다
[TX-B]  intent 재조회 · 상태 전이 · 멱등 complete            → 커밋
[AFTER] 알림
```

1. **`[NO-TX]` 구간에서 어떤 리포지토리도 호출하지 마라.** 하나라도 부르면 커넥션을 다시 쥔다
2. **TX-B는 intent를 재조회한다** — `PaymentIntent` 에 `@Version` 낙관적 락이 있다
3. **TX-A/TX-B는 별도 빈의 `REQUIRES_NEW`** — self-invocation은 프록시를 우회한다
4. **`IntentStatusUpdater` 패턴을 따르라.** 이미 있는 것을 새로 만들지 마라

### V-4. 관측 — 인프라가 재측정 판정에 쓴다. 바꾸지 마라

| 지표 | 기대 |
|---|---|
| `hikaricp_connections_active{qr}` 최대 | 15 → **15 미만** |
| `hikaricp_connections_pending{qr}` 최대 | 12 → **0** |
| `/actuator/health` | 424 ms → **수십 ms** ← **가장 명확한 지표** |

```
log.info("[APPROVE_PHASE] phase={} intentId={} elapsedMs={}", ...)
log.warn("[APPROVE_ORPHAN] intentId={} reason={}", ...)
```

### V-5. 하지 말아야 할 것 (측정으로 배제됨)

| | 이유 |
|---|---|
| **Argon2 파라미터 약화** | OWASP 1순위. 알고리즘 선택은 옳다. 측정용 도구였고 원복됐다 |

## 4. 고칠 것

### 4-1. 현상 — PIN 검증이 결제 임계 경로에서 가장 비싸다

`approve()` 가 monolith를 **3번** 부르는데 PIN 검증이 가장 비싸다.

| 구간 (monolith 서버측) | 구성 1 무부하 | 구성 2 무부하 | 구성 2 · 조회 부하 500 |
|---|---|---|---|
| **PIN 검증** | **365.0 ms** | **72.1 ms** | **627.3 ms** |
| 자금 차감 | 121.2 ms | 25.4 ms | 275.6 ms |
| 알림 | 42.2 ms | 11.4 ms | 196.7 ms |
| **approve 전체** | 652.5 ms | 142.6 ms | 2,177.8 ms |
| **PIN 비중** | **56%** | 51% | **29%** |

### 4-2. ★ Argon2 자체는 문제가 아니다 — 알고리즘은 옳다

`Argon2PasswordEncoder(16, 32, 1, 1<<13, 3)` 는 **OWASP 1순위 권고다. 절대 바꾸지 마라.**

측정이 보여준 것은 다른 것이다 — **같은 Argon2 계산이 CPU 경합 때문에 6배로 부풀어 있었다.**

| | Argon2 | 호스트 | PIN 검증 |
|---|---|---|---|
| A0 | 운영값 | 공유 (2 vCPU에 4프로세스) | **365.0 ms** |
| A2-0 | 약화 (측정 전용) | 공유 | **12.3 ms** |
| B0 | 운영값 | **전용** | **72.1 ms** |

```
공유 호스트의 Argon2 비용   365.0 − 12.3  ≈  353 ms
전용 호스트의 Argon2 비용    72.1 − 12     ≈   60 ms
```

**서버 분리로 이미 5배 줄였다. 남은 60 ms를 결제 임계 경로에서 없애는 것이 토큰화다.**

> A2-0의 Argon2 약화는 **변인 분리용 측정 도구**였고 이미 원복됐다
> (`deploy/seed/argon2-{weak,strong}.sql`). **운영에 쓸 수 있는 방법이 아니다.**

**문제는 알고리즘이 아니라 호출 위치다.** 결제마다 Argon2를 돌리지 않게 하는 것이 목표다.

### 4-3. 설계 — v2 설계안에 이미 상세안이 있다

`docs/v2/프롬프트_코드기획AI.md` §4 (작업 4)에 흐름이 적혀 있다. **그걸 따르라.**

```
1~3. (변경 없음) QR 스캔 → 주문서 생성 → 금액 표시
4. 손님이 PIN 입력 → 프론트가 qr이 아니라 monolith로 직접 전송
5. monolith가 PIN 대조 → 성공 시 단기(약 60초) 서명 토큰 발급     ← 네 작업
6. 프론트 → qr /approve (PIN 대신 토큰 첨부)
7. qr이 토큰 서명을 로컬 검증 → monolith 호출 0                   ← 세트 #33
8. qr → monolith 차감 ← 이것만 남음
```

**두 서비스가 이미 `JWT_SECRET` 을 공유한다** (qr이 monolith 발급 JWT를 그대로 검증).
**인프라를 새로 만들 필요가 없다.**

### 4-4. 반드시 지킬 것 (v2 설계안 §4에서 그대로)

| # | | 왜 |
|---|---|---|
| 1 | **토큰에 주문서 ID(intent publicId)를 포함하라** | 없으면 A주문서용 토큰으로 B주문서를 결제할 수 있다 |
| 2 | **1회용으로 만들어라** | qr이 토큰 식별자(`jti`)를 Redis에 기록해 재사용 차단. 멱등키가 이중결제는 이미 막지만 토큰 자체도 1회용이어야 깔끔하다. **기록은 세트 #33(qr)이 한다 — 너는 `jti` 를 넣기만 하라** |
| 3 | **수명을 짧게.** 60초 내외 | `payment.pin.token-ttl-seconds` (V-1) |
| 4 | **잠금 정책(`failed_count`/`locked_until`)을 유지하라** | PIN은 6자리라 경우의 수가 10⁶뿐. **실질적 1차 방어선은 해시가 아니라 잠금이다** |

### 4-5. 정직하게 인정할 것 — 문서에 명확히 쓰라

**토큰화를 해도 monolith가 죽으면 결제는 여전히 안 된다.** PIN이 monolith 소유인 이상 변하지 않는다.

토큰화가 없애는 것은 **"qr 스레드가 monolith를 기다리며 붙잡혀 있는 시간"** 이지
**monolith 의존 자체가 아니다.** 이 구분을 워크로그와 문서에 명확히 써라. 부풀리지 마라.

### 4-6. 부수 항목 — PIN 검증은 읽기가 아니라 쓰기다

```java
// PinAuthService.verify() — 성공 경로
row.setFailedCount(0); row.setLockedUntil(null);
row.setLastVerifyAt(now); row.setUpdatedAt(now);
customerPinAuthRepository.save(row);      // ← 성공해도 UPDATE 한다
```

**결제 1건마다 monolith MySQL에 쓰기가 1건 더 붙는다. MySQL이 병목인데 그렇다.**

토큰화하면 PIN 검증이 결제마다가 아니라 **결제 세션당 1회**가 되므로 자연히 줄지만,
그것과 별개로 이 UPDATE 자체를 줄일 수 있다.

**판단해서 결정하고 근거를 남겨라. 선택지:**

| 안 | 내용 | 트레이드오프 |
|---|---|---|
| (a) | **실패 시에만 기록** — 성공 시 `failedCount` 가 이미 0이면 UPDATE 생략 | 쓰기가 거의 사라진다. `last_verify_at` 정확도를 잃는다 |
| (b) | `last_verify_at` 만 비동기/배치로 분리 | 감사 목적은 유지. 복잡도 증가 |
| (c) | 그대로 둔다 | 토큰화만으로도 결제당 → 세션당으로 줄어드니 충분할 수 있다 |

**권고는 (a)다** — `failedCount` 가 이미 0이고 `lockedUntil` 이 null이면 **상태 변화가 없으므로
UPDATE가 무의미하다.** 다만 `last_verify_at` 이 감사·보안 목적으로 쓰이는 곳이 있는지
**먼저 grep으로 확인하고** 결정하라. 쓰는 곳이 있으면 (b)나 (c)다.

### 4-7. 병행 지원이 필수다 — 프론트가 이 저장소 밖에 있다

**PIN 토큰화의 핵심은 프론트가 PIN을 qr이 아니라 monolith로 직접 보내는 것**인데,
프론트는 `C:/keeping/frontend` 로 이 저장소 밖이다.

**→ 기존 `/internal/customers/{id}/pin-verify` 를 지우지 마라.**
새 토큰 발급 엔드포인트를 **추가**하고 둘 다 살려둬라.
프론트가 준비되면 전환한다. 병행 지원이 아니면 프론트 배포와 백엔드 배포 사이에 결제가 끊긴다.

- [ ] 토큰에 **intent publicId 가 포함**된다
- [ ] 토큰에 **`jti`** 가 포함된다 (1회용 처리는 qr이 함)
- [ ] 토큰 수명이 `payment.pin.token-ttl-seconds` (기본 60) 로 설정 가능
- [ ] `JWT_SECRET` 공유 서명 — 새 시크릿을 만들지 않았다
- [ ] **잠금 정책 로직이 그대로 살아 있다**
- [ ] Argon2 파라미터 **변경 없음**
- [ ] 기존 `pin-verify` 엔드포인트가 **살아 있다** (병행 지원)
- [ ] §4-6 결정과 근거가 워크로그에 있다

## 6. 테스트 (작성만. 실행 금지)

| # | 시나리오 | 단언 |
|---|---|---|
| P-1 | 올바른 PIN + intentPublicId | 토큰 발급. **디코드하면 intentPublicId·jti·exp 가 들어 있다** |
| P-2 | 틀린 PIN | 토큰 미발급 + **`failedCount` 증가** |
| P-3 | 잠금 상태(`lockedUntil` 미래) | PIN이 맞아도 거부 |
| P-4 | 잠금 임계 도달 | `lockedUntil` 설정됨 |
| P-5 | 토큰 만료(TTL 경과) | 검증 실패 (**세트 #33과 계약이 맞는지 확인용**) |
| P-6 | intentPublicId 없이 요청 | 400 — A주문서 토큰으로 B주문서 결제 방지의 근거 |
| P-7 | §4-6 (a) 채택 시 | 성공·무변화일 때 **UPDATE 쿼리가 발생하지 않음** |

**무엇이 담겼는지**를 단언해야 한다.

## 8. 하지 말 것

1. **Argon2 파라미터를 바꾸지 마라.** OWASP 1순위이고 선택은 옳다 (V-5)
2. **잠금 정책(`failed_count`/`locked_until`)을 완화하지 마라.** PIN은 10⁶ 경우의 수뿐이라 실질 방어선이다
3. **기존 `pin-verify` 엔드포인트를 지우지 마라.** 프론트가 저장소 밖이라 병행 지원이 필수다
4. **새 시크릿을 만들지 마라.** `JWT_SECRET` 이 이미 공유된다
5. **토큰에 PIN 자체나 해시를 담지 마라**
6. **`qr-service/` 를 건드리지 마라.** 검증은 세트 #33이다
7. **`domain/wallet` `domain/payment` 를 건드리지 마라.** v2 원장 작업 영역이다
8. **"monolith 의존이 사라졌습니다"라고 쓰지 마라.** §4-5를 보라 — 사라지는 건 대기 시간이지 의존이 아니다
9. **`gradlew`·`docker`·`git` 쓰기를 실행하지 마라**
