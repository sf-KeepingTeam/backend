# 결제 지연 개선 3건 — 오케스트레이션 설계 요청

인프라 담당이 부하측정을 마쳤고, **코드로만 고칠 수 있는 병목 3건**이 근거와 함께 확보됐다.
너는 이걸 **코드AI가 실행할 프롬프트들로 쪼개고 `docs/v3/오케스트레이션.md`를 작성**해라.

**상세 근거·수치·검증방법은 `docs/v3/요청_코드개선_측정근거.md` 에 있다. 먼저 읽어라.**

---

## ★ 절대 제약 — 이번 작업은 코드 작성만 한다

| 금지 | |
|---|---|
| **빌드 실행** | `gradlew`, `docker build`, `docker compose` 일절 금지 |
| **테스트 실행** | 단위·통합·컨트랙트 테스트 **돌리지 마라** |
| **서버 접근** | EC2, k6, Prometheus, DB 접속 금지 |
| **측정** | 성능 검증을 시도하지 마라 |

**검증은 인프라 담당이 재측정으로 한다.** 코드AI는 **파일 편집만** 하고 끝낸다.
테스트 *코드*를 새로 쓰는 것은 괜찮다 — **실행하지만 마라.**

> 이 제약을 지켜야 사람이 중간에 권한 승인을 하지 않고 작업이 끝까지 흐른다.
> 각 프롬프트 안에 이 제약을 **매번 다시 명시**해라.

## 고쳐야 할 것 3건

### 1. 알림을 결제 트랜잭션 밖으로 (난이도 낮음 · 1순위)

`PaymentIntentService.approve()` 안에서 알림을 **동기로** 보낸다.
결제 1건당 monolith DB에 INSERT 2건(`PAYMENT_REQUEST`+`PAYMENT_APPROVED`)이 생기고,
**MySQL이 이 시스템의 병목이다**(측정으로 확정).

→ **커밋 이후 비동기 발행으로 분리.** 알림 실패가 결제에 영향을 주면 안 된다.
근거 수치: 알림 구간 196.7 ms = approve 전체의 9%.

### 2. `approve()` 트랜잭션 경계에서 HTTP 호출 분리 (난이도 중간 · 핵심)

`@Transactional` 안에서 monolith를 **HTTP로 3번** 부른다(PIN 검증·자금 차감·알림).
**HTTP 왕복 내내 qr-service의 DB 커넥션을 쥐고 있다.**

측정: qr Hikari **15/15 포화**, pending 12, 그런데 **CPU는 4.4%로 한산**.
그 여파로 결제와 무관한 `/actuator/health`가 **424 ms**가 됐다.

→ **외부 호출을 기다리는 동안 DB 커넥션을 쥐지 않도록** 트랜잭션 경계를 재설계.
**설계 방식은 네 판단에 맡긴다.** 단 트랜잭션을 쪼개면 중간 실패 시 정합성 문제가 새로 생기니
기존 `UNCERTAIN` 상태 + 복구 스케줄러와 어떻게 맞출지 반드시 설계에 포함해라.

### 3. PIN 토큰화 (난이도 높음 · 작업 4)

`approve()`가 monolith를 3번 부르는데 PIN 검증이 가장 비싸다(조회 부하 하 **627.3 ms**, approve의 29%).

→ **결제마다 Argon2를 돌리지 말고, 1회 검증 후 짧은 수명 토큰을 재사용.**

**⚠️ Argon2 알고리즘은 절대 바꾸지 마라.** OWASP 1순위이고 선택은 옳다.
문제는 알고리즘이 아니라 **호출 위치(결제 임계 경로)** 다.
잠금 정책(`failed_count`/`locked_until`)도 유지해야 한다 — PIN은 6자리라 경우의 수가 10⁶뿐이고
실질적 1차 방어선은 해시가 아니라 잠금이다.

**부수 항목:** `PinAuthService.verify()`가 **성공해도** `customer_pin_auth`를 UPDATE한다
(`last_verify_at` 등). MySQL이 병목인데 결제마다 쓰기 1건이 더 붙는다. 같이 검토해라.

## 하지 말아야 할 것 (측정으로 배제됨)

| | 이유 |
|---|---|
| Argon2 파라미터 약화 | 알고리즘 선택은 옳다 |
| Hikari 풀만 키우기 | 20→60 실험에서 처리량 **−3.2%**. 병목이 아니다 |
| 톰캣 스레드만 키우기 | 200 포화는 원인이 아니라 결과다 |
| 캐싱 확대 | HTTP 호출은 없애지만 같은 MySQL·CPU 경합은 못 막는다 |

   - 앞 작업의 산출물에 의존하면 그 사실을 명시
3. 이 문서를 시작으로 **오케스트레이션.md만 돌리면 나머지가 전부 이어지도록** 구성
