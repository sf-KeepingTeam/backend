## 세트 #31 — approve 트랜잭션 경계 재설계

### 설계 — 최종 구조

```
[TX-A]  ApproveTransactionHelper.prepareApproval()  (REQUIRES_NEW, 별도 빈)
   - 멱등 슬롯 선점/로드 (IdempotencyService.beginOrLoad)
   - body hash 충돌 확인
   - DONE → replay 반환 / IN_PROGRESS → 202 반환
   - intent 조회 + 상태(PENDING)·만료·소유자 검증
   - items 조회 → PaymentIntentItemView 리스트로 메모리 복사
   → 커밋. 커넥션 반납. ApprovePhaseAResult (값 객체) 반환.

[NO-TX]  PaymentIntentService.approveSplit()  (orchestrator, @Transactional 없음)
   - PIN 검증 (CustomerClient.verifyPin — HTTP)
   - 자금 캡처 (FundsService.capture — HTTP)
   ※ 리포지토리 호출 0건. DB 커넥션 미점유.
   ※ FundsService.capture 내부의 IntentStatusUpdater.markUncertain() 은
     REQUIRES_NEW 전파로 자체 커넥션을 잠깐 열어 처리함 (예외 경로, 허용).

[TX-B]  ApproveTransactionHelper.finalizeApproved() / finalizeDeclined()  (REQUIRES_NEW, 별도 빈)
   - intent 를 ID 로 재조회 (@Version 낙관적 락)
   - markApproved / markDeclined 상태 전이
   - 멱등 슬롯 DONE 마킹 + 응답 스냅샷 (성공 경로만)
   → 커밋.

[AFTER]  알림 (세트 #30 이벤트 기반, TX 밖에서 발행)
```

### §4-5 여섯 가지를 어떻게 다뤘나

| # | 문제 | 결정 | 근거 |
|---|---|---|---|
| 1 | TX-A 와 TX-B 사이 사망 | intent 는 PENDING 으로 남음. 멱등 슬롯은 IN_PROGRESS. 기존 복구 스케줄러(`PaymentRecoveryService.findRecoveryTargets`)가 만료된 PENDING 을 스윕한다. 멱등 슬롯은 `cleanupStalledInProgress(5분)`가 정리. | `PaymentIntentRepository.findRecoveryTargets` 쿼리가 `pendingStatus AND expiresAt < now` 조건으로 만료 PENDING 을 조회함 (파일:PaymentIntentRepository.java:36-49) |
| 2 | 멱등 슬롯 IN_PROGRESS 고아 | `IdempotencyService.cleanupStalledInProgress()` 가 5분 초과된 IN_PROGRESS 레코드를 삭제. 기존 동작과 동일. | 파일:IdempotencyService.java:107-118 |
| 3 | TX-B 에서 intent 상태가 이미 바뀌어 있음 | `finalizeApproved()` 내부에서 `status == APPROVED` 이면 멱등 재생(응답 재구성). `finalizeDeclined()` 내부에서 `status != PENDING` 이면 스킵. @Version 충돌 시 orchestrator 가 `PAYMENT_INTENT_STATUS_CONFLICT` 던짐, 재시도 없음. | 파일:ApproveTransactionHelper.java:finalizeApproved (이미 APPROVED 방어), finalizeDeclined (이미 비-PENDING 방어) |
| 4 | `FundsService.capture()` 내부 `IntentStatusUpdater` 호출 | UNCERTAIN 마킹은 `IntentStatusUpdater.markUncertain()` 이 `REQUIRES_NEW` 로 자체 트랜잭션을 열어 처리. NO-TX 구간에서도 동작하며, 커넥션을 잠깐(< 10ms) 점유한다. 예외 경로이므로 허용. | 파일:IntentStatusUpdater.java:19 (`propagation = Propagation.REQUIRES_NEW`) |
| 5 | `initiate()` 도 같은 문제인지 | `initiate()` 의 HTTP 호출은 캐시 읽기(MenuClient, StoreClient — WRITE_THROUGH 모드)로 빠르다. 알림은 세트 #30 이 이미 비동기화. 승인(approve)의 PIN 627ms + 자금 275ms 와는 성격이 다르다. 현재 병목이 아니므로 보류. | application.yml: CACHE_MODE=WRITE_THROUGH (기본) |
| 6 | @Version 충돌 시 재시도? | 재시도하지 않는다. `ObjectOptimisticLockingFailureException` catch 후 `PAYMENT_INTENT_STATUS_CONFLICT` 던짐. HTTP 를 다시 부르는 재시도를 만들지 않는다 (V-5 금지). | 파일:PaymentIntentService.java:approveSplit 내 catch 블록 |

### 🔴 §4-3 markDeclined 롤백 버그

- **CustomException 상속 계층**: `CustomException extends RuntimeException` (파일:CustomException.java:6)
- **실제 버그인가**: **예**. 기존 코드에서 `markDeclined` + `intentRepository.save()` 후 `throw new CustomException(ErrorCode.PIN_INVALID)` 하면, `@Transactional` 이 `RuntimeException` 을 감지하고 전체 트랜잭션을 롤백한다. DECLINED 상태가 DB 에 영속되지 않는다.
- **영향 범위**: PIN 실패 경로(line 351-355), 잔액 부족 경로(line 368-376), 정책 위반 경로(line 378-380) — 모두 같은 구조
- **이번 재설계가 고치는가**: **예**. `approveSplit()` 에서는 `approveHelper.finalizeDeclined()` (REQUIRES_NEW, 별도 빈)가 DECLINED 를 커밋한 **후** orchestrator 가 CustomException 을 던진다. 두 트랜잭션이 별개이므로 예외가 DECLINED 커밋에 영향을 주지 않는다.
- **같은 구조의 다른 경로**: `approveLegacy()` (split-transaction=false 경로)는 기존 코드 그대로이므로 같은 버그가 남아 있다. 레거시 경로는 폴백 전용이며, 운영 기본값은 split-transaction=true.
- **markExpired 경로**: TX-A 에서 `intent.markExpired(now)` + `intentRepository.save(intent)` 후 예외를 던지는데, TX-A 도 REQUIRES_NEW 이므로 예외가 나가도 TX-A 는 이미 커밋된 상태. 즉 만료 마킹은 정상 영속된다.

### [NO-TX] 구간 무결성 증명

`approveSplit()` 메서드의 NO-TX 구간 (PIN 검증 ~ 자금 캡처):

호출되는 메서드:
1. `customerClient.verifyPin(customerId, req.getPin())` — HTTP 호출, 리포지토리 없음
2. `fundsService.capture(intentSnapshot, itemSnapshots)` — HTTP 호출 래퍼

`intentSnapshot` 은 `PaymentIntent.builder()...build()` 로 새로 생성한 비영속(transient) 객체.
`itemSnapshots` 은 `PaymentIntentItem.builder()...build()` 로 새로 생성한 비영속 객체 리스트.

FundsService.capture 내부에서 UNCERTAIN 경로 시 `IntentStatusUpdater.markUncertain()` 이 호출되나,
이것은 REQUIRES_NEW 전파로 자체 트랜잭션을 여는 별도 빈이다 (파일:IntentStatusUpdater.java:19).
orchestrator 자체는 리포지토리를 호출하지 않는다.
