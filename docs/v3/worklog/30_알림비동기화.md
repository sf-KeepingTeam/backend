### 설계 판단
- 이벤트 발행 방식: `ApplicationEventPublisher.publishEvent()` → `@TransactionalEventListener(AFTER_COMMIT)` + `@Async("notificationExecutor")`. Spring 기본 도메인 이벤트 메커니즘 사용. 이벤트는 TX 안에서 발행하되 리스너는 커밋 후 비동기 실행
- 스레드풀 설정 (크기·큐·포화 정책)과 근거:
  - core=2, max=4: 알림은 경량 HTTP 1건(NotificationClient → monolith). 동시 결제 처리량 대비 소수 스레드로 충분
  - queue=64: 순간 버스트 흡수. 결제 TPS 200 기준 약 0.3초 분량
  - 포화 정책: 커스텀 핸들러 (로그 경고 + 작업 버림). `DiscardPolicy` 대신 로그를 남겨 운영 가시성 확보. `CallerRunsPolicy` 는 결제 스레드가 알림을 대신 처리하게 되므로 금지
- initiate 의 PAYMENT_REQUEST 처리 방식: approve 와 동일하게 이벤트 발행 + `AFTER_COMMIT` 리스너. `storeClient.getStore()` 호출도 리스너 안으로 이동하여 TX 안 HTTP 제거

### 가정 / 확인하지 못한 것
- `@EnableAsync` 가 `AsyncConfig` 에 이미 있으므로 `@Async("notificationExecutor")` 가 프록시 처리될 것으로 가정. 확인 불가 (테스트 실행 금지)
- `@TransactionalEventListener` 는 같은 ApplicationContext 안의 `@Transactional` 메서드에서 발행된 이벤트에만 반응한다고 가정
- `PaymentNotificationListener` 가 `@Component` 이므로 Spring 프록시가 `@Async` 를 인식할 것으로 가정 (자기 호출 아님)
- 큐 포화 시 알림이 유실된다. 이는 의도된 동작이며, 결제 성립에는 영향 없음
