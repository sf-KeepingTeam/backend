# #60 조사 — PAYMENT_REQUESTED 롱폴링 전환 (2026-09-01)

## 동기

F6r 러닝: notificationExecutor 큐 포화(core2/max4/queue64)로 PAYMENT_REQUESTED 유실 **41.3 %**.
스레드풀 20개 확대 시 유실 0이지만 결제 처리량 **-34.7 %**로 역효과.
→ 손님이 화면 앞에서 기다리는 알림(PAYMENT_REQUESTED)은 push → **pull(롱폴링)** 으로 전환.

## 조사 결과

### Q1. QrTokenService.scanAndConsumeQr 에서 tokenId를 어떻게 후속 단계에 전달하나?

현재: `scanAndConsumeQr(tokenId)` → GETDEL(원자 소비) → QrScanSession 저장.
세션에는 `sessionToken / walletId / customerId / bindStoreId / expiresAt / ttl` 이 있고 **tokenId는 없다**.
initiate()는 sessionToken만 알므로 tokenId를 역참조하는 매핑이 없다.

**해결**: scan 시 `qrflow:s2t:{sessionToken}` = `{tokenId}` (TTL 180 s) 추가 저장.
initiate()가 sessionToken으로 이 키를 MGET해 tokenId를 얻는다.

### Q2. 롱폴링 엔드포인트가 QR이 없음(404) vs 아직 initiate 안 됨을 어떻게 구분하나?

scan 시 `qrflow:active:{tokenId}` = "1" (TTL 180 s) 추가 저장.
GET /{tokenId}/intent 진입 시 이 키가 없으면 404 즉시 반환.
있으면 waiter 등록 후 대기 (initiate 완료 전 → 25 s 타임아웃 → 204).

### Q3. initiate TX 경계를 건드리지 않고 AFTER_COMMIT 시점에 Redis 쓰기를 보장하려면?

`@TransactionalEventListener(phase = AFTER_COMMIT)` — initiate()에서 이벤트 발행(TX 내부),
리스너가 커밋 후 `qrflow:intent:{tokenId}` = `{intentPublicId}:{customerId}` 저장.
리스너는 **@Async 없이** 동기 실행 → Redis 쓰기 누락 없음.
DiscardPolicy 스레드풀에 맡기면 write가 drop되어 폴링 fallback만 남게 됨.

### Q4. 기존 @Scheduled 스레드(복구 스케줄러 등)와 폴러를 어떻게 격리하나?

`spring.task.scheduling.pool.size` 미설정 = 기본 1 스레드.
복구 스케줄러(`PaymentRecoveryService`)가 1 스레드를 점유하는 구조.
→ `intentWaitScheduler` 전용 `ScheduledExecutorService` (core 2) 를 별도 Bean으로 신설.

## 절대 건드리지 않는 것

1. `scanAndConsumeQr()` 의 GETDEL (`consumeToken`) — 보안·원자성
2. `initiate()` 의 TX 경계 — F2 성과 (커넥션 점유 단축)
3. 기존 `PaymentRequestedEvent` 발행 블록 — 백업 알림 경로 유지
