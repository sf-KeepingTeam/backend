## 5. ★★★ 치명적 결함 발견

### D-1: `approveSplit()` 에서 `@TransactionalEventListener(AFTER_COMMIT)` 이벤트가 무시된다

**심각도: CRITICAL — 운영 기본값(`split-transaction=true` + `notification.async=true`)에서 결제 승인 알림이 100% 유실된다**

**근거:**
- `approveSplit()` (L473)에는 `@Transactional` 어노테이션이 없다
- `approve()` (L291)에도 `@Transactional`이 없다
- TX-B (`finalizeApproved`, REQUIRES_NEW)는 별도 빈의 별도 트랜잭션이고, 호출 반환 시점에 이미 커밋 완료
- L620-623에서 `eventPublisher.publishEvent(new PaymentApprovedEvent(...))` 호출 시점에 활성 트랜잭션이 없다
- `PaymentNotificationListener.onPaymentApproved()`는 `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`
- Spring Framework: 활성 트랜잭션 없이 발행된 이벤트에 대해 `@TransactionalEventListener`는 **`fallbackExecution = true`가 아니면 무시한다** (Spring 기본값 `fallbackExecution = false`)
- `PaymentNotificationListener`에 `fallbackExecution = true` 설정 없음

**영향:**
- `split-transaction=true` (운영 기본값) → 승인 알림 무시 (점주, 고객 모두)
- `split-transaction=false` (레거시 폴백) → `TransactionTemplate.execute()` 안에서 발행하므로 정상 동작
- `initiate()` → `@Transactional` 메서드 안에서 발행하므로 정상 동작

**대조:**
| 경로 | TX 존재 | 이벤트 동작 |
|---|---|---|
| `initiate()` | `@Transactional` ✅ | 정상 발행 |
| `approveLegacy()` | `TransactionTemplate.execute()` ✅ | 정상 발행 |
| `approveSplit()` | 없음 ❌ | **무시됨** |

**수정 방향 (코드 수정은 이 세트의 범위 밖):**
- (a) `PaymentNotificationListener`의 `@TransactionalEventListener`에 `fallbackExecution = true` 추가
- (b) 또는 `approveSplit()`의 이벤트 발행을 `@ApplicationEventListener`(일반 리스너)로 변경
- (c) 또는 TX-B 안에서 이벤트를 발행하도록 `finalizeApproved` 내부로 이동

## 7. 논리 추적 (4-6)

### 시나리오 1: 정상 결제

```
approve() → approveSplit()
  [TX-A] prepareApproval: 멱등 슬롯 IN_PROGRESS + intent PENDING 확인 + items 스냅샷 → 커밋
  [NO-TX] PIN 검증 (토큰 or HTTP) → 성공
  [NO-TX] fundsService.capture → 성공
  [TX-B] finalizeApproved: intent 재조회 + APPROVED + 멱등 DONE → 커밋
  [AFTER] 알림 이벤트 발행 ← ★ D-1: 무시됨 (치명적 결함)
```

TX-A → HTTP → TX-B 순서는 코드로 성립한다 (L485 → L498-536 → L571 → L604-612).
**그러나 알림이 무시되는 결함(D-1)이 있다.**

### 시나리오 2: TX-A 후 프로세스 사망

- intent: PENDING (TX-A에서 상태 변경 없음)
- 멱등 슬롯: IN_PROGRESS
- 복구 쿼리: `findRecoveryTargets` — `status = PENDING AND expiresAt < now` 조건. 3분 만료 후 스윕 대상 ✅
- 멱등 슬롯: `cleanupStalledInProgress(5분)` 정리 ✅
- **정적으로 성립함**

### 시나리오 3: capture 성공 후 TX-B 실패

**이것이 가장 위험한 경로.**
- capture 성공 → monolith에서 돈이 빠짐 (walletClient.capture 멱등키로 영속)
- TX-B (`finalizeApproved`) 실패 시 — `ObjectOptimisticLockingFailureException` catch → `PAYMENT_INTENT_STATUS_CONFLICT` 던짐 (L607-611)
- intent는 PENDING으로 남음 (TX-B 커밋 안 됨)
- 멱등 슬롯은 IN_PROGRESS
- **결과: 돈은 빠졌는데 intent가 APPROVED로 안 바뀜**
- **복구 경로**: `PaymentRecoveryService.findRecoveryTargets` → 만료된 PENDING 스윕 → Phase 1에서 `/internal/payments/check?idempotencyKey=` 호출 → 캡처 성공 확인 → Phase 2에서 APPROVED로 전이. **정적으로 성립함** — 캡처 멱등키가 결정적(`UUID.nameUUIDFromBytes("capture:" + publicId)`)이므로 복구 시 동일 키로 조회 가능.
- **그러나 3분 만료 전에는 복구되지 않고, 고객은 PENDING 상태를 본다.** 이는 기존 UNCERTAIN 경로와 유사한 패턴.

### 시나리오 4: 같은 멱등키 동시 2회

- 첫 번째: TX-A에서 슬롯 선점 (IN_PROGRESS)
- 두 번째: TX-A에서 `!begin.isCreated() && IN_PROGRESS` → `earlyReturn(202 + Retry-After: 2)` (L118-122)
- **1회만 처리된다. 정적으로 성립함**

### 시나리오 5: 토큰 검증 실패

- `pinTokenVerifier.verify()` → `CustomException` 던짐
- `approveSplit()` L506-511: catch → `approveHelper.finalizeDeclined()` → DECLINED 커밋 → 원래 예외 re-throw
- 세트 #31 상태 전이와 일관 ✅
- PIN HTTP 실패 경로(L531-534)도 동일 패턴: `finalizeDeclined` → throw

**판정: ⚠️ 5개 시나리오 중 시나리오 1에서 D-1 결함. 나머지 4개는 정적으로 성립함**
