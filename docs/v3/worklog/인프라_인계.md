## 1. 새 설정 키 표

모든 키의 기본값은 **신규 기능 활성화**(true)로 되어 있다.
롤백 시 환경변수로 false 전환.

| 키 | 기본값 | 서비스 | 설명 | 롤백 환경변수 |
|---|---|---|---|---|
| `payment.notification.async` | `true` | qr-service | 알림을 TX 커밋 후 비동기 발송 | `PAYMENT_NOTIFICATION_ASYNC=false` |
| `payment.approve.split-transaction` | `true` | qr-service | approve를 TX-A/NO-TX/TX-B로 분리 | `PAYMENT_APPROVE_SPLIT_TRANSACTION=false` |
| `payment.pin.token-enabled` | `true` | qr-service | PIN 토큰 로컬 검증 (monolith 왕복 제거) | `PAYMENT_PIN_TOKEN_ENABLED=false` |
| `payment.pin.token-ttl-seconds` | `60` | monolith + qr-service | PIN 토큰 수명(초) | — |

**주의**: `token-ttl-seconds`는 monolith(`@Value`)와 qr-service(`PaymentTuningProperties`)에 각각 설정돼 있다. qr-service는 토큰의 `exp` 클레임으로 만료를 판단하므로 값이 동일하지 않아도 동작하지만, jti Redis TTL 계산에 사용되므로 맞추는 것이 바람직하다.

## 2. 배포 순서 제약

```
monolith 배포 → (확인) → qr-service 배포
```

**이유**: qr-service의 PIN 토큰 검증(`PinTokenVerifier`)은 monolith가 발급한 토큰을 소비한다. monolith에 `PinTokenController`(`POST /customers/pin/verify-token`)가 없는 상태에서 qr-service가 토큰 경로를 활성화하면 프론트가 토큰을 발급받을 수 없다.

**역순 배포 시 위험**: qr-service만 먼저 올리고 `token-enabled=true`이면, 프론트가 토큰 발급 실패 → PIN 폴백으로 동작. 치명적이지 않으나 의도하지 않은 경로.

## 6. 알아둘 위험

### ~~D-1: approveSplit() 승인 알림 무시~~ → **수정 완료 (세트 #35)**

`PaymentNotificationListener`의 `@TransactionalEventListener`에 `fallbackExecution = true` 추가 (방안 a 채택).
로컬 스모크에서 운영 기본값(`split-transaction=true` + `async=true`)으로 승인 알림 발송 확인됨.
점주(PAYMENT_APPROVED) + 고객(PAYMENT_APPROVED) 2건 정상 발송, monolith DB 저장 확인.

### markDeclined 롤백 버그 (기존, LOW)

`approveLegacy()`(split-transaction=false)에서 `markDeclined` + `save` 후 `CustomException`(RuntimeException) 던지면 `@Transactional`이 롤백하여 DECLINED가 DB에 영속되지 않는다.
`split-transaction=true`에서는 REQUIRES_NEW 별도 빈이 DECLINED를 커밋하므로 해소.

### Redis 장애 시 토큰 경로 결제 실패

`PinTokenVerifier`의 jti 기록에 Redis 사용. Redis 장애 시 `setIfAbsent` 예외 → 결제 실패.
이는 의도된 동작 (토큰 재사용 공격 방지). 대응: `token-enabled=false`로 기존 PIN 경로 폴백.

### 알림 유실 허용

큐 포화(64개 초과) 시 알림이 버려진다. `[NOTIFICATION_DROPPED]` 로그로 감지. 결제 성립에 영향 없음.

### ⚠️ k6 스크립트 수정 필요

토큰 경로(A3, B0) 측정 시 k6 스크립트가 PIN 토큰을 발급받아 approve에 넘겨야 한다.

**1) PIN 토큰 발급 (monolith)**
```
POST /customers/pin/verify-token
Authorization: Bearer <accessToken>
Content-Type: application/json

{"pin": "123456", "intentPublicId": "<intent UUID>"}

→ 200 {"pinToken": "<JWT>"}
```

**2) approve 요청 (qr-service) — 토큰 경로**
```
POST /payments/<intentPublicId>/approve
Idempotency-Key: <UUID>
Content-Type: application/json

{"pinToken": "<위에서 받은 JWT>"}
```

**기존 PIN 경로** (A0, A1, A2 측정 시):
```
{"pin": "123456"}
```

`ApproveRequest` 필드: `pin` (String, 6자리) + `pinToken` (String, JWT). 둘 중 하나 필수.
`token-enabled=false`면 `pinToken`이 있어도 PIN HTTP 경로로 폴백.
