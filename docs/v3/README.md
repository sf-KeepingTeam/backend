## 1. v2 는 무엇을 남겼나

v2 의 마지막 산출물은 **부하측정**이었다. 그전까지 v1 문서는
*"서버를 분리하고 캐싱해서 결제 지연을 해결했다"* 고 주장했지만 **근거가 없었다.**

이제 근거가 있다.

| | 구성 1 (합침) | 구성 2 (분리) |
|---|---|---|
| 조회 부하 500 하 결제 성공률 | **31.7%** | **99.1%** |
| 결제 처리량 (조회 부하 500) | 0.96 건/초 | **4.03 건/초** |
| 결제 처리량 (무부하) | 15.2 건/초 | **22.5 건/초 (천장)** |
| Approve p95 (조회 부하 500) | 7,700 ms | 6,687 ms |

**두 줄 요약**

1. **서버 분리는 "붕괴"를 막았다** — 성공률 31.7% → 99.1%, 504 타임아웃 560건 → 0건
2. **그러나 "지연"은 못 막았다** — 13% 개선에 그침. **SLO(1,000 ms)의 6.7배**

그리고 **남은 지연의 정체**가 코드 레벨에서 특정됐다.

## 2. v3 가 할 일 — 순서가 곧 의존관계다

```
[1] 코드 개선 3건        ← 지금
      ↓
[2] 재측정 (before/after)  ← keeping-loadgen 을 유지하는 이유
      ↓
[3] Kafka
```

**[2]를 건너뛰면 [1]의 효과를 증명할 방법이 없다.**
그래서 `keeping-loadgen` 은 Kafka 로 전환하지 않는다 — Kafka 는 `keeping-allinone`(구성 1,
측정이 끝나 역할이 없다)에 올린다.

### [1] 코드 개선 3건

| 순위 | 항목 | 근거 | 난이도 |
|---|---|---|---|
| **1** | **알림을 결제 트랜잭션 밖으로** | 결제 1건당 DB INSERT 2건이 임계 경로 안. 누적 44,921건 | 낮음 |
| **2** | **`approve()` 트랜잭션 경계에서 HTTP 분리** | qr Hikari 15/15 포화. HTTP 왕복 내내 커넥션 점유 | 중간 |
| **3** | **PIN 토큰화** | monolith 왕복 3회 중 1회 제거. approve 의 29% | 높음 |

- 상세 근거·수치·검증방법: [`요청_코드개선_측정근거.md`](./요청_코드개선_측정근거.md)
- 코드기획AI 투입 프롬프트: [`프롬프트_코드기획AI_개선요청.md`](./프롬프트_코드기획AI_개선요청.md)
- 오케스트레이션: `오케스트레이션.md` (코드기획AI 가 작성)

**★ 이 단계에서는 빌드·테스트·서버 접근을 하지 않는다.** 검증은 [2]에서 인프라가 한다.

### [2] 재측정 — 기준선은 이미 확보돼 있다

```bash
RUN_MODE=legacy ./runner.sh B1-after   config2 500 30 4m "개선 후"
RUN_MODE=v2     ./runner.sh S2-60-after config2   0 60 3m "개선 후 수용량"
```

**before (개선 전)**

| | B1 (조회부하 500) | S2-60 (무부하 60 VU) |
|---|---|---|
| 성공률 | 99.1% | 100% |
| **처리량** | **4.03 건/초** | **22.30 건/초** |
| approve p95 | 6,686.6 ms | 1,148.7 ms |
| Intent p95 | 2,881.4 ms | 568.7 ms |
| qr Hikari active 최대 | **15 (포화)** | — |
| `/actuator/health` | **424 ms** | — |

**항목별로 봐야 할 지표**

| 개선 항목 | 확인할 것 |
|---|---|
| 1 · 알림 비동기화 | approve 에서 알림 구간 196.7 ms 가 사라졌는가 / monolith 쓰기 감소 |
| 2 · 트랜잭션 분리 | **`/actuator/health` 가 수십 ms 로 돌아왔는가** ← 가장 명확한 지표<br>`hikaricp_connections_active{qr}` 최대가 15 아래로, pending 이 0 으로 |
| 3 · PIN 토큰화 | PIN 검증 627.3 ms 제거 / monolith 왕복 3회 → 2회 |

원본 데이터: [`../측정결과_부하격리/raw/`](../측정결과_부하격리/raw/) — 러닝 17회분
(`meta.txt` 조건 · `metrics.csv` 5초 시계열 · `volume.txt` 실투입량)

### [3] Kafka

설계 근거는 v2 에 이미 적어뒀다 — [`../v2/infra/06-Kafka.md`](../v2/infra/06-Kafka.md)

| 항목 | 결정 |
|---|---|
| 위치 | **`keeping-allinone`** (구성 1. 측정 완료로 역할 종료) |
| 모드 | KRaft 단일 브로커 |
| `replication.factor` | 1 — **브로커가 죽으면 미소비 메시지 유실. 문서에 반드시 명시** |
| 전제 | [1]·[2] 완료 후 시작 |

> v2 스스로 경고한 것을 그대로 옮긴다:
> **"알림만을 위해서라면 오버엔지니어링이다. 정당화되려면 결제 이벤트 버스여야 한다."**
> 그리고 Kafka 를 넣는 순간 이중 쓰기 문제가 생기므로 **Transactional Outbox 가 세트로 따라온다.**
