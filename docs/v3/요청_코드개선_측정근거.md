## 0. 요약 — 세 가지를 요청한다

| 순위 | 항목 | 근거 | 난이도 |
|---|---|---|---|
| **1** | **알림을 결제 트랜잭션 밖으로** | 결제 1건당 DB INSERT 2건이 임계 경로 안. 누적 44,921건 | 낮음 |
| **2** | **`approve()` 트랜잭션 경계에서 HTTP 호출 분리** | qr Hikari 15/15 포화. HTTP 왕복 내내 커넥션 점유 | 중간 |

## 1. 측정으로 확인된 사실 (요청의 근거)

두 구성을 각각 측정했다.

| | 구성 1 (한 서버에 합침) | 구성 2 (main / payment 분리) |
|---|---|---|
| 조회 부하 500 VU 하 결제 성공률 | **31.7%** | **99.1%** |
| 결제 처리량 (조회 부하 500) | 0.96 건/초 | **4.03 건/초** |
| 결제 처리량 (무부하) | 15.2 건/초 | **22.5 건/초 (천장)** |
| Approve p95 (조회 부하 500) | 7,700 ms | **6,687 ms** |

### 결론 두 줄

1. **서버 분리는 "붕괴"를 막았다** — 성공률 31.7% → 99.1%, 504 타임아웃 560건 → 0건
2. **그러나 "지연"은 못 막았다** — approve p95 13% 개선에 그침. **SLO(1,000 ms)의 6.7배**

**남은 지연의 정체가 아래 세 항목이다. 인프라로는 더 못 줄인다. 코드가 바뀌어야 한다.**

## 2. 요청 1 — 알림을 결제 트랜잭션 밖으로 ★ 1순위

### 현상

`keeping-main` 이 부하 중 멎기 직전 로그가 알림으로 도배돼 있었다.

```
고객 알림 DB 저장 완료 - 고객ID: 26, 알림ID: 44914, 타입: PAYMENT_APPROVED
로그아웃 상태 감지 - 알림 전송 차단: customer:26
고객 알림 DB 저장 완료 - 고객ID: 133, 알림ID: 44913, 타입: PAYMENT_REQUEST
로그아웃 상태 감지 - 알림 전송 차단: customer:133
```

- **결제 1건당 `PAYMENT_REQUEST` + `PAYMENT_APPROVED` = INSERT 2건**
- 알림 ID 가 **44,921** 까지 갔다 (측정 중 누적)
- 그리고 **전부 "로그아웃 상태 감지 → 전송 차단"** 으로 끝난다

### 왜 문제인가

**병목이 MySQL 이다.** (측정으로 확정 — `result.md` §4-2)

> Hikari 풀을 20 → 60 으로 **3배** 늘렸는데 처리량은 **−3.2%**.
> 구조만 `20+179+1=200` → `60+139+1=200` 으로 동일하게 반복됐고 CPU 는 평균 42% 로 여유였다.
> **커넥션이 부족했던 게 아니라 커넥션 뒤의 MySQL 이 한계였다.**

그 MySQL 에 **결제마다 쓰기가 2건 더 얹히고 있다.** 게다가 `approve()` 의 `@Transactional`
안에 있어서 **커넥션 점유 시간까지 늘린다** (요청 2 참조).

서버측 실측: 알림 구간이 **196.7 ms** (구성 2, 조회 부하 500 하). approve 전체 2,177.8 ms 중 **9%**.

### 요청

**알림 발행을 결제 커밋 이후로 미뤄달라.** 알림은 결제 성립과 무관하다.

- `@TransactionalEventListener(phase = AFTER_COMMIT)` 또는 동등한 방식
- 실패해도 결제는 성립해야 한다 (현재는 알림 실패가 결제 트랜잭션에 영향을 줄 수 있는 구조)

### 기대 효과

- approve 임계 경로에서 **196.7 ms** 제거 (약 9%)
- monolith MySQL 에서 **결제당 쓰기 2건** 제거
- qr 의 DB 커넥션 점유 시간 9% 단축

### ⚠️ 측정 조건의 한계 — 정직하게

부하테스트 계정은 로그인 상태가 아니므로 **"전송 차단"까지 동일하다고 단정하지 않는다.**
실서비스에서는 수신자가 로그인 상태일 수 있다.
**근거로 쓰는 것은 "INSERT 가 결제 임계 경로 안에 있다"는 사실 하나다.**

## 3. 요청 2 — `approve()` 트랜잭션 경계에서 HTTP 호출 분리 ★ 핵심

### 현상

`qr-service/domain/intent/service/PaymentIntentService.java`

```java
@Transactional                                    // ← 트랜잭션 시작 = DB 커넥션 획득
public IdempotentResult<PaymentIntentDetailResponse> approve(...) {
  ...
  boolean pinOk = customerClient.verifyPin(customerId, req.getPin());   // HTTP → monolith
  FundsService.FundsResult funds = fundsService.capture(intent, items); // HTTP → monolith
  ...
  notificationClient.sendToOwner(...);                                  // HTTP → monolith
  notificationClient.sendToCustomer(...);                               // HTTP → monolith
}                                                 // ← 여기서야 커넥션 반납
```

**외부 HTTP 호출 3종이 전부 트랜잭션 경계 안에 있다.**
monolith 를 기다리는 내내 **qr-service 의 DB 커넥션을 쥐고 있다.**

### 지표 증거 (B1 · 구성 2 · 조회 부하 500 · 결제 30 VU)

| | 값 |
|---|---|
| `hikaricp_connections_max` (qr) | 15 |
| `hikaricp_connections_active` 최대 | **15 (포화)** |
| `hikaricp_connections_pending` 최대 | **12** |
| `process_cpu_usage` (qr) 평균 | **0.044 — 한산하다** |

**CPU 는 4.4% 로 놀고 있는데 커넥션이 다 찼다.** 그 결과 결제와 무관한 엔드포인트까지 느려졌다.

```
/actuator/health       424 ms   ← DB 검증 쿼리 + Redis ping 뿐인데
/actuator/prometheus   909 ms
/cpqr/{s}/initiate     732 ms
```

리틀의 법칙 검산:

```
approve 처리율  3.72 건/초
approve 소요    2.178 초
점유 커넥션 = 3.72 × 2.178 ≈ 8.1 개   (풀 15개 중 절반 이상)
```

여기에 `initiate` 의 INSERT 가 겹치면 15개가 찬다.

### 요청

**HTTP 호출을 트랜잭션 밖으로 빼달라.** 예를 들면:

```
[트랜잭션 1]  intent 상태 검증 · 잠금        → 커밋
[트랜잭션 밖]  PIN 검증 · 자금 차감 (HTTP)
[트랜잭션 2]  결과 반영 (APPROVED/실패)      → 커밋
[커밋 이후]   알림 (요청 1)
```

**설계는 코드팀 판단에 맡긴다.** 인프라가 요청하는 것은 하나다 —
**"외부 호출을 기다리는 동안 DB 커넥션을 쥐고 있지 않을 것".**

> ⚠️ 트랜잭션을 쪼개면 **중간 실패 시 상태 정합성** 문제가 새로 생긴다.
> 이미 `UNCERTAIN` 상태와 복구 스케줄러가 있으므로 그 경로를 활용하는 게 자연스러워 보이나,
> **판단은 코드팀 몫이다.** 인프라는 이 트레이드오프가 있다는 것만 명시한다.

### 기대 효과

- qr 커넥션 점유가 **2.18초 → 수십 ms 수준**으로 축소
- **풀 포화(15/15) 해소** → `initiate` · `health` 지연 동반 해소
- Hikari 15 라는 천장 자체가 무의미해진다

### 검증 방법

```
hikaricp_connections_active{service="qr-service"}   최대치가 15 아래로 내려오는가
hikaricp_connections_pending{service="qr-service"}  0 에 머무는가
/actuator/health 응답시간                            수십 ms 로 돌아오는가
```

## 4. 요청 3 — PIN 토큰화 (작업 4)

### 현상

`approve()` 가 monolith 를 **3번** 부른다. 그중 하나가 PIN 검증이고, **가장 비싸다.**

| 구간 (monolith 서버측) | 구성 1 무부하 | 구성 2 무부하 | 구성 2 · 조회 부하 500 |
|---|---|---|---|
| **PIN 검증** | **365.0 ms** | **72.1 ms** | **627.3 ms** |
| 자금 차감 | 121.2 ms | 25.4 ms | 275.6 ms |
| 알림 | 42.2 ms | 11.4 ms | 196.7 ms |
| **approve 전체** | 652.5 ms | 142.6 ms | 2,177.8 ms |
| **PIN 비중** | **56%** | 51% | **29%** |

### ★ Argon2 자체는 문제가 아니다 — 알고리즘 선택은 옳다

`Argon2PasswordEncoder(16, 32, 1, 1<<13, 3)` 는 OWASP 1순위 권고다. **바꾸지 말 것.**

측정에서 확인한 것은 다른 것이다 — **같은 Argon2 계산이 CPU 경합 때문에 6배로 부풀어 있었다.**

| | Argon2 | 호스트 | PIN 검증 |
|---|---|---|---|
| A0 | 운영값 | 공유 (2 vCPU 에 4개 프로세스) | **365.0 ms** |
| A2-0 | **약화** (측정 전용) | 공유 | **12.3 ms** |
| B0 | 운영값 | **전용** | **72.1 ms** |

```
공유 호스트에서 Argon2 비용   365.0 − 12.3  ≈  353 ms
전용 호스트에서 Argon2 비용    72.1 − 12     ≈   60 ms
```

**서버 분리로 이미 5배 줄였다. 남은 60 ms 를 없애는 것이 토큰화다.**

> A2-0 의 Argon2 약화는 **변인 분리용 측정 도구**였고 이미 원복했다.
> `deploy/seed/argon2-{weak,strong}.sql` 참조. **운영에 쓸 수 있는 방법이 아니다.**

### 요청

**결제마다 Argon2 를 돌리지 말 것.** 1회 검증 후 짧은 수명의 토큰을 재사용하는 방식.

설계는 코드팀 판단이나, 최소한 아래는 지켜져야 한다.

- 토큰 수명은 짧게 (결제 세션 범위)
- 토큰 탈취 시 재사용 불가 (1회성 또는 결제 건에 바인딩)
- **잠금 정책(`failed_count` / `locked_until`)은 유지** — PIN 은 6자리라 경우의 수가 10⁶ 뿐이고,
  실질적 1차 방어선은 해시가 아니라 잠금이다

### 부수 항목 — PIN 검증은 읽기가 아니라 쓰기다

```java
// PinAuthService.verify() — 성공 경로
row.setFailedCount(0); row.setLockedUntil(null);
row.setLastVerifyAt(now); row.setUpdatedAt(now);
customerPinAuthRepository.save(row);      // ← 성공해도 UPDATE 한다
```

**결제 1건마다 monolith MySQL 에 쓰기가 1건 더 붙는다.** MySQL 이 병목인데 그렇다.
`last_verify_at` 이 감사 목적이라면 **비동기/배치로 빼거나 실패 시에만 기록**하면
결제 임계 경로에서 쓰기 1건이 사라진다.

### 기대 효과

- monolith 왕복 **3회 → 2회**
- 조회 부하 하에서 approve 임계 경로 **627.3 ms** 제거 (약 29%)

## 5. 세 가지를 다 해도 SLO 는 아마 못 맞춘다 — 정직하게

현재 B1 의 approve 서버측 2,177.8 ms 에서 위 셋을 빼면:

```
2,177.8 − 196.7(알림) − 627.3(PIN) ≈ 1,354 ms
```

**요청 2(트랜잭션 분리)는 지연보다 처리량·안정성에 효과가 크다.**
그리고 큐 대기(1.1~1.8초)는 monolith 가 포화인 한 남는다.

**SLO `p95 < 1,000 ms` 는 여전히 미달일 가능성이 높다.**
남은 것은 monolith 자체의 MySQL 한계이고, 그건 인덱스·쿼리·스케일아웃의 영역이다.

> **그래도 이 셋은 해야 한다.** 처리량과 커넥션 포화 해소만으로도 값어치가 충분하고,
> 무엇보다 **"측정으로 근거를 확보하고 고쳤다"** 는 서사가 성립한다.
