## 기술 선택 요약

| 항목 | 내용 |
|------|------|
| **문제** | 동시 결제 시 Lost Update 발생 (10,000원 - 5,000원 - 3,000원 = 7,000원, 정상은 2,000원) |
| **해결 후보** | 비관적 락(Pessimistic Lock), 낙관적 락(Optimistic Lock), 분산 락(Redis), Atomic Update |
| **선택** | 잔액 차감 → 비관적 락 / Intent 상태 → 낙관적 락 / 추가 안전장치 → Atomic Update |
| **이유** | 충돌 빈도와 복구 비용에 따른 최적 선택 |

### 해결 후보 비교

| 솔루션 | 장점 | 단점 | 적용 대상 |
|--------|------|------|----------|
| **비관적 락** | 충돌 시 대기, 정합성 보장 | 데드락 위험, 처리량 저하 | 잔액 차감 ✅ |
| **낙관적 락** | 충돌 없으면 빠름, 데드락 없음 | 충돌 시 재시도 필요 | Intent 상태 ✅ |
| **분산 락** | 서비스 간 동시성 제어 | Redis 의존, 구현 복잡 | 검토 중 |
| **Atomic Update** | 락 없이 조건부 업데이트 | 복잡한 로직 불가 | 추가 안전장치 ✅ |

### 락 선택 의사결정

```
┌─────────────────────────────────┐
│     충돌이 자주 발생하는가?       │
└───────────────┬─────────────────┘
                │
    ┌───────────┴───────────┐
    │                       │
    ▼                       ▼
┌─────────┐           ┌──────────────────┐
│ 자주    │           │ 가끔 발생        │
│ (>5%)   │           │ (<5%)            │
└────┬────┘           └────────┬─────────┘
     │                         │
     ▼                         ▼
┌──────────┐         ┌─────────────────┐
│ 비관적 락 │         │ 복구 비용 큰가? │
└──────────┘         └────────┬────────┘
                              │
                  ┌───────────┴───────────┐
                  │                       │
                  ▼                       ▼
            ┌──────────┐           ┌──────────┐
            │ 크다     │           │ 작다     │
            │ → 비관적 │           │ → 낙관적 │
            └──────────┘           └──────────┘
```

### 현재 구현 현황

| 대상 | 락 종류 | 이유 | 위치 |
|------|---------|------|------|
| **WalletStoreBalance** | 비관적 락 (PESSIMISTIC_WRITE) | 충돌 시 금전 손실, 복구 비용 높음 | `WalletStoreBalanceRepository.java` |
| **PaymentIntent** | 낙관적 락 (@Version) | 충돌 빈도 낮음, 재시도 가능 | `PaymentIntent.java` |
| **잔액 차감** | Atomic Update | 락 + 조건부 업데이트로 이중 안전장치 | `decrementIfEnough()` |

> 💡 **선택 근거**: 잔액 차감은 충돌 빈도가 낮아도(~0.1%) 복구 비용이 높음(환불 처리 필요) → 비관적 락. Intent 상태는 충돌 빈도 매우 낮고(~0.001%) 재시도로 해결 가능 → 낙관적 락

## 기본 개념: 비관적 락 vs 낙관적 락

### 왜 락이 필요한가?

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                          Lost Update 문제 (락 없이)                              │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [시나리오: 고객 A의 잔액 10,000원, 동시에 2건의 결제 발생]                        │
│                                                                                 │
│  시간       결제 1 (5,000원)              결제 2 (3,000원)                       │
│  ─────────────────────────────────────────────────────────────────────          │
│  T1         SELECT balance                                                      │
│             → 10,000원 읽음                                                     │
│                                                                                 │
│  T2                                       SELECT balance                        │
│                                           → 10,000원 읽음                       │
│                                                                                 │
│  T3         UPDATE balance = 10,000 - 5,000                                     │
│             → 5,000원으로 저장                                                  │
│                                                                                 │
│  T4                                       UPDATE balance = 10,000 - 3,000       │
│                                           → 7,000원으로 덮어씀!                 │
│                                                                                 │
│  [결과]                                                                         │
│  ├─ 기대 잔액: 10,000 - 5,000 - 3,000 = 2,000원                                 │
│  ├─ 실제 잔액: 7,000원 (Lost Update 발생!)                                      │
│  └─ 문제: 결제 1의 차감이 소실됨 → 5,000원 손실                                   │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 비관적 락 (Pessimistic Lock)

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                          비관적 락 동작 원리                                      │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [철학]                                                                          │
│  "충돌이 발생할 것이라고 비관적으로 가정한다"                                      │
│  → 데이터를 읽는 시점에 락을 걸어 다른 트랜잭션의 접근을 차단                       │
│                                                                                 │
│  [동작]                                                                          │
│                                                                                 │
│  시간       결제 1 (5,000원)              결제 2 (3,000원)                       │
│  ─────────────────────────────────────────────────────────────────────          │
│  T1         SELECT ... FOR UPDATE                                               │
│             → 10,000원 읽음 + 행 잠금 획득 🔒                                    │
│                                                                                 │
│  T2                                       SELECT ... FOR UPDATE                 │
│                                           → 락 대기 중... ⏳                    │
│                                                                                 │
│  T3         UPDATE balance = 5,000                                              │
│             COMMIT                                                              │
│             → 락 해제 🔓                                                        │
│                                                                                 │
│  T4                                       → 락 획득! 🔒                          │
│                                           SELECT → 5,000원 읽음                 │
│                                           UPDATE balance = 2,000                │
│                                           COMMIT                                │
│                                                                                 │
│  [결과] 잔액 2,000원 ✅ 정합성 보장                                              │
│                                                                                 │
│  [SQL 예시]                                                                      │
│  SELECT * FROM wallet_store_balances                                            │
│  WHERE wallet_id = ? AND store_id = ?                                           │
│  FOR UPDATE;  -- 비관적 락 (PESSIMISTIC_WRITE)                                  │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 낙관적 락 (Optimistic Lock)

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                          낙관적 락 동작 원리                                      │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [철학]                                                                          │
│  "충돌이 거의 발생하지 않을 것이라고 낙관적으로 가정한다"                           │
│  → 읽을 때는 락을 걸지 않고, 쓸 때 충돌 여부를 검사                                │
│                                                                                 │
│  [동작]                                                                          │
│                                                                                 │
│  시간       결제 1 (5,000원)              결제 2 (3,000원)                       │
│  ─────────────────────────────────────────────────────────────────────          │
│  T1         SELECT balance, version                                             │
│             → 10,000원, version=1                                               │
│                                                                                 │
│  T2                                       SELECT balance, version               │
│                                           → 10,000원, version=1                 │
│                                                                                 │
│  T3         UPDATE balance = 5,000                                              │
│             WHERE id = ? AND version = 1                                        │
│             → version = 2로 증가                                                │
│             → 성공! ✅                                                          │
│                                                                                 │
│  T4                                       UPDATE balance = 7,000                │
│                                           WHERE id = ? AND version = 1          │
│                                           → version 불일치!                     │
│                                           → 실패! ❌                            │
│                                           → ObjectOptimisticLockingFailure     │
│                                                                                 │
│  [결과]                                                                         │
│  ├─ 결제 1: 성공                                                                │
│  └─ 결제 2: 실패 → 재시도 필요                                                   │
│                                                                                 │
│  [JPA 예시]                                                                      │
│  @Entity                                                                        │
│  public class PaymentIntent {                                                   │
│      @Version                                                                   │
│      private Long version;  // JPA가 자동으로 관리                               │
│  }                                                                              │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

```
│                                                                                 │
│                        ┌─────────────────────────┐                              │
│                        │ 충돌이 자주 발생하는가? │                              │

│                     ┌──────────────┴──────────────┐                             │

│                   │                              │                              │
│                   ▼                              ▼                              │
│          ┌──────────────┐               ┌──────────────┐                        │
│          │  비관적 락   │               │ 충돌 시 복구 │                        │
│          │ PESSIMISTIC  │               │ 비용이 큰가? │                        │
│          └──────────────┘               └──────┬───────┘                        │
│                                                │                                │
│                                   ┌────────────┴────────────┐                   │
│                                   │                         │                   │
│                                   ▼                         ▼                   │
│                            ┌──────────┐              ┌──────────┐               │
│                            │ 복구 비용 │              │ 복구 비용 │               │
│                            │ 크다     │              │ 작다     │               │
│                            └────┬─────┘              └────┬─────┘               │
│                                 │                         │                     │
│                                 ▼                         ▼                     │
│                        ┌──────────────┐           ┌──────────────┐              │
│                        │  비관적 락   │           │  낙관적 락   │              │
│                        │ PESSIMISTIC  │           │ OPTIMISTIC   │              │
│                        └──────────────┘           └──────────────┘              │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 비교표

| 항목 | 비관적 락 | 낙관적 락 |
|------|----------|----------|
| **락 획득 시점** | 읽기 시점 | 쓰기 시점 |
| **충돌 처리** | 대기 (blocking) | 실패 후 재시도 |
| **충돌 빈도** | 높을 때 유리 | 낮을 때 유리 |
| **처리량** | 낮음 (순차 처리) | 높음 (병렬 처리) |
| **DB 부하** | 락 관리 오버헤드 | 버전 체크 오버헤드 |
| **데드락** | 가능성 있음 | 없음 |
| **구현 복잡도** | 낮음 | 재시도 로직 필요 |

### 실무 선택 가이드

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                          실무 적용 시나리오                                       │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [비관적 락이 적합한 경우]                                                        │
│                                                                                 │
│  1. 잔액 차감                                                                    │
│     - 충돌 시 금전적 손실 발생                                                   │
│     - 복구 비용이 매우 큼 (환불 처리 필요)                                        │
│     - 동일 지갑에 동시 결제 가능성 있음                                           │
│                                                                                 │
│  2. 재고 차감                                                                    │
│     - 인기 상품은 충돌 빈도 높음                                                  │
│     - 초과 판매 시 CS 비용 발생                                                  │
│                                                                                 │
│  3. 좌석 예약                                                                    │
│     - 같은 좌석에 동시 예약 시도 빈번                                             │
│     - 중복 예약은 허용 불가                                                       │
│                                                                                 │
│  [낙관적 락이 적합한 경우]                                                        │
│                                                                                 │
│  1. 결제 상태 변경 (PaymentIntent)                                               │
│     - PENDING → APPROVED는 1회만 발생                                            │
│     - 같은 Intent를 동시에 승인할 확률 낮음                                       │
│     - 충돌 시 재시도하면 됨 (비용 낮음)                                           │
│                                                                                 │
│  2. 사용자 프로필 수정                                                           │
│     - 동시 수정 가능성 매우 낮음                                                  │
│     - 충돌 시 "다시 시도해주세요" 안내 가능                                        │
│                                                                                 │
│  3. 게시글/댓글 수정                                                             │
│     - 충돌 빈도 낮음                                                             │
│     - 충돌 시 사용자에게 알림 가능                                                │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

## 현재 구현 상태 분석

### 프로젝트 내 락 사용 현황

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                          현재 락 전략 분석                                        │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [비관적 락 적용 (모놀리스 - 지갑/잔액)]                                          │
│                                                                                 │
│  WalletStoreBalanceRepository.java:                                             │
│  ┌─────────────────────────────────────────────────────────────────────────┐    │
│  │  @Lock(LockModeType.PESSIMISTIC_WRITE)                                  │    │
│  │  @QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout",      │    │
│  │                          value = "3000"))  // 3초 타임아웃               │    │
│  │  Optional<WalletStoreBalance> lockByWalletIdAndStoreId(                 │    │
│  │      Long walletId, Long storeId);                                      │    │
│  └─────────────────────────────────────────────────────────────────────────┘    │
│                                                                                 │
│  사용 위치:                                                                      │
│  ├─ WalletService.doSharePoints() - 포인트 공유 시 잔액 잠금                      │
│  ├─ WalletService.doReclaimPoints() - 포인트 회수 시 잔액 잠금                    │
│  └─ InternalWalletService.capture() - 결제 자금 캡처 시 잔액 잠금                 │
│                                                                                 │
│  왜 비관적 락?                                                                   │
│  ├─ 동일 지갑에 동시 결제 가능성 있음 (가족 공유 지갑 등)                          │
│  ├─ 충돌 시 금전적 손실 발생 (잔액 불일치)                                        │
│  └─ 복구 비용이 높음 (환불 처리 필요)                                             │
│                                                                                 │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [낙관적 락 적용 (QR 서비스 - PaymentIntent)]                                    │
│                                                                                 │
│  PaymentIntent.java:                                                            │
│  ┌─────────────────────────────────────────────────────────────────────────┐    │
│  │  @Version                                                               │    │
│  │  @Column(name = "version", nullable = false)                            │    │
│  │  private Long version;  // 낙관적 락                                    │    │
│  └─────────────────────────────────────────────────────────────────────────┘    │
│                                                                                 │
│  왜 낙관적 락?                                                                   │
│  ├─ Intent는 1회성 생성 → 1회 승인의 단순한 흐름                                  │
│  ├─ 동일 Intent 동시 승인 시도 확률 낮음 (QR 스캔 → 승인은 순차적)                │
│  ├─ 충돌 시 "이미 처리된 결제입니다" 안내 가능                                    │
│  └─ 비관적 락의 대기 시간 없이 빠른 응답 가능                                     │
│                                                                                 │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [Atomic Update 적용 (추가 안전장치)]                                            │
│                                                                                 │
│  WalletStoreBalanceRepository.java:                                             │
│  ┌─────────────────────────────────────────────────────────────────────────┐    │
│  │  @Modifying                                                             │    │
│  │  @Query(value = """                                                     │    │
│  │      UPDATE wallet_store_balances                                       │    │
│  │         SET balance = balance - :amount                                 │    │
│  │       WHERE wallet_id = :walletId                                       │    │
│  │         AND store_id = :storeId                                         │    │
│  │         AND balance >= :amount                                          │    │
│  │  """, nativeQuery = true)                                               │    │
│  │  int decrementIfEnough(Long walletId, Long storeId, Long amount);       │    │
│  └─────────────────────────────────────────────────────────────────────────┘    │
│                                                                                 │
│  특징:                                                                          │
│  ├─ 조건부 UPDATE (balance >= amount 조건)                                       │
│  ├─ 반환값: 1 = 성공, 0 = 실패 (잔액 부족 또는 경합)                              │
│  ├─ DB 레벨에서 원자적 처리 (Read + Compare + Write가 한 번에)                   │
│  └─ 비관적 락 없이도 Lost Update 방지 가능                                        │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

## 각 락의 한계점과 해결 방안

### 비관적 락의 한계점

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                          비관적 락의 문제점                                       │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [문제 1: 데드락 (Deadlock)]                                                     │
│                                                                                 │
│  시나리오: 포인트 공유 중 양방향 잠금                                             │
│                                                                                 │
│  Transaction A                          Transaction B                           │
│  ─────────────────────────────────────────────────────────────                  │
│  LOCK 지갑 1 🔒                                                                  │
│                                         LOCK 지갑 2 🔒                           │
│  LOCK 지갑 2 대기... ⏳                                                          │
│                                         LOCK 지갑 1 대기... ⏳                   │
│                                                                                 │
│  → 서로 상대방의 락을 대기하며 영원히 진행 불가! 💀                               │
│                                                                                 │
│  [해결 방안]                                                                     │
│  ├─ 락 순서 고정: 항상 walletId 오름차순으로 락 획득                              │
│  │   if (walletId1 < walletId2) {                                               │
│  │       lock(walletId1); lock(walletId2);                                      │
│  │   } else {                                                                   │
│  │       lock(walletId2); lock(walletId1);                                      │
│  │   }                                                                          │
│  │                                                                              │
│  ├─ 락 타임아웃: 3초 대기 후 실패 처리 (현재 적용됨)                               │
│  │   @QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout",          │
│  │                          value = "3000"))                                    │
│  │                                                                              │
│  └─ DB 레벨 데드락 감지: InnoDB의 자동 데드락 감지 활용                            │
│                                                                                 │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [문제 2: 락 대기로 인한 처리량 저하]                                             │
│                                                                                 │
│  고부하 상황:                                                                    │
│  ├─ 100명이 동시에 같은 그룹 지갑에서 결제 시도                                   │
│  ├─ 99명은 락 대기 상태 (최대 3초씩)                                              │
│  └─ TPS 급격히 저하                                                              │
│                                                                                 │
│  [해결 방안]                                                                     │
│  ├─ 락 범위 최소화: 꼭 필요한 행만 잠금                                           │
│  │   // Bad: 전체 지갑 잠금                                                      │
│  │   SELECT * FROM wallets WHERE wallet_id = ? FOR UPDATE;                      │
│  │                                                                              │
│  │   // Good: 특정 매장 잔액만 잠금                                              │
│  │   SELECT * FROM wallet_store_balances                                        │
│  │   WHERE wallet_id = ? AND store_id = ? FOR UPDATE;                           │
│  │                                                                              │
│  ├─ Atomic Update 활용: 락 없이 조건부 업데이트                                   │
│  │   UPDATE wallet_store_balances                                               │
│  │   SET balance = balance - ?                                                  │
│  │   WHERE wallet_id = ? AND store_id = ? AND balance >= ?;                     │
│  │                                                                              │
│  └─ 락 타임아웃 단축: 3초 → 1초 (빠른 실패, 빠른 재시도)                          │
│                                                                                 │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [문제 3: 분산 환경에서의 한계]                                                   │
│                                                                                 │
│  MSA 환경:                                                                       │
│  ├─ QR 서비스 DB ≠ 모놀리스 DB                                                   │
│  ├─ DB 레벨 비관적 락은 단일 DB 내에서만 동작                                     │
│  └─ 크로스 서비스 락 불가능                                                       │
│                                                                                 │
│  [해결 방안]                                                                     │
│  ├─ 분산 락 (Redis): SETNX + TTL로 서비스 간 락 공유                             │
│  ├─ 멱등성 키: 중복 처리 방지 (현재 적용됨)                                       │
│  └─ 최종 일관성: 이벤트 소싱, Saga 패턴                                           │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 낙관적 락의 한계점

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                          낙관적 락의 문제점                                       │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [문제 1: 충돌 시 재시도 폭주 (Retry Storm)]                                      │
│                                                                                 │
│  시나리오: 인기 상품 재고 100개, 동시에 200명 구매 시도                            │
│                                                                                 │
│  Round 1:                                                                       │
│  ├─ 200명 동시 시도 → 1명 성공, 199명 실패                                       │
│  └─ 199명 재시도 발생                                                            │
│                                                                                 │
│  Round 2:                                                                       │
│  ├─ 199명 동시 재시도 → 1명 성공, 198명 실패                                     │
│  └─ 198명 재시도 발생                                                            │
│                                                                                 │
│  ... 반복 ...                                                                    │
│                                                                                 │
│  → 시스템 부하 폭증! DB 커넥션 고갈!                                              │
│                                                                                 │
│  [해결 방안]                                                                     │
│  ├─ 지수 백오프 (Exponential Backoff)                                            │
│  │   재시도 1회: 100ms 대기                                                      │
│  │   재시도 2회: 200ms 대기                                                      │
│  │   재시도 3회: 400ms 대기                                                      │
│  │   + 지터(Jitter) 추가로 동시 재시도 분산                                       │
│  │                                                                              │
│  ├─ 재시도 횟수 제한                                                             │
│  │   @Retry(maxAttempts = 3, backoff = @Backoff(delay = 100, multiplier = 2))   │
│  │                                                                              │
│  └─ 충돌 빈도 높으면 비관적 락으로 전환                                           │
│                                                                                 │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [문제 2: ABA 문제]                                                              │
│                                                                                 │
│  시나리오:                                                                       │
│  ├─ T1: 상태 읽음 (A)                                                            │
│  ├─ T2: 상태를 A → B로 변경                                                      │
│  ├─ T3: 상태를 B → A로 되돌림                                                    │
│  └─ T1: 상태가 A인지 확인 → 동일! → 업데이트 진행                                 │
│                                                                                 │
│  문제: T1은 중간에 상태가 변경되었다는 것을 모름                                   │
│                                                                                 │
│  [해결 방안]                                                                     │
│  ├─ @Version 사용 (현재 적용됨)                                                   │
│  │   → 상태가 아닌 버전 번호로 변경 감지                                          │
│  │   → A(v1) → B(v2) → A(v3) 이므로 v1 ≠ v3 감지 가능                            │
│  │                                                                              │
│  └─ 타임스탬프 활용                                                              │
│      → updatedAt 컬럼으로 변경 시점 추적                                          │
│                                                                                 │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [문제 3: 긴 트랜잭션에서의 충돌 증가]                                            │
│                                                                                 │
│  시나리오: 트랜잭션이 10초 동안 열려있는 경우                                      │
│  ├─ 그 사이 다른 트랜잭션이 같은 데이터 수정 가능성 높음                           │
│  └─ 낙관적 락 충돌 확률 증가                                                      │
│                                                                                 │
│  [해결 방안]                                                                     │
│  ├─ 트랜잭션 범위 최소화                                                         │
│  │   // Bad: 외부 API 호출을 트랜잭션 안에서                                      │
│  │   @Transactional                                                             │
│  │   public void process() {                                                    │
│  │       Payment p = repository.findById(id);                                   │
│  │       externalApi.call();  // 3초 소요                                        │
│  │       p.setStatus(APPROVED);                                                 │
│  │   }                                                                          │
│  │                                                                              │
│  │   // Good: 외부 호출 후 트랜잭션                                              │
│  │   public void process() {                                                    │
│  │       externalApi.call();  // 트랜잭션 밖에서                                 │
│  │       updateStatus(id, APPROVED);  // 짧은 트랜잭션                           │
│  │   }                                                                          │
│  │                                                                              │
│  └─ 필요한 경우 비관적 락으로 전환                                                │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

```javascript
// monitoring/load-tests/scenarios/concurrency/concurrent-payment-test.js

import http from 'k6/http';
import { check, sleep } from 'k6';
import { Counter } from 'k6/metrics';

const successCounter = new Counter('payment_success');
const failCounter = new Counter('payment_fail');
const conflictCounter = new Counter('payment_conflict');

export let options = {
  scenarios: {
    // 같은 지갑에 동시 결제 시뮬레이션
    concurrent_same_wallet: {
      executor: 'per-vu-iterations',
      vus: 10,  // 10명이 동시에
      iterations: 1,  // 각각 1번씩 결제 시도
      exec: 'sameWalletPayment',
    },
  },
  thresholds: {
    'payment_success': ['count==1'],  // 정확히 1건만 성공
    'payment_conflict': ['count==9'],  // 9건은 충돌
  },
};

const SHARED_WALLET_ID = __ENV.WALLET_ID;  // 테스트용 공유 지갑

export function sameWalletPayment() {
  const res = http.post(
    `${__ENV.BASE_URL}/internal/wallets/${SHARED_WALLET_ID}/capture`,
    JSON.stringify({ amount: 10000 }),
    { headers: { 'Content-Type': 'application/json' } }
  );

  if (res.status === 200) {
    successCounter.add(1);
  } else if (res.status === 409) {  // Conflict
    conflictCounter.add(1);
  } else {
    failCounter.add(1);
  }
}
```
