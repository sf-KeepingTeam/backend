# 기술 선택 가이드: 문제별 해결책 비교 분석

## 요약: 문제 / 해결 후보 / 선택 / 이유

| 문제 | 해결 후보 | 선택 | 이유 |
|------|----------|------|------|
| **모놀리식 병목** | A) 스케일업, B) 스케일아웃, C) MSA 분리, D) 캐싱 | **C + D** | 핵심 도메인 격리 + 읽기 부하 감소 |
| **연쇄 장애** | A) Circuit Breaker, B) Retry, C) Timeout, D) Bulkhead, E) Rate Limiter | **A + B + C** | 장애 전파 차단 + 일시적 오류 복구 |
| **로그 파편화** | A) 중앙 로그(ELK), B) 분산 추적(Zipkin), C) APM(Datadog), D) 로그 ID 전파 | **D** | 비용 0, 구현 간단, 즉시 효과 |
| **중복 결제** | A) 멱등성 키, B) 분산 트랜잭션(2PC), C) Saga, D) 재시도 금지 | **A** | 업계 표준, 간단, 고성능 |
| **Lost Update** | A) 비관적 락, B) 낙관적 락, C) 분산 락, D) Atomic Update | **A (잔액) + B (상태)** | 용도별 최적 전략 |

## 1. 모놀리식 병목 문제

### 문제 정의

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           QR 결제 병목 현상                                       │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [상황]                                                                          │
│  - Wallet API에 부하 폭주 (이벤트 등)                                             │
│  - QR 결제는 Wallet과 무관한데 함께 느려짐                                         │
│                                                                                 │
│  [원인]                                                                          │
│  - 단일 서버, 단일 DB Connection Pool                                            │
│  - Wallet이 Connection 점유 → QR가 Connection 대기                               │
│                                                                                 │
│  [영향]                                                                          │
│  - QR 응답시간: 25ms → 8,169ms (320배)                                           │
│  - 결제 실패율 급증                                                               │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 해결 후보 비교

| 후보 | 설명 | 장점 | 단점 |
|------|------|------|------|
| **A) 스케일업** | 서버 사양 증가 | 구현 간단 | 한계 있음, 비용 증가 |
| **B) 스케일아웃** | 서버 수 증가 (로드밸런싱) | 수평 확장 가능 | 상태 공유 문제, 세션 관리 |
| **C) MSA 분리** | QR 서비스를 별도 서버로 | 완전한 격리, 독립 배포 | 복잡도 증가, 네트워크 오버헤드 |
| **D) 캐싱** | Redis로 읽기 부하 감소 | 응답 속도 향상 | 캐시 일관성 관리 필요 |

### 선택: C + D (MSA 분리 + Redis 캐싱)

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           선택 이유                                               │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [왜 스케일업(A)은 부적합한가?]                                                   │
│  - 근본적 해결 아님: CPU/메모리 증가해도 Connection Pool 경합은 동일               │
│  - 비용 효율성 낮음: t3.medium → t3.xlarge는 4배 비용이지만 4배 성능 아님          │
│  - 한계점 존재: 단일 서버는 수직 확장에 물리적 한계                                │
│                                                                                 │
│  [왜 스케일아웃(B)은 단독으로 부족한가?]                                           │
│  - DB 병목 미해결: 서버 2대여도 DB Connection Pool 경합은 동일                    │
│  - 상태 공유 문제: QR 토큰이 서버 A에 있는데 요청이 서버 B로 가면?                  │
│  - 세션 스티키니스 필요 → 복잡도 증가                                             │
│                                                                                 │
│  [왜 MSA(C)를 선택했는가?]                                                        │
│  - 완전한 격리: QR 서비스는 별도 DB, 별도 Connection Pool                         │
│  - 독립 배포: QR만 수정해도 전체 재배포 불필요                                     │
│  - 독립 스케일링: QR 부하 증가 시 QR 서버만 증설                                   │
│  - 장애 격리: Wallet 장애가 QR에 영향 최소화 (Circuit Breaker 활용)                │
│                                                                                 │
│  [왜 캐싱(D)을 함께 적용했는가?]                                                  │
│  - MSA 분리 후에도 모놀리스 호출 필요 (Store, Menu 조회)                          │
│  - 캐싱으로 모놀리스 의존도 감소                                                  │
│  - PUSH 모드로 Cold Start 문제 해결                                              │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 각 해결책 상세 설명

#### A) 스케일업 (Vertical Scaling)

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           스케일업 상세                                           │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [개념]                                                                          │
│  "더 강력한 단일 서버로 교체"                                                     │
│                                                                                 │
│  Before:                      After:                                            │
│  ┌──────────────┐            ┌──────────────┐                                   │
│  │ t3.medium    │     →      │ t3.xlarge    │                                   │
│  │ 2 vCPU       │            │ 4 vCPU       │                                   │
│  │ 4GB RAM      │            │ 16GB RAM     │                                   │
│  └──────────────┘            └──────────────┘                                   │
│                                                                                 │
│  [동작 원리]                                                                     │
│  - CPU 증가 → 동시 처리량 증가                                                   │
│  - 메모리 증가 → JVM Heap 증가 → GC 빈도 감소                                    │
│  - 네트워크 대역폭 증가 → I/O 처리량 증가                                         │
│                                                                                 │
│  [적합한 경우]                                                                   │
│  - 일시적 부하 증가                                                              │
│  - 빠른 대응 필요 (분 단위)                                                       │
│  - 아키텍처 변경 부담스러울 때                                                    │
│                                                                                 │
│  [한계점]                                                                        │
│  - AWS 최대 사양: u-24tb1.112xlarge (448 vCPU, 24TB RAM) - 그 이상 불가           │
│  - 비용 비선형 증가: 사양 2배 → 비용 2배+ (고사양일수록 단가 높음)                  │
│  - 단일 장애점: 그 서버 죽으면 전체 서비스 다운                                    │
│  - Connection Pool 경합 미해결                                                   │
│                                                                                 │
│  [비용 예시 (AWS EC2, 서울 리전)]                                                │
│  t3.medium  : $0.052/시간 → 월 $37                                              │
│  t3.xlarge  : $0.208/시간 → 월 $150 (4배 비용)                                   │
│  t3.2xlarge : $0.416/시간 → 월 $300 (8배 비용)                                   │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

#### B) 스케일아웃 (Horizontal Scaling)

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           스케일아웃 상세                                         │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [개념]                                                                          │
│  "동일 사양 서버를 여러 대 운영"                                                  │
│                                                                                 │
│                    ┌─────────────┐                                              │
│                    │ Load        │                                              │
│                    │ Balancer    │                                              │
│                    └──────┬──────┘                                              │
│               ┌──────────┼──────────┐                                           │
│               ▼          ▼          ▼                                           │
│         ┌─────────┐ ┌─────────┐ ┌─────────┐                                     │
│         │ Server1 │ │ Server2 │ │ Server3 │                                     │
│         └────┬────┘ └────┬────┘ └────┬────┘                                     │
│              └───────────┼───────────┘                                          │
│                          ▼                                                      │
│                    ┌─────────┐                                                  │
│                    │   DB    │  ← 여전히 단일 DB!                               │
│                    └─────────┘                                                  │
│                                                                                 │
│  [동작 원리]                                                                     │
│  - Load Balancer가 요청을 여러 서버에 분배                                        │
│  - 각 서버가 일부 요청만 처리 → 서버당 부하 감소                                   │
│  - 서버 1대 장애 시에도 나머지가 서비스 유지                                       │
│                                                                                 │
│  [로드밸런싱 알고리즘]                                                           │
│  - Round Robin: 순서대로 분배 (가장 단순)                                         │
│  - Least Connections: 연결 적은 서버로 분배                                       │
│  - IP Hash: 같은 IP는 같은 서버로 (세션 스티키니스)                                │
│  - Weighted: 서버 사양에 따라 가중치 부여                                         │
│                                                                                 │
│  [문제점]                                                                        │
│  1. 상태 공유 문제                                                               │
│     - QR 토큰을 Server1에서 생성                                                 │
│     - 다음 요청이 Server2로 가면 토큰 없음!                                       │
│     - 해결: Redis 세션 스토어, Sticky Session                                    │
│                                                                                 │
│  2. DB 병목 미해결                                                               │
│     - 서버 3대여도 DB는 1대                                                       │
│     - Connection Pool 3배 → DB 부하 3배                                          │
│     - 해결: Read Replica, DB 샤딩                                                │
│                                                                                 │
│  3. 배포 복잡도                                                                  │
│     - 3대 모두 배포해야 함                                                        │
│     - 롤링 배포, Blue-Green 배포 필요                                             │
│                                                                                 │
│  [적합한 경우]                                                                   │
│  - Stateless 애플리케이션                                                        │
│  - 읽기 위주 워크로드                                                             │
│  - 점진적 확장 필요                                                               │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

#### C) MSA 분리 (Microservices Architecture)

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           MSA 분리 상세                                           │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [개념]                                                                          │
│  "하나의 큰 애플리케이션을 작은 독립 서비스로 분리"                                 │
│                                                                                 │
│  Before (Monolith):             After (MSA):                                    │
│  ┌──────────────────┐           ┌──────────┐    ┌──────────┐                    │
│  │   Monolith App   │           │ QR Svc   │    │ Wallet   │                    │
│  │ ┌──────────────┐ │     →     │          │    │ Svc      │                    │
│  │ │ QR Service   │ │           │ Redis    │    │ MySQL    │                    │
│  │ │ Wallet Svc   │ │           └──────────┘    └──────────┘                    │
│  │ │ Payment Svc  │ │           ┌──────────┐                                    │
│  │ └──────────────┘ │           │ Payment  │                                    │
│  │      MySQL       │           │ Svc      │                                    │
│  └──────────────────┘           └──────────┘                                    │
│                                                                                 │
│  [분리 기준 (DDD)]                                                               │
│  - Bounded Context: 비즈니스 도메인 경계로 분리                                   │
│  - QR 결제: 빠른 응답 필요, 독립적 생명주기                                        │
│  - Wallet: 정합성 중요, 트랜잭션 무결성                                           │
│                                                                                 │
│  [통신 방식]                                                                     │
│  1. 동기 (Sync) - REST API / gRPC                                               │
│     - 장점: 즉각 응답, 구현 간단                                                  │
│     - 단점: 호출 서비스 장애 시 영향받음                                          │
│     - 현재 사용 중                                                               │
│                                                                                 │
│  2. 비동기 (Async) - Message Queue (Kafka, RabbitMQ)                             │
│     - 장점: 느슨한 결합, 버퍼링                                                   │
│     - 단점: 복잡도 증가, 최종 일관성                                              │
│     - 알림 전송 등에 적합                                                         │
│                                                                                 │
│  [장점]                                                                          │
│  - 독립 배포: QR만 수정해도 QR만 배포                                             │
│  - 독립 스케일링: QR 부하 증가 → QR 서버만 증설                                   │
│  - 기술 다양성: QR은 Redis, Wallet은 MySQL                                       │
│  - 장애 격리: Wallet 장애가 QR에 전파되지 않음                                    │
│  - 팀 독립성: QR팀, Wallet팀이 독립적으로 개발                                    │
│                                                                                 │
│  [단점]                                                                          │
│  - 복잡도 증가: 서비스 간 통신, 분산 트랜잭션                                      │
│  - 운영 부담: 여러 서버 모니터링, 배포 파이프라인                                  │
│  - 네트워크 오버헤드: HTTP 호출 지연                                              │
│  - 데이터 일관성: 서비스 간 데이터 동기화 필요                                     │
│                                                                                 │
│  [Anti-Corruption Layer (ACL)]                                                  │
│  - MSA 분리 시 외부 서비스 호출을 추상화                                          │
│  - 현재 WalletClient, StoreClient 등이 ACL 역할                                  │
│  - 외부 서비스 변경 시 ACL만 수정                                                 │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

#### D) 캐싱 (Caching)

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           캐싱 전략 상세                                          │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [캐시 패턴 비교]                                                                │
│                                                                                 │
│  1. Cache-Aside (PULL 모드)                                                     │
│     ┌─────────────────────────────────────────────┐                             │
│     │  Application                                │                             │
│     │       │                                     │                             │
│     │  1. 캐시 조회 ─────────► Cache              │                             │
│     │       │                   │                 │                             │
│     │  2. 캐시 미스 시          │                 │                             │
│     │     DB 조회 ────────────► DB                │                             │
│     │       │                                     │                             │
│     │  3. 캐시 저장 ─────────► Cache              │                             │
│     └─────────────────────────────────────────────┘                             │
│                                                                                 │
│     장점: 구현 간단, 필요한 데이터만 캐시                                         │
│     단점: 첫 요청 느림 (Cold Start), Cache Miss 시 DB 부하                       │
│                                                                                 │
│  2. Write-Through                                                               │
│     ┌─────────────────────────────────────────────┐                             │
│     │  Application                                │                             │
│     │       │                                     │                             │
│     │  1. 쓰기 ────────────────► Cache ──► DB     │                             │
│     │       │                   (동시 기록)        │                             │
│     │  2. 읽기 ────────────────► Cache            │                             │
│     └─────────────────────────────────────────────┘                             │
│                                                                                 │
│     장점: 캐시와 DB 항상 동기화                                                   │
│     단점: 쓰기 지연 증가, 불필요한 데이터도 캐시                                   │
│                                                                                 │
│  3. Write-Behind (Write-Back)                                                   │
│     ┌─────────────────────────────────────────────┐                             │
│     │  Application                                │                             │
│     │       │                                     │                             │
│     │  1. 쓰기 ────────────────► Cache            │                             │
│     │                             │               │                             │
│     │                       (비동기 배치)          │                             │
│     │                             ▼               │                             │
│     │                            DB               │                             │
│     └─────────────────────────────────────────────┘                             │
│                                                                                 │
│     장점: 쓰기 성능 극대화                                                        │
│     단점: 데이터 유실 위험 (캐시 장애 시)                                          │
│                                                                                 │
│  4. Refresh-Ahead (PUSH 모드) ← 현재 선택                                        │
│     ┌─────────────────────────────────────────────┐                             │
│     │  [시작 시] Cache Warming                    │                             │
│     │  DB ─────────────────────► Cache (전체 로드)│                             │
│     │                                             │                             │
│     │  [변경 시] Webhook                          │                             │
│     │  DB 변경 ───► Webhook ───► Cache (갱신)     │                             │
│     │                                             │                             │
│     │  [조회 시]                                  │                             │
│     │  Application ────────────► Cache (항상 히트)│                             │
│     └─────────────────────────────────────────────┘                             │
│                                                                                 │
│     장점: 첫 요청도 빠름, Cache Miss 없음                                         │
│     단점: Warming 시간, Webhook 구현 필요                                         │
│                                                                                 │
│  [왜 PUSH 모드를 선택했는가?]                                                    │
│  - Store/Menu는 자주 변하지 않음 (읽기 >> 쓰기)                                   │
│  - 결제 시 첫 요청도 빨라야 함 (Cold Start 불가)                                  │
│  - 모놀리스 장애 시에도 캐시 데이터로 서비스 가능                                  │
│                                                                                 │
│  [캐시 무효화 전략]                                                              │
│  - TTL (Time To Live): 일정 시간 후 자동 만료                                    │
│  - Event-based: 데이터 변경 시 즉시 무효화 (현재 사용)                            │
│  - Manual: 관리자가 수동 무효화                                                  │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

## 2. 연쇄 장애 (Cascading Failure)

### 문제 정의

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           연쇄 장애 시나리오                                       │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  모놀리스 장애                                                                   │
│       │                                                                         │
│       ▼                                                                         │
│  QR Service → 모놀리스 호출 → 30초 타임아웃 대기                                  │
│       │                                                                         │
│       ▼                                                                         │
│  스레드 블로킹 (200개 스레드가 모두 대기)                                          │
│       │                                                                         │
│       ▼                                                                         │
│  신규 요청 처리 불가 (스레드 풀 고갈)                                              │
│       │                                                                         │
│       ▼                                                                         │
│  QR Service도 다운! (연쇄 장애 완성)                                              │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 해결 후보 비교

| 후보 | 설명 | 적용 시점 | 복잡도 |
|------|------|----------|--------|
| **A) Circuit Breaker** | 장애 감지 시 빠른 실패 | 장애 감지 후 | 중 |
| **B) Retry** | 일시적 오류 시 재시도 | 오류 발생 시 | 낮 |
| **C) Timeout** | 응답 대기 시간 제한 | 항상 | 낮 |
| **D) Bulkhead** | 리소스 격리 (스레드 풀 분리) | 항상 | 중 |
| **E) Rate Limiter** | 요청 수 제한 | 요청 진입 시 | 낮 |
| **F) Fallback** | 대체 응답 반환 | 실패 시 | 중 |
| **G) Saga Pattern** | 분산 트랜잭션 보상 | 트랜잭션 실패 시 | 높 |

### 선택: A + B + C (Circuit Breaker + Retry + Timeout)

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           선택 이유                                               │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [조합 전략]                                                                     │
│                                                                                 │
│  요청 ───► Timeout (10초) ───► Retry (3회) ───► Circuit Breaker ───► 호출       │
│                                                                                 │
│  1. Timeout: 응답 대기 시간 제한 (무한 대기 방지)                                  │
│  2. Retry: 일시적 네트워크 오류 복구                                              │
│  3. Circuit Breaker: 지속적 장애 시 빠른 실패                                     │
│                                                                                 │
│  [왜 Bulkhead(D)는 Phase 2인가?]                                                 │
│  - 기본 3종 (A+B+C)만으로도 연쇄 장애 방지 가능                                   │
│  - Bulkhead는 더 세밀한 격리 (고급 기능)                                          │
│  - 구현 복잡도 대비 효과가 추가적                                                 │
│                                                                                 │
│  [왜 Rate Limiter(E)는 Phase 2인가?]                                             │
│  - 정상 상황에서는 불필요                                                         │
│  - DDoS나 급격한 부하 시에만 필요                                                 │
│  - 오탐 시 정상 요청도 차단 위험                                                  │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 각 해결책 상세 설명

#### A) Circuit Breaker

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           Circuit Breaker 상세                                    │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [개념 - 전기 회로 차단기에서 유래]                                               │
│  - 과부하 시 회로를 끊어 화재 방지                                                │
│  - 소프트웨어에서는 장애 전파를 끊어 연쇄 장애 방지                                │
│                                                                                 │
│  [상태 전이]                                                                     │
│                                                                                 │
│       성공률 정상                    실패율 > 임계치                              │
│           │                              │                                      │
│           ▼                              ▼                                      │
│      ┌─────────┐                    ┌─────────┐                                 │
│      │ CLOSED  │ ──────────────────►│  OPEN   │                                 │
│      │ (정상)  │   50% 이상 실패    │ (차단)  │                                 │
│      └────▲────┘                    └────┬────┘                                 │
│           │                              │                                      │
│           │         waitDuration (30초) │                                       │
│           │                              ▼                                      │
│           │                        ┌──────────┐                                 │
│           │         성공           │HALF_OPEN │                                 │
│           └────────────────────────│ (테스트) │                                 │
│                                    └──────────┘                                 │
│                    실패 시 다시 OPEN으로                                         │
│                                                                                 │
│  [설정 파라미터]                                                                 │
│  ┌────────────────────────────────────────────────────────────────────────┐     │
│  │  slidingWindowSize: 10        # 최근 10개 요청 기준 판단                │     │
│  │  minimumNumberOfCalls: 5      # 최소 5개 요청 후 판단 시작              │     │
│  │  failureRateThreshold: 50     # 50% 이상 실패 시 OPEN                  │     │
│  │  waitDurationInOpenState: 30s # OPEN 후 30초 대기                       │     │
│  │  permittedNumberOfCallsInHalfOpenState: 3  # HALF_OPEN에서 3개 테스트   │     │
│  └────────────────────────────────────────────────────────────────────────┘     │
│                                                                                 │
│  [Sliding Window 종류]                                                          │
│                                                                                 │
│  1. Count-based (현재 사용)                                                      │
│     - 최근 N개 요청 기준                                                         │
│     - 예: 최근 10개 중 5개 실패 → 50% 실패율                                     │
│                                                                                 │
│  2. Time-based                                                                  │
│     - 최근 N초 요청 기준                                                         │
│     - 예: 최근 10초 동안의 요청 중 50% 실패                                       │
│                                                                                 │
│  [Fallback 처리]                                                                │
│  @CircuitBreaker(name = "walletClient", fallbackMethod = "fallback")            │
│  public BigDecimal getBalance(Long walletId) { ... }                            │
│                                                                                 │
│  private BigDecimal fallback(Long walletId, Throwable t) {                      │
│      // OPEN 상태일 때 호출됨                                                    │
│      log.warn("Circuit Breaker OPEN - fallback 실행");                          │
│      throw new ServiceUnavailableException("서비스 일시 불가");                   │
│  }                                                                              │
│                                                                                 │
│  [구현체 비교]                                                                   │
│  - Resilience4j: 경량, Spring Boot 통합 (현재 사용)                              │
│  - Hystrix: Netflix, 유지보수 중단 (deprecated)                                  │
│  - Sentinel: Alibaba, 더 많은 기능                                               │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

#### B) Retry

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           Retry 전략 상세                                         │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [개념]                                                                          │
│  - 일시적 오류(네트워크 불안정, 일시적 부하) 시 자동 재시도                        │
│  - 영구적 오류(잘못된 요청, 인증 실패)는 재시도해도 의미 없음                      │
│                                                                                 │
│  [재시도 가능한 오류 (Transient)]                                                │
│  - 500 Internal Server Error (서버 일시 오류)                                    │
│  - 502 Bad Gateway (프록시 오류)                                                 │
│  - 503 Service Unavailable (과부하)                                              │
│  - 504 Gateway Timeout (타임아웃)                                                │
│  - Connection Refused (연결 거부)                                                │
│  - Connection Timeout (연결 시간 초과)                                            │
│                                                                                 │
│  [재시도 불가 오류 (Non-Transient)]                                              │
│  - 400 Bad Request (잘못된 요청)                                                 │
│  - 401 Unauthorized (인증 실패)                                                  │
│  - 403 Forbidden (권한 없음)                                                     │
│  - 404 Not Found (리소스 없음)                                                   │
│                                                                                 │
│  [Backoff 전략]                                                                  │
│                                                                                 │
│  1. Fixed Delay (고정 대기)                                                      │
│     재시도 1: 1초 대기                                                           │
│     재시도 2: 1초 대기                                                           │
│     재시도 3: 1초 대기                                                           │
│     문제: 모든 클라이언트가 동시에 재시도 → 부하 폭주                             │
│                                                                                 │
│  2. Exponential Backoff (지수 증가)                                              │
│     재시도 1: 100ms 대기                                                         │
│     재시도 2: 200ms 대기 (2배)                                                   │
│     재시도 3: 400ms 대기 (2배)                                                   │
│     장점: 부하 분산                                                              │
│                                                                                 │
│  3. Exponential Backoff + Jitter (무작위성 추가) ← 권장                          │
│     재시도 1: 100ms + random(0~50ms)                                             │
│     재시도 2: 200ms + random(0~100ms)                                            │
│     재시도 3: 400ms + random(0~200ms)                                            │
│     장점: 동시 재시도 분산 (Thundering Herd 방지)                                 │
│                                                                                 │
│  [설정 예시]                                                                     │
│  ┌────────────────────────────────────────────────────────────────────────┐     │
│  │  resilience4j:                                                         │     │
│  │    retry:                                                              │     │
│  │      instances:                                                        │     │
│  │        walletClient:                                                   │     │
│  │          maxAttempts: 3                    # 최대 3회                   │     │
│  │          waitDuration: 100ms               # 초기 대기                  │     │
│  │          enableExponentialBackoff: true    # 지수 증가                  │     │
│  │          exponentialBackoffMultiplier: 2   # 2배씩 증가                 │     │
│  │          enableRandomizedWait: true        # 무작위성 추가              │     │
│  │          randomizedWaitFactor: 0.5         # 50% 범위                   │     │
│  │          retryExceptions:                                              │     │
│  │            - java.net.ConnectException                                 │     │
│  │            - java.net.SocketTimeoutException                           │     │
│  │          ignoreExceptions:                                             │     │
│  │            - com.example.BusinessException # 비즈니스 에러는 재시도 안함│     │
│  └────────────────────────────────────────────────────────────────────────┘     │
│                                                                                 │
│  [주의: 멱등성]                                                                  │
│  - 재시도 = 같은 요청을 여러 번 보내는 것                                         │
│  - 쓰기 작업(결제 등)은 멱등성 키 필수                                            │
│  - 읽기 작업은 안전하게 재시도 가능                                               │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

#### C) Timeout

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           Timeout 전략 상세                                       │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [개념]                                                                          │
│  - 응답 대기 시간에 제한을 둠                                                     │
│  - 무한 대기로 인한 리소스 고갈 방지                                              │
│                                                                                 │
│  [Timeout 종류]                                                                  │
│                                                                                 │
│  1. Connection Timeout                                                          │
│     - TCP 연결 수립까지 대기 시간                                                 │
│     - 서버가 아예 응답하지 않을 때 감지                                           │
│     - 권장: 2~5초                                                                │
│                                                                                 │
│  2. Read Timeout (Socket Timeout)                                               │
│     - 연결 후 데이터 수신 대기 시간                                               │
│     - 서버가 처리 중인데 너무 오래 걸릴 때 감지                                    │
│     - 권장: 5~30초 (작업 특성에 따라)                                             │
│                                                                                 │
│  3. Write Timeout                                                               │
│     - 데이터 전송 완료 대기 시간                                                  │
│     - 대용량 업로드 시 중요                                                       │
│                                                                                 │
│  [계층별 Timeout 설계]                                                           │
│                                                                                 │
│  ┌─────────────────────────────────────────────────────────────────────────┐    │
│  │                                                                         │    │
│  │  Client (App) ─────────────────────────────────────────► 10초          │    │
│  │       │                                                                 │    │
│  │       ▼                                                                 │    │
│  │  Nginx Gateway ──────────────────────────────► 8초                      │    │
│  │       │                                                                 │    │
│  │       ▼                                                                 │    │
│  │  QR Service (TimeLimiter) ────────────► 5초                             │    │
│  │       │                                                                 │    │
│  │       ▼                                                                 │    │
│  │  RestTemplate ─────────────► connect: 2초, read: 3초                    │    │
│  │       │                                                                 │    │
│  │       ▼                                                                 │    │
│  │  Monolith                                                               │    │
│  │                                                                         │    │
│  │  규칙: 상위 Timeout > 하위 Timeout (여유 두기)                           │    │
│  │                                                                         │    │
│  └─────────────────────────────────────────────────────────────────────────┘    │
│                                                                                 │
│  [왜 계층별로 다르게 설정하는가?]                                                 │
│  - 하위 계층 Timeout이 상위보다 크면 의미 없음                                    │
│  - 예: RestTemplate 30초인데 Gateway 8초면                                       │
│    → Gateway에서 먼저 타임아웃 → RestTemplate은 계속 대기 (리소스 낭비)           │
│                                                                                 │
│  [설정 예시]                                                                     │
│  ┌────────────────────────────────────────────────────────────────────────┐     │
│  │  // RestTemplate                                                       │     │
│  │  HttpComponentsClientHttpRequestFactory factory =                      │     │
│  │      new HttpComponentsClientHttpRequestFactory();                     │     │
│  │  factory.setConnectTimeout(Duration.ofSeconds(2));                     │     │
│  │  factory.setReadTimeout(Duration.ofSeconds(3));                        │     │
│  │                                                                        │     │
│  │  // Resilience4j TimeLimiter                                           │     │
│  │  resilience4j:                                                         │     │
│  │    timelimiter:                                                        │     │
│  │      instances:                                                        │     │
│  │        walletClient:                                                   │     │
│  │          timeoutDuration: 5s                                           │     │
│  │          cancelRunningFuture: true                                     │     │
│  │                                                                        │     │
│  │  // Nginx                                                              │     │
│  │  proxy_connect_timeout 5s;                                             │     │
│  │  proxy_read_timeout 8s;                                                │     │
│  └────────────────────────────────────────────────────────────────────────┘     │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

#### D) Bulkhead

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           Bulkhead 패턴 상세                                      │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [개념 - 선박의 격벽(Bulkhead)에서 유래]                                          │
│  - 선박은 여러 구역으로 나뉨                                                      │
│  - 한 구역에 물이 차도 다른 구역은 안전                                           │
│  - 소프트웨어에서는 리소스를 격리하여 한 서비스 문제가 전파되지 않도록 함          │
│                                                                                 │
│  [Bulkhead 종류]                                                                 │
│                                                                                 │
│  1. Semaphore Bulkhead (동시 호출 제한)                                          │
│     ┌───────────────────────────────────────────────────────────────────┐       │
│     │                                                                   │       │
│     │  WalletClient용 Semaphore: 최대 10개 동시 호출 허용               │       │
│     │  ┌─┬─┬─┬─┬─┬─┬─┬─┬─┬─┐                                           │       │
│     │  │●│●│●│●│●│○│○│○│○│○│  (● = 사용 중, ○ = 여유)                  │       │
│     │  └─┴─┴─┴─┴─┴─┴─┴─┴─┴─┘                                           │       │
│     │                                                                   │       │
│     │  11번째 요청 → 대기 또는 즉시 거부                                 │       │
│     │                                                                   │       │
│     └───────────────────────────────────────────────────────────────────┘       │
│                                                                                 │
│     장점: 경량, 빠름                                                             │
│     단점: 스레드 자체는 공유 (블로킹 발생 가능)                                   │
│                                                                                 │
│  2. Thread Pool Bulkhead (스레드 풀 격리)                                        │
│     ┌───────────────────────────────────────────────────────────────────┐       │
│     │                                                                   │       │
│     │  Main Thread Pool (Tomcat): 200 threads                           │       │
│     │  ┌─────────────────────────────────────────────────────────────┐  │       │
│     │  │ WalletClient Pool: 10 threads (격리된 별도 풀)              │  │       │
│     │  │ ┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐                             │  │       │
│     │  │ │T1│T2│T3│T4│T5│T6│T7│T8│T9│10│                             │  │       │
│     │  │ └──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘                             │  │       │
│     │  └─────────────────────────────────────────────────────────────┘  │       │
│     │                                                                   │       │
│     │  WalletClient가 10개 스레드 전부 사용해도                         │       │
│     │  Main Pool 190개는 다른 요청 처리 가능                            │       │
│     │                                                                   │       │
│     └───────────────────────────────────────────────────────────────────┘       │
│                                                                                 │
│     장점: 완전한 격리                                                            │
│     단점: 스레드 생성 오버헤드, 컨텍스트 스위칭 비용                               │
│                                                                                 │
│  [설정 예시]                                                                     │
│  ┌────────────────────────────────────────────────────────────────────────┐     │
│  │  resilience4j:                                                         │     │
│  │    bulkhead:                                                           │     │
│  │      instances:                                                        │     │
│  │        walletClient:                                                   │     │
│  │          maxConcurrentCalls: 10     # 최대 10개 동시 호출              │     │
│  │          maxWaitDuration: 500ms     # 초과 시 500ms 대기 후 거부       │     │
│  │                                                                        │     │
│  │    thread-pool-bulkhead:                                               │     │
│  │      instances:                                                        │     │
│  │        walletClient:                                                   │     │
│  │          maxThreadPoolSize: 10      # 스레드 풀 크기                   │     │
│  │          coreThreadPoolSize: 5      # 코어 스레드                      │     │
│  │          queueCapacity: 20          # 대기 큐 크기                     │     │

### 해결 후보 비교

| 후보 | 설명 | 비용 | 복잡도 | 효과 |

## 4. 중복 결제 문제

### 문제 정의

```
네트워크 타임아웃 → 재시도 → 같은 결제가 2번 처리됨
```

### 해결 후보 비교

| 후보 | 설명 | 복잡도 | 성능 | 일관성 |
|------|------|--------|------|--------|
| **A) 멱등성 키** | 요청에 고유 키 부여 | 낮음 | 높음 | 최종 |
| **B) 분산 트랜잭션 (2PC)** | Two-Phase Commit | 매우 높음 | 낮음 | 강력 |
| **C) Saga 패턴** | 보상 트랜잭션 | 높음 | 중간 | 최종 |
| **D) 재시도 금지** | 실패 시 재시도 안함 | 매우 낮음 | - | - |

### 선택: A (멱등성 키)

```
[선택 이유 - 이전 문서 참조]
- 업계 표준 (Stripe, PayPal, 토스)
- 구현 간단 (HTTP 헤더 + DB 테이블)
- 성능 영향 최소 (SELECT 1회)
- Retry 정책과 자연스럽게 통합
```

### 각 해결책 상세 설명

#### B) 분산 트랜잭션 (2PC - Two-Phase Commit)

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           2PC 상세                                               │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [개념]                                                                          │
│  - Coordinator가 모든 참여자(Participant)에게 Commit 준비 요청                   │
│  - 모두 OK면 Commit, 하나라도 실패면 Rollback                                    │
│                                                                                 │
│  [Phase 1: Prepare (투표)]                                                       │
│                                                                                 │
│      Coordinator                                                                │
│           │                                                                     │
│           │ "Prepare to commit"                                                 │
│           ├─────────────────────────────────────────►  QR Service               │
│           │                                            │                        │
│           │                                            │ (로컬 작업 수행)        │
│           │                                            │ (아직 Commit 안함)      │
│           │◄──────────────── "Ready" ──────────────────┘                        │
│           │                                                                     │
│           │ "Prepare to commit"                                                 │
│           ├─────────────────────────────────────────►  Wallet Service           │
│           │                                            │                        │
│           │                                            │ (잔액 차감 준비)        │
│           │                                            │ (아직 Commit 안함)      │
│           │◄──────────────── "Ready" ──────────────────┘                        │
│           │                                                                     │
│                                                                                 │
│  [Phase 2: Commit (또는 Abort)]                                                  │
│                                                                                 │
│      Coordinator                                                                │
│           │                                                                     │
│           │ (모두 Ready면)                                                       │
│           │ "Commit"                                                            │
│           ├─────────────────────────────────────────►  QR Service               │
│           ├─────────────────────────────────────────►  Wallet Service           │
│           │                                                                     │
│           │ (하나라도 실패면)                                                    │
│           │ "Abort"                                                             │
│           ├─────────────────────────────────────────►  QR Service               │
│           ├─────────────────────────────────────────►  Wallet Service           │
│           │                                                                     │
│                                                                                 │
│  [문제점]                                                                        │
│                                                                                 │
│  1. Blocking                                                                    │
│     - Prepare 후 Commit/Abort 대기 동안 리소스 잠김                              │
│     - Coordinator 장애 시 참여자들이 무한 대기 가능                               │
│                                                                                 │
│  2. 단일 장애점 (SPOF)                                                           │
│     - Coordinator 장애 시 전체 트랜잭션 실패                                      │
│                                                                                 │
│  3. 성능                                                                        │
│     - 2번의 네트워크 라운드트립                                                  │
│     - 락 유지 시간 길음                                                          │
│                                                                                 │
│  4. 복잡한 복구                                                                  │
│     - 참여자가 Prepare 후 장애 → Commit인지 Abort인지 모름                        │
│     - 로그 기반 복구 필요                                                        │
│                                                                                 │
│  [왜 선택하지 않았는가?]                                                         │
│  - MSA에서 2PC는 안티패턴으로 간주                                               │
│  - 서비스 자율성 침해 (강결합)                                                    │
│  - 가용성 저하 (CAP 정리상 Consistency ↑ = Availability ↓)                       │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

#### C) Saga 패턴

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           Saga 패턴 상세                                          │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [개념]                                                                          │
│  - 긴 트랜잭션을 여러 로컬 트랜잭션으로 분리                                      │
│  - 각 단계 실패 시 이전 단계들을 보상 트랜잭션으로 되돌림                          │
│                                                                                 │
│  [Saga 종류]                                                                     │
│                                                                                 │
│  1. Choreography (이벤트 기반)                                                   │
│     ┌─────────────────────────────────────────────────────────────────────┐     │
│     │                                                                     │     │
│     │  QR Service ──(PaymentCreated)──► Wallet Service                    │     │
│     │                                      │                              │     │
│     │                              (잔액 차감 성공)                        │     │
│     │                                      │                              │     │
│     │  QR Service ◄──(BalanceDeducted)────┘                              │     │

│     │                                                                     │     │
│     └─────────────────────────────────────────────────────────────────────┘     │
│                                                                                 │

│     단점: 흐름 추적 어려움, 디버깅 복잡                                           │
│                                                                                 │
│  2. Orchestration (오케스트레이터 기반)                                          │
│     ┌─────────────────────────────────────────────────────────────────────┐     │
│     │                                                                     │     │
│     │          Saga Orchestrator                                          │     │
│     │               │                                                     │     │
│     │   Step 1: CreatePayment                                             │     │
│     │               │──────────────► QR Service                           │     │
│     │               │◄──────────────                                      │     │
│     │               │                                                     │     │
│     │   Step 2: DeductBalance                                             │     │
│     │               │──────────────► Wallet Service                       │     │
│     │               │◄──────────────                                      │     │
│     │               │                                                     │     │
│     │   Step 3: SendNotification                                          │     │
│     │               │──────────────► Notification Service                 │     │
│     │               │◄──────────────                                      │     │
│     │                                                                     │     │
│     │  [Step 2 실패 시]                                                   │     │
│     │   Compensate Step 1: CancelPayment                                  │     │
│     │               │──────────────► QR Service                           │     │
│     │                                                                     │     │
│     └─────────────────────────────────────────────────────────────────────┘     │
│                                                                                 │
│     장점: 흐름 명확, 관리 용이                                                    │
│     단점: Orchestrator = 단일 장애점, 결합도 증가                                 │
│                                                                                 │
│  [보상 트랜잭션 예시]                                                            │
│                                                                                 │
│  | 정방향 트랜잭션 | 보상 트랜잭션 |                                              │
│  |----------------|--------------|                                              │
│  | 잔액 차감 | 잔액 복원 |                                                       │
│  | 결제 생성 | 결제 취소 |                                                       │
│  | 알림 발송 | (보상 불가 - idempotent) |                                        │
│                                                                                 │
│  [왜 선택하지 않았는가?]                                                         │
│  - 현재 규모에서는 오버엔지니어링                                                 │
│  - 멱등성 키로 충분히 중복 방지 가능                                              │
│  - Saga는 여러 서비스에 걸친 복잡한 워크플로우에 적합                              │
│  - 메시지 큐 인프라 필요 (Kafka 등)                                               │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

## 5. Lost Update 문제

### 문제 정의

```
두 트랜잭션이 동시에 같은 데이터를 수정 → 하나의 변경이 유실됨
```

### 해결 후보 비교

| 후보 | 락 시점 | 충돌 처리 | 적합 상황 |
|------|---------|----------|----------|
| **A) 비관적 락** | 읽기 시 | 대기 | 충돌 빈번, 복구 비용 높음 |
| **B) 낙관적 락** | 쓰기 시 | 재시도 | 충돌 드묾, 복구 비용 낮음 |
| **C) 분산 락 (Redis)** | 읽기 시 | 대기 | 분산 환경 |
| **D) Atomic Update** | DB 레벨 | 경합 | 단순 증감 연산 |

### 선택: A (잔액) + B (상태)

```
[선택 이유 - 이전 문서 참조]
- 잔액 차감: 비관적 락 (금전적 손실 불가)
- Intent 상태: 낙관적 락 (충돌 드물고 재시도 가능)
```

### 각 해결책 상세 설명

#### C) 분산 락 (Redis)

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           분산 락 상세                                            │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [왜 필요한가?]                                                                  │
│  - DB 락은 단일 DB 내에서만 동작                                                 │
│  - MSA에서 서비스 간 락 필요 시 분산 락 사용                                      │
│                                                                                 │
│  [Redis 분산 락 원리]                                                            │
│                                                                                 │
│  1. SETNX (SET if Not eXists)                                                   │
│     ┌────────────────────────────────────────────────────────────────────────┐  │
│     │  SETNX lock:payment:123 "server-1" EX 30                               │  │
│     │                                                                        │  │
│     │  - 키가 없으면: 설정 + 1 반환 (락 획득!)                               │  │
│     │  - 키가 있으면: 0 반환 (락 획득 실패)                                   │  │
│     │  - EX 30: 30초 후 자동 만료 (데드락 방지)                               │  │
│     └────────────────────────────────────────────────────────────────────────┘  │
│                                                                                 │
│  2. Redlock 알고리즘 (Redis Cluster용)                                           │
│     ┌────────────────────────────────────────────────────────────────────────┐  │
│     │                                                                        │  │
│     │  5개의 독립적인 Redis 노드                                             │  │
│     │  ┌───┐  ┌───┐  ┌───┐  ┌───┐  ┌───┐                                    │  │
│     │  │ R1│  │ R2│  │ R3│  │ R4│  │ R5│                                    │  │
│     │  └───┘  └───┘  └───┘  └───┘  └───┘                                    │  │
│     │                                                                        │  │
│     │  락 획득 조건: 과반수(3개+) 노드에서 락 획득 성공                       │  │
│     │  + 총 소요 시간 < 락 TTL                                               │  │
│     │                                                                        │  │
│     └────────────────────────────────────────────────────────────────────────┘  │
│                                                                                 │
│  [Redisson 라이브러리 사용 예시]                                                 │
│  ┌────────────────────────────────────────────────────────────────────────┐     │
│  │  @Autowired                                                            │     │
│  │  private RedissonClient redisson;                                      │     │
│  │                                                                        │     │
│  │  public void processPayment(Long paymentId) {                          │     │
│  │      RLock lock = redisson.getLock("payment:" + paymentId);            │     │
│  │                                                                        │     │
│  │      try {                                                             │     │
│  │          // 5초 대기, 획득 후 10초 유지                                 │     │
│  │          boolean acquired = lock.tryLock(5, 10, TimeUnit.SECONDS);     │     │
│  │                                                                        │     │
│  │          if (!acquired) {                                              │     │
│  │              throw new LockAcquisitionException("락 획득 실패");        │     │
│  │          }                                                             │     │
│  │                                                                        │     │
│  │          // 비즈니스 로직                                               │     │
│  │          doPayment(paymentId);                                         │     │
│  │                                                                        │     │
│  │      } finally {                                                       │     │
│  │          if (lock.isHeldByCurrentThread()) {                           │     │
│  │              lock.unlock();                                            │     │
│  │          }                                                             │     │
│  │      }                                                                 │     │
│  │  }                                                                     │     │
│  └────────────────────────────────────────────────────────────────────────┘     │
│                                                                                 │
│  [주의사항]                                                                      │
│                                                                                 │
│  1. TTL 설정                                                                    │
│     - 너무 짧으면: 작업 완료 전 락 해제 → 동시성 문제                            │
│     - 너무 길면: 장애 시 오래 기다림                                             │
│     - 해결: Watchdog (Redisson) - 작업 중이면 자동 연장                          │
│                                                                                 │
│  2. 락 해제 시 검증                                                              │
│     - 내가 획득한 락만 해제해야 함                                               │
│     - Lua 스크립트로 원자적 검증 + 삭제                                          │
│     ┌────────────────────────────────────────────────────────────────────────┐  │
│     │  if redis.call("get", KEYS[1]) == ARGV[1] then                        │  │
│     │      return redis.call("del", KEYS[1])                                │  │
│     │  else                                                                 │  │
│     │      return 0                                                         │  │
│     │  end                                                                  │  │
│     └────────────────────────────────────────────────────────────────────────┘  │
│                                                                                 │
│  [현재 프로젝트에서 사용하지 않는 이유]                                           │
│  - 멱등성 키 + DB 비관적 락으로 충분                                             │
│  - 추가 인프라 (Redis Cluster) 복잡도                                            │
│  - 현재 규모에서는 오버엔지니어링                                                 │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
```

#### D) Atomic Update

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│                           Atomic Update 상세                                      │
├─────────────────────────────────────────────────────────────────────────────────┤
│                                                                                 │
│  [개념]                                                                          │
│  - 읽기 + 수정 + 쓰기를 하나의 SQL로 처리                                         │
│  - DB가 원자성 보장                                                              │
│                                                                                 │
│  [일반적인 방식 (문제 있음)]                                                      │
│  ┌────────────────────────────────────────────────────────────────────────┐     │
│  │  // Java 코드                                                          │     │
│  │  Balance balance = repository.findById(id);  // SELECT                 │     │
│  │  balance.setAmount(balance.getAmount() - 1000);  // 애플리케이션에서 계산│     │
│  │  repository.save(balance);  // UPDATE                                  │     │
│  │                                                                        │     │
│  │  // 동시 실행 시 Lost Update 발생 가능                                  │     │
│  └────────────────────────────────────────────────────────────────────────┘     │
│                                                                                 │
│  [Atomic Update 방식]                                                           │
│  ┌────────────────────────────────────────────────────────────────────────┐     │
│  │  @Modifying                                                            │     │
│  │  @Query(value = """                                                    │     │
│  │      UPDATE wallet_store_balances                                      │     │
│  │         SET balance = balance - :amount                                │     │
│  │       WHERE wallet_id = :walletId                                      │     │
│  │         AND store_id = :storeId                                        │     │
│  │         AND balance >= :amount                                         │     │
│  │  """, nativeQuery = true)                                              │     │
│  │  int decrementIfEnough(@Param("walletId") Long walletId,               │     │
│  │                        @Param("storeId") Long storeId,                 │     │
│  │                        @Param("amount") Long amount);                  │     │
│  │                                                                        │     │
│  │  // 반환값: 1 = 성공, 0 = 실패 (잔액 부족 또는 경합)                    │     │
│  └────────────────────────────────────────────────────────────────────────┘     │
│                                                                                 │
│  [장점]                                                                         │
│  - 락 없이도 안전 (DB가 보장)                                                    │
│  - 성능 좋음 (단일 SQL)                                                          │
│  - 조건부 업데이트 가능 (balance >= amount)                                       │
│                                                                                 │
│  [단점]                                                                         │
│  - 단순 연산만 가능 (복잡한 비즈니스 로직 불가)                                    │
│  - 업데이트 전 값을 모름 (SELECT 별도 필요)                                       │
│  - ORM의 변경 감지(Dirty Checking) 활용 불가                                      │
│                                                                                 │
│  [Compare-And-Swap (CAS) 패턴]                                                   │
│  ┌────────────────────────────────────────────────────────────────────────┐     │
│  │  UPDATE wallet_store_balances                                          │     │
│  │     SET balance = :newBalance,                                         │     │
│  │         version = version + 1                                          │     │
│  │   WHERE wallet_id = :walletId                                          │     │
│  │     AND balance = :expectedBalance   -- 기대값 확인                    │     │
│  │     AND version = :expectedVersion   -- 버전 확인                      │     │
│  │                                                                        │     │
│  │  // affected rows = 0 이면 다른 트랜잭션이 먼저 수정함                  │     │
│  │  // → 재시도 또는 오류 처리                                             │     │
│  └────────────────────────────────────────────────────────────────────────┘     │
│                                                                                 │
│  [현재 프로젝트 적용]                                                            │
│  - WalletStoreBalanceRepository.decrementIfEnough() 에서 사용                    │
│  - 비관적 락과 함께 사용 (이중 안전장치)                                          │
│                                                                                 │
└─────────────────────────────────────────────────────────────────────────────────┘
