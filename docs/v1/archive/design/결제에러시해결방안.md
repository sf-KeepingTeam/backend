# QR 결제 타임아웃 복구 프로세스 설계서

---

## 0. 빠른 이해를 위한 개요

> 이 섹션은 전체 복구 프로세스를 쉽게 이해할 수 있도록 작성되었습니다.

### 0.1 한 줄 요약

```
결제 요청 → 타임아웃 발생 → "결과 모름" 상태로 저장 → 나중에 확인해서 환불
```

---

### 0.2 연결 성공/실패를 어떻게 판단하는가?

#### Java의 RestTemplate이 알아서 판단합니다

```java
try {
    // 모놀리스에 결제 요청
    FundsResponse response = walletClient.capture(request, idempotencyKey);

    // 여기 도달 = 성공! (응답 받음)
    return FundsResult.success(response);

} catch (ResourceAccessException e) {
    // 여기 도달 = 타임아웃 또는 연결 실패!
    // - SocketTimeoutException: 응답이 3초 안에 안 옴
    // - ConnectException: 서버에 연결 자체가 안 됨

    return FundsResult.uncertain();
}
```

```
┌─────────────────────────────────────────────────────────────────────┐
│                    연결 상태 판단 기준                               │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  성공 (try 블록 통과):                                              │
│  - HTTP 200 응답 받음                                               │
│  - 모놀리스가 "결제 완료"라고 알려줌                                │
│                                                                      │
│  실패 - 명확한 에러 (HttpClientErrorException):                     │
│  - HTTP 400: 잘못된 요청                                            │
│  - HTTP 401: PIN 오류                                               │
│  - HTTP 402: 잔액 부족                                              │
│  → 이건 "실패"가 확실함 → FAILED 상태                               │
│                                                                      │
│  실패 - 결과 모름 (ResourceAccessException):                        │
│  - 타임아웃: 3초 안에 응답 안 옴                                    │
│  - 연결 실패: 모놀리스 서버가 안 떠있음                             │
│  → 모놀리스에서 처리됐는지 안 됐는지 모름 → UNCERTAIN 상태          │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

### 0.3 플래그(깃발)가 뭐고 왜 쓰는가?

#### 플래그 = "상태를 기억하는 변수"

```
일상 예시:

집에서 "우편함 확인해야 해?"라는 질문에 대한 답:

- 우편 왔다는 알림 받음 → "확인해야 해 = true"
- 우편함 확인 완료 → "확인해야 해 = false"
- 다음에 또 알림 받음 → "확인해야 해 = true"

매번 우편함까지 가서 확인하는 게 아니라,
"확인해야 해" 여부만 보고 갈지 말지 결정!
```

#### 우리 코드에서의 플래그

```
┌─────────────────────────────────────────────────────────────────────┐
│                         2개의 플래그                                 │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  1. hasRecoveryTarget = "복구할 게 있어?"                           │
│     ┌─────────────────────────────────────────────────────────┐     │
│     │ false (기본값)                                          │     │
│     │   → 복구할 게 없음                                      │     │
│     │   → DB 조회 안 함 (부하 절약)                           │     │
│     │                                                         │     │
│     │ true                                                    │     │
│     │   → 복구할 게 있음                                      │     │
│     │   → DB 조회해서 처리해야 함                             │     │
│     └─────────────────────────────────────────────────────────┘     │
│                                                                      │
│  2. isRecovering = "지금 복구 중이야?"                              │
│     ┌─────────────────────────────────────────────────────────┐     │
│     │ false (기본값)                                          │     │
│     │   → 복구 작업 안 하는 중                                │     │
│     │   → 새 복구 작업 시작 가능                              │     │
│     │                                                         │     │
│     │ true                                                    │     │
│     │   → 복구 작업 하는 중                                   │     │
│     │   → 다른 복구 작업 시작하면 안 됨 (중복 방지)           │     │
│     └─────────────────────────────────────────────────────────┘     │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

### 0.4 전체 흐름 (스토리로 이해하기)

#### 등장인물
- **손님**: 결제하는 사람
- **QR 서버**: 결제 요청을 받는 서버
- **모놀리스**: 실제로 돈을 차감하는 서버
- **복구 담당자**: 10초마다 깨어나서 문제 있는지 확인하는 역할 (@Scheduled)

#### 스토리

```
📖 1장: 정상 결제

손님: "5000원 결제할게요"
QR 서버: "알겠습니다. 모놀리스야, 5000원 차감해줘"
모놀리스: "네, 차감했습니다. 완료!"
QR 서버: "손님, 결제 완료되었습니다!"

→ hasRecoveryTarget = false (복구할 거 없음)
→ 끝!
```

```
📖 2장: 타임아웃 발생

손님: "5000원 결제할게요"
QR 서버: "알겠습니다. 모놀리스야, 5000원 차감해줘"
모놀리스: (열심히 처리 중... 근데 응답이 늦음)
QR 서버: "어? 3초가 지났는데 응답이 없네? 타임아웃!"

QR 서버 내부:
┌─────────────────────────────────────────────────────────────────────┐
│ 1. catch (ResourceAccessException e)  ← 타임아웃 예외 발생!        │
│                                                                      │
│ 2. 이 결제 상태를 UNCERTAIN(결과 모름)으로 저장                     │
│    intent.setStatus(PaymentStatus.UNCERTAIN);                       │
│    intentRepository.save(intent);                                   │
│                                                                      │
│ 3. 깃발 올림: "복구할 거 생겼다!"                                   │
│    hasRecoveryTarget = true;                                        │
│                                                                      │
│ 4. 손님에게 응답                                                    │
│    "결제 처리 중 오류가 발생했습니다. 잠시 후 확인해주세요."        │
└─────────────────────────────────────────────────────────────────────┘

→ 손님은 "결제 실패"로 인식
→ 하지만 실제로 돈이 빠졌을 수도 있음!
```

```
📖 3장: 복구 담당자 등장

(10초 후, 복구 담당자가 깨어남)

복구 담당자: "음... 복구할 거 있나?"
             hasRecoveryTarget 확인 → true!
             "오, 있네! DB 조회해볼게"

┌─────────────────────────────────────────────────────────────────────┐
│ DB 조회: UNCERTAIN 상태인 결제 찾기                                 │
│                                                                      │
│ 결과: Intent #1 발견 (손님의 5000원 결제)                           │
└─────────────────────────────────────────────────────────────────────┘

복구 담당자: "모놀리스야, 이 결제 실제로 됐어?"
             GET /internal/payments/check?idempotencyKey=xxx

모놀리스: "응, 5000원 차감됐어. 거래 ID는 123이야"
         { "exists": true, "transactionId": 123, "amount": 5000 }

복구 담당자: "아, 돈은 빠졌구나. 근데 손님은 실패로 알고 있으니 환불해줘야지"
             POST /internal/wallets/{walletId}/refund

모놀리스: "환불 완료!"

복구 담당자: "좋아, 이 결제 상태를 ROLLED_BACK(환불됨)으로 바꿀게"
             intent.setStatus(PaymentStatus.ROLLED_BACK);

복구 담당자: "다른 복구 대상 있나? 없네. 깃발 내릴게"
             hasRecoveryTarget = false;

→ 손님 입장: 결제 실패 → 돈 안 빠짐 (환불됨) → 정상!
```

```
📖 4장: 모놀리스가 처리 못 한 경우

(위와 같은 상황, 하지만 모놀리스가 처리 전에 다운됐다면)

복구 담당자: "모놀리스야, 이 결제 실제로 됐어?"
             GET /internal/payments/check?idempotencyKey=xxx

모놀리스: "아니, 그런 거래 없어"
         { "exists": false }

복구 담당자: "아, 결제 자체가 안 된 거구나. 환불할 것도 없네"
             intent.setStatus(PaymentStatus.EXPIRED);

→ 손님 입장: 결제 실패 → 실제로도 안 됨 → 정상!
```

### 0.5 복구 주기는 어떻게 조정되는가?

```
┌─────────────────────────────────────────────────────────────────────┐
│                      복구 주기 결정 로직                             │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  @Scheduled(fixedRate = 10000)  ← 10초마다 이 메서드 실행           │
│  public void recoverPeriodically() {                                │
│                                                                      │
│      // 1단계: 복구 대상 있어?                                      │
│      if (!hasRecoveryTarget) {                                      │
│          return;  // 없으면 바로 끝 (나노초)                        │
│      }                                                               │
│                                                                      │
│      // 2단계: 지금 피크 시간이야?                                  │
│      if (피크 시간이면) {                                           │
│          interval = 10초;   // 10초마다 실제 복구                   │
│      } else {                                                       │
│          interval = 60초;   // 60초마다 실제 복구                   │
│      }                                                               │
│                                                                      │
│      // 3단계: 마지막 복구 후 interval 지났어?                      │
│      if (지금 - 마지막실행시간 < interval) {                        │
│          return;  // 아직 때가 안 됐음                              │
│      }                                                               │
│                                                                      │
│      // 4단계: 실제 복구 실행!                                      │
│      ...                                                             │
│  }                                                                   │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

```
예시 (피크 시간 = 11시~14시):

시간        실제 동작
─────────────────────────────────────────────────────
10:00:00    10초 체크 → 피크 아님 → interval=60초 → 실행
10:00:10    10초 체크 → 60초 안 지남 → 스킵
10:00:20    10초 체크 → 60초 안 지남 → 스킵
...
10:01:00    10초 체크 → 60초 지남! → 실행
...
11:00:00    10초 체크 → 피크임 → interval=10초 → 실행
11:00:10    10초 체크 → 10초 지남! → 실행
11:00:20    10초 체크 → 10초 지남! → 실행
```

### 0.6 중복 실행 방지는 어떻게?

```
문제 상황:

복구 작업이 15초 걸리면?

T=0초:   복구 시작 (100개 처리 중...)
T=10초:  스케줄러가 또 실행됨!
         → 같은 100개를 또 처리하면 안 됨!
```

```
해결: isRecovering 플래그

┌─────────────────────────────────────────────────────────────────────┐
│                                                                      │
│  T=0초: 복구 시작                                                   │
│         isRecovering = false → true로 변경 (문 잠금)                │
│         100개 처리 시작...                                          │
│                                                                      │
│  T=10초: 스케줄러 실행                                              │
│          isRecovering 확인 → true네?                                │
│          "아, 누가 이미 하고 있구나. 나는 빠질게~"                  │
│          return; (바로 종료)                                        │
│                                                                      │
│  T=15초: 복구 완료                                                  │
│          isRecovering = false (문 열기)                             │
│                                                                      │
│  T=20초: 스케줄러 실행                                              │
│          isRecovering 확인 → false네?                               │
│          "좋아, 내가 할게"                                          │
│          isRecovering = true (문 잠금)                              │
│          ...                                                         │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

### 0.7 서버 재시작하면 어떻게 되는가?

```
문제:

서버가 다운됐다가 다시 켜지면
메모리에 있던 플래그(hasRecoveryTarget, isRecovering)가
전부 false로 초기화됨!

근데 DB에는 UNCERTAIN 상태인 결제가 남아있을 수 있음!
```

```
해결: @PostConstruct (서버 시작 시 자동 실행)

┌─────────────────────────────────────────────────────────────────────┐
│                                                                      │
│  서버 시작                                                          │
│      │                                                               │
│      ▼                                                               │
│  @PostConstruct 실행                                                │
│      │                                                               │
│      ├─ DB 조회: UNCERTAIN 상태인 거 있어?                          │
│      │                                                               │
│      ├─ 있으면 → hasRecoveryTarget = true                           │
│      │          복구 작업 시작                                      │
│      │                                                               │
│      └─ 없으면 → 정상 시작                                          │
│                                                                      │
│  → 서버가 다운됐다 켜져도 복구 대상 놓치지 않음!                    │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

### 0.9 핵심 정리

```
┌─────────────────────────────────────────────────────────────────────┐
│                         핵심 포인트                                  │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  Q: 연결 끊김을 어떻게 알아?                                        │
│  A: Java가 예외(ResourceAccessException)를 던져줌                   │
│                                                                      │
│  Q: 플래그는 왜 씀?                                                 │
│  A: 매번 DB 조회하면 부하 → 플래그로 "할 일 있는지" 먼저 확인      │
│                                                                      │
│  Q: 복구 주기 10초인데 부하 없어?                                   │
│  A: 플래그가 false면 즉시 리턴 (나노초) → 부하 없음                │
│                                                                      │
│  Q: 중복 복구는?                                                    │
│  A: isRecovering 플래그로 "지금 하는 중" 표시 → 다른 건 스킵       │
│                                                                      │
│  Q: 서버 재시작하면?                                                │
│  A: @PostConstruct가 시작할 때 DB 확인 → 놓치지 않음               │
│                                                                      │
│  Q: 진짜 환불해야 하는지 어떻게 알아?                               │
│  A: 모놀리스에 "이 결제 됐어?" 물어봄 → 됐으면 환불, 아니면 무시   │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

## 1. 문제 정의

### 1.1 현재 상황

QR 결제 시스템은 **QR 서버**와 **모놀리스 서버**가 분리된 MSA 구조로 운영됩니다.

```
┌─────────────────┐         HTTP          ┌─────────────────┐
│    QR Server    │ ──────────────────▶  │    Monolith     │
│    (8082)       │                       │    (8080)       │
├─────────────────┤                       ├─────────────────┤
│  - qr-redis     │                       │  - keeping-redis│
│  - qr-mysql     │                       │  - keeping-mysql│
│    (payment_    │                       │    (ssafy_      │
│     service)    │                       │     fintech_db) │
└─────────────────┘                       └─────────────────┘
```

### 1.2 핵심 문제

**타임아웃 시 데이터 불일치 문제**

```
시나리오:
1. QR 서버 → 모놀리스: "5000원 결제해줘" (HTTP 요청)
2. 모놀리스: 잔액 차감 성공, Transaction 생성 완료
3. 모놀리스 → QR 서버: 응답 전송 중... (네트워크 지연 또는 서버 다운)
4. QR 서버: 타임아웃 발생! (3초 초과)
5. 결과:
   - 모놀리스 DB: 잔액 차감됨, 거래 기록 있음
   - QR 서버 DB: 결제 실패로 기록
   - 사용자: "결제 실패" 메시지 수신
   - 실제: 돈은 빠져나감 💥
```

### 1.3 해결 목표

| 목표 | 설명 |
|------|------|
| **데이터 정합성** | 모든 에러 상황에서 최종적으로 일관된 상태 보장 |
| **추가 인프라 없음** | Kafka, 공유 Redis 등 추가 인프라 불필요 |
| **자동 복구** | 수동 개입 없이 자동으로 복구 |
| **사용자 경험** | 명확한 상태 안내 및 빠른 복구 |

## 3. 에러 시나리오 분석

### 3.1 시나리오 A: QR 서버 다운

**발생 시점**: QR 서버가 모놀리스에 요청 후, 응답 수신 전 크래시

```
┌─────────────────────────────────────────────────────────────────────┐
│                    시나리오 A: QR 서버 다운                          │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  타임라인:                                                           │
│  ─────────────────────────────────────────────────────────────────  │
│  T1: QR서버 → 모놀리스 HTTP 요청 전송                               │
│  T2: 모놀리스 잔액 차감 성공                                         │
│  T3: 모놀리스 Transaction 생성                                       │
│  T4: 모놀리스 → QR서버 응답 전송 시도                               │
│  T5: ⚡ QR 서버 다운 (응답 수신 불가)                               │
│                                                                      │
│  결과 상태:                                                          │
│  ┌─────────────────────┬──────────────────────────────────────────┐ │
│  │ 저장소              │ 상태                                     │ │
│  ├─────────────────────┼──────────────────────────────────────────┤ │
│  │ QR MySQL            │ PaymentIntent = PENDING (변경 못 함)     │ │
│  │ Monolith MySQL      │ Transaction 존재, 잔액 차감됨            │ │
│  │ 사용자 인지         │ 결제 실패 (응답 없음)                    │ │
│  │ 실제 상태           │ 결제 성공 (돈 빠져나감)                  │ │
│  └─────────────────────┴──────────────────────────────────────────┘ │
│                                                                      │
│  특이점:                                                             │
│  - QR 서버가 다운되어 상태를 UNCERTAIN으로 변경하지 못함            │
│  - PENDING 상태 + 만료된 PaymentIntent로 식별 가능                  │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

### 3.2 시나리오 B: 모놀리스 서버 다운

**발생 시점**: QR 서버 요청 중 모놀리스가 다운되어 처리 불가

```
┌─────────────────────────────────────────────────────────────────────┐
│                   시나리오 B: 모놀리스 다운                          │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  타임라인:                                                           │
│  ─────────────────────────────────────────────────────────────────  │
│  T1: QR서버 → 모놀리스 HTTP 요청 전송                               │
│  T2: ⚡ 모놀리스 다운 (요청 처리 불가)                              │
│  T3: QR서버 연결 실패 또는 5xx 응답 수신                            │
│  T4: QR서버 예외 처리 (ResourceAccessException)                     │
│  T5: QR서버 PaymentIntent 상태 → UNCERTAIN                         │
│                                                                      │
│  결과 상태:                                                          │
│  ┌─────────────────────┬──────────────────────────────────────────┐ │
│  │ 저장소              │ 상태                                     │ │
│  ├─────────────────────┼──────────────────────────────────────────┤ │
│  │ QR MySQL            │ PaymentIntent = UNCERTAIN                │ │
│  │ Monolith MySQL      │ Transaction 없음 (처리 안 됨)            │ │
│  │ 사용자 인지         │ 결제 실패                                │ │
│  │ 실제 상태           │ 결제 실패 (돈 안 빠져나감)               │ │
│  └─────────────────────┴──────────────────────────────────────────┘ │
│                                                                      │
│  특이점:                                                             │
│  - 데이터 불일치 없음 (둘 다 실패 상태)                             │
│  - 복구 시 모놀리스에 확인하면 "없음" 응답 → 환불 불필요            │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

### 3.3 시나리오 C: 네트워크 타임아웃

**발생 시점**: 모놀리스 처리 완료 후, 응답 전송 중 네트워크 지연으로 타임아웃

```
┌─────────────────────────────────────────────────────────────────────┐
│                   시나리오 C: 네트워크 타임아웃                      │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  타임라인:                                                           │
│  ─────────────────────────────────────────────────────────────────  │
│  T1: QR서버 → 모놀리스 HTTP 요청 전송 (timeout: 3초)                │
│  T2: 모놀리스 처리 시작                                              │
│  T3: 모놀리스 잔액 차감 성공 (2.5초 소요)                           │
│  T4: 모놀리스 Transaction 생성                                       │
│  T5: 모놀리스 → QR서버 응답 전송 시작... (네트워크 지연)            │
│  T6: ⚡ QR서버 타임아웃 (3초 초과)                                  │
│  T7: QR서버 예외 처리 (SocketTimeoutException)                      │
│  T8: QR서버 PaymentIntent 상태 → UNCERTAIN                         │
│                                                                      │
│  결과 상태:                                                          │
│  ┌─────────────────────┬──────────────────────────────────────────┐ │
│  │ 저장소              │ 상태                                     │ │
│  ├─────────────────────┼──────────────────────────────────────────┤ │
│  │ QR MySQL            │ PaymentIntent = UNCERTAIN                │ │
│  │ Monolith MySQL      │ Transaction 존재, 잔액 차감됨            │ │
│  │ 사용자 인지         │ 결제 실패 또는 "확인 중"                 │ │
│  │ 실제 상태           │ 결제 성공 (돈 빠져나감)                  │ │
│  └─────────────────────┴──────────────────────────────────────────┘ │
│                                                                      │
│  특이점:                                                             │
│  - 가장 빈번하게 발생하는 케이스                                    │
│  - QR서버가 UNCERTAIN 상태로 변경 가능                              │
│  - 복구 프로세스에서 환불 처리 필요                                 │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

### 3.4 시나리오 비교 요약

| 시나리오 | QR MySQL 상태 | Monolith 거래 | 환불 필요 | 복구 방법 |
|----------|---------------|---------------|-----------|-----------|
| A. QR 다운 | PENDING (만료) | 존재 | **필요** | @PostConstruct |
| B. 모놀리스 다운 | UNCERTAIN | 없음 | 불필요 | @Scheduled |
| C. 네트워크 지연 | UNCERTAIN | 존재 | **필요** | @Scheduled |

**핵심 인사이트**: 모든 시나리오를 **하나의 복구 로직**으로 처리 가능
- 모놀리스에 확인 → 거래 있으면 환불, 없으면 무시

## 4. 해결 방안: 복구 프로세스

### 4.1 PaymentStatus 확장

```java
public enum PaymentStatus {
    PENDING,       // 결제 대기 중 (Intent 생성 직후)
    APPROVED,      // 승인 완료 (정상 결제)
    FAILED,        // 명확한 실패 (잔액 부족, PIN 오류 등)
    UNCERTAIN,     // 타임아웃 발생 (결과 불명) ← 추가
    ROLLED_BACK,   // 보상 트랜잭션 완료 ← 추가
    EXPIRED        // 만료됨 (3분 초과)
}
```

### 4.2 3단계 안전망 구조

```
┌─────────────────────────────────────────────────────────────────────┐
│                          3단계 안전망                                │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  ┌─────────────────────────────────────────────────────────────┐    │
│  │ 1️⃣ 즉시 마킹 (실시간)                                        │    │
│  │                                                              │    │
│  │    타임아웃 발생 즉시:                                       │    │
│  │    - intent.setStatus(UNCERTAIN)                             │    │
│  │    - recoveryService.markRecoveryNeeded()                    │    │
│  │    - hasRecoveryTarget = true                                │    │
│  │                                                              │    │
│  │    → 다음 @Scheduled 사이클에서 복구                         │    │
│  └─────────────────────────────────────────────────────────────┘    │
│                              ↓                                       │
│  ┌─────────────────────────────────────────────────────────────┐    │
│  │ 2️⃣ 주기적 복구 (1분마다)                                     │    │
│  │                                                              │    │
│  │    @Scheduled(fixedRate = 60000)                             │    │
│  │    if (hasRecoveryTarget.get()) {                            │    │
│  │        List<PaymentIntent> targets = findRecoveryTargets();  │    │
│  │        for (PaymentIntent intent : targets) {                │    │
│  │            recoverSinglePayment(intent);                     │    │
│  │        }                                                     │    │
│  │        if (targets.isEmpty()) {                              │    │
│  │            hasRecoveryTarget.set(false);                     │    │
│  │        }                                                     │    │
│  │    }                                                         │    │
│  │                                                              │    │
│  │    → 플래그가 false면 DB 조회 안 함 (부하 최소화)            │    │
│  └─────────────────────────────────────────────────────────────┘    │
│                              ↓                                       │
│  ┌─────────────────────────────────────────────────────────────┐    │
│  │ 3️⃣ 서버 시작 복구 (재시작 시)                                │    │
│  │                                                              │    │
│  │    @PostConstruct                                            │    │
│  │    - 무조건 한 번 DB 조회 (메모리 플래그 손실 복구)          │    │
│  │    - UNCERTAIN 상태 복구                                     │    │
│  │    - PENDING + 만료된 것도 함께 복구 (시나리오 A 대응)       │    │
│  │                                                              │    │
│  │    → 서버 다운 후 재시작해도 복구 대상 놓치지 않음           │    │
│  └─────────────────────────────────────────────────────────────┘    │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

### 4.3 복구 주기 설정

#### 4.3.1 기본 주기 vs 피크 시간대 주기

복구 주기는 시간대에 따라 다르게 설정할 수 있습니다.

```
┌─────────────────────────────────────────────────────────────────────┐
│                      복구 주기 설정 가이드                           │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  일반 시간대:                                                        │
│  - 주기: 60초                                                        │
│  - 이유: 결제 빈도 낮음, 부하 최소화                                │
│                                                                      │
│  피크 시간대 (11:00 ~ 14:00, 17:00 ~ 19:00):                        │
│  - 주기: 10초 ~ 20초                                                │
│  - 이유: 결제 빈도 높음, 빠른 복구 필요                             │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

#### 4.3.2 10초 주기도 부하 없는 이유

```java
@Scheduled(fixedRate = 10000) // 10초마다
public void recoverPeriodically() {
    // ⚡ 이 체크는 메모리 연산 (나노초 수준)
    if (!hasRecoveryTarget.get()) {
        return;  // DB 조회 안 함!
    }

    // 플래그가 true일 때만 DB 조회
    // ...
}
```

| 상황 | 10초마다 발생하는 일 | 부하 |
|------|---------------------|------|
| 복구 대상 **없음** (99.9%) | `AtomicBoolean.get()` 한 번 | **0에 가까움** |
| 복구 대상 **있음** | DB 조회 + 모놀리스 API 호출 | 있지만 필요한 작업 |

#### 4.3.3 시간대별 주기 조정 코드

```java
@Service
public class PaymentRecoveryService {

    // 피크 시간대 설정
    private static final int LUNCH_START = 11;
    private static final int LUNCH_END = 14;
    private static final int DINNER_START = 17;
    private static final int DINNER_END = 19;

    // 주기 설정
    private static final long PEAK_INTERVAL_MS = 10_000;    // 피크: 10초
    private static final long NORMAL_INTERVAL_MS = 60_000;  // 일반: 60초

    private long lastExecutionTime = 0;

    /**
     * 10초마다 실행되지만, 실제 복구는 시간대에 따라 다른 주기로 수행
     */
    @Scheduled(fixedRate = 10000)
    public void recoverPeriodically() {
        if (!hasRecoveryTarget.get()) {
            return;
        }

        // 시간대에 따른 주기 결정
        long interval = isPeakTime() ? PEAK_INTERVAL_MS : NORMAL_INTERVAL_MS;
        long now = System.currentTimeMillis();

        // 마지막 실행 후 interval 이상 지났는지 확인
        if (now - lastExecutionTime < interval) {
            return;
        }

        lastExecutionTime = now;
        // 복구 로직 실행...
    }

    private boolean isPeakTime() {
        int hour = LocalTime.now().getHour();
        return (hour >= LUNCH_START && hour < LUNCH_END)
            || (hour >= DINNER_START && hour < DINNER_END);
    }
}
```

### 4.4 동시성 제어 (메모리 락)

#### 4.4.1 왜 락이 필요한가?

@Scheduled 메서드가 10초마다 실행되는데, 복구 작업이 10초 이상 걸리면 중복 실행될 수 있습니다.

```
문제 상황 (락 없을 때):

T=0초:  스케줄러 실행 → 100개 복구 시작 (25초 소요 예상)
T=10초: 스케줄러 실행 → 또 100개 복구 시작? 💥 중복!
T=20초: 스케줄러 실행 → 또 100개 복구 시작? 💥 중복!
```

#### 4.4.2 일반 if문의 문제점

```java
// ❌ 이렇게 하면 문제 발생 (멀티스레드 환경에서)
private boolean isRecovering = false;

public void recoverPeriodically() {
    if (isRecovering == false) {   // 1. 체크
        isRecovering = true;        // 2. 변경
        // 복구 작업...
    }
}
```

```
두 스레드가 거의 동시에 실행되면:

스레드 A                              스레드 B
──────────────────────────────────────────────────────────
if (isRecovering == false) ✅
                                      if (isRecovering == false) ✅
                                      (아직 A가 true로 안 바꿈!)
isRecovering = true
                                      isRecovering = true
복구 시작...                          복구 시작... 💥 둘 다 들어감!
```

#### 4.4.3 AtomicBoolean.compareAndSet() 해결

```java
// ✅ 이렇게 하면 안전
private final AtomicBoolean isRecovering = new AtomicBoolean(false);

public void recoverPeriodically() {
    // "체크 + 변경"을 한 번에 (원자적으로) 실행
    if (!isRecovering.compareAndSet(false, true)) {
        return;  // 다른 스레드가 이미 처리 중
    }

    try {
        // 복구 작업...
    } finally {
        isRecovering.set(false);  // 완료 후 해제
    }
}
```

```
compareAndSet(false, true)의 동작:

┌─────────────────────────────────────────────────────────────────────┐
│  1. 현재 값이 false인지 확인                                        │
│  2. false면 → true로 변경하고 → true 반환 (성공)                   │
│  3. true면 → 아무것도 안 하고 → false 반환 (실패)                  │
│                                                                      │
│  ⚡ 이 세 단계가 CPU 레벨에서 "한 번에" 실행됨!                     │
│     중간에 다른 스레드가 끼어들 수 없음                             │
└─────────────────────────────────────────────────────────────────────┘
```

#### 4.4.4 동시 실행 시 동작

```
스레드 A                              스레드 B
──────────────────────────────────────────────────────────
compareAndSet(false, true)
  └─ 현재값: false
  └─ false→true 변경
  └─ return true ✅
                                      compareAndSet(false, true)
                                        └─ 현재값: true (A가 바꿈!)
                                        └─ 변경 안 함
                                        └─ return false ❌

if (true) { 복구 시작 }               if (false) { 스킵 }
```

#### 4.4.5 두 플래그의 역할 분리

```
┌─────────────────────────────────────────────────────────────────────┐
│                         2개의 플래그                                 │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  1. hasRecoveryTarget (복구 대상 있어?)                             │
│     - 타임아웃 발생 시: markRecoveryNeeded() → true                 │
│     - 복구 완료 시: set(false)                                      │
│     - 용도: DB 조회 여부 결정                                       │
│                                                                      │
│  2. isRecovering (지금 복구 중이야?)                                │
│     - 스케줄러 시작 시: compareAndSet(false, true)                  │
│     - 스케줄러 종료 시: finally에서 set(false)                      │
│     - 용도: 중복 실행 방지                                          │
│     - ⚠️ 외부에서 절대 건드리지 않음!                               │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

```
시간    isRecovering    hasRecoveryTarget    무슨 일이?
────────────────────────────────────────────────────────────────
T=0초   false→true      true                 스케줄러 시작, 100개 처리
T=10초  true            true                 스케줄러 #2: true라서 스킵
T=11초  true ⬅️안바뀜!  true                 새 타임아웃! markRecoveryNeeded()
                                             └─ isRecovering은 안 건드림!
T=20초  true            true                 스케줄러 #3: true라서 스킵
T=25초  true→false      true                 스케줄러 #1 완료, finally 실행
T=30초  false→true      true                 스케줄러 #4: 획득 성공!
T=35초  true→false      true→false           모두 처리 완료
```

#### 4.5.1 HTTP 스레드 풀 vs @Scheduled 스레드 풀

```
┌─────────────────────────────────────────────────────────────────────┐
│                         QR 서버                                      │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  1. HTTP 요청 처리 스레드 (Tomcat)                                  │
│     ┌─────────────────────────────────────────┐                     │
│     │ 기본 200개 스레드                       │                     │
│     │                                         │                     │
│     │ 손님A 결제 요청 → 스레드 #1             │                     │
│     │ 손님B 결제 요청 → 스레드 #2             │                     │
│     │ 손님C 결제 요청 → 스레드 #3             │                     │
│     │ ...                                     │                     │
│     └─────────────────────────────────────────┘                     │
│                                                                      │
│  2. @Scheduled 스레드 (TaskScheduler)         ← 완전 별개!          │
│     ┌─────────────────────────────────────────┐                     │
│     │ 기본 1개 스레드 (단일 스레드)           │                     │
│     │                                         │                     │

│     └─────────────────────────────────────────┘                     │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

#### 4.5.2 데이터 정합성

```
손님 5명이 동시에 결제해도 정합성 보장:

스레드 #1: 손님A 결제 처리  ─┐
스레드 #2: 손님B 결제 처리  ─┼─→ DB 트랜잭션이 정합성 보장
스레드 #3: 손님C 결제 처리  ─┤
스레드 #4: 손님D 결제 처리  ─┤
스레드 #5: 손님E 결제 처리  ─┘

→ HTTP는 멀티스레드여도 DB가 정합성 보장!
→ @Scheduled와는 별개의 스레드 풀!
```

#### 4.5.3 @Scheduled 기본 동작 (단일 스레드)

```
기본 설정에서는 @Scheduled가 단일 스레드로 실행됩니다.

T=0초:  recoverPeriodically() 실행 시작
        (100개 처리 중... 25초 소요)

T=10초: 스케줄러가 실행하려고 함
        └─ 어? 아직 이전 작업이 안 끝났네
        └─ 기다림 (대기열에 쌓임)

T=20초: 스케줄러가 실행하려고 함
        └─ 어? 아직 이전 작업이 안 끝났네
        └─ 기다림 (대기열에 쌓임)

T=25초: 0초에 시작한 작업 완료!
        └─ 대기 중이던 작업 실행

결론: 기본 설정에서는 중복 실행 안 됨!
```

#### 4.5.4 그러면 왜 락을 쓰나?

```
┌─────────────────────────────────────────────────────────────────────┐
│                      락을 쓰는 이유                                  │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  1. 방어적 프로그래밍                                               │
│     - 나중에 누가 스레드 풀 설정을 바꿀 수 있음                     │
│     - 다른 개발자가 @Async 추가할 수 있음                           │
│     - 설정 변경에도 안전하게 동작                                   │
│                                                                      │
│  2. 락 비용이 거의 없음                                             │
│     - AtomicBoolean은 CPU 명령어 하나 (CAS)                         │
│     - 나노초 단위                                                   │
│     - 부하 거의 없음                                                │
│                                                                      │
│  3. 코드 명확성                                                     │
│     - "이 코드는 동시 실행되면 안 됨"이 명시적으로 표현됨           │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

#### 4.5.5 스레드 풀 분리 설정 (선택사항)

다른 @Scheduled 작업이 있을 때 복구 작업만 분리하고 싶다면:

```java
@Configuration
@EnableScheduling
public class SchedulerConfig {

    // 복구 전용 스레드 풀 (단일)
    @Bean("recoveryScheduler")
    public TaskScheduler recoveryScheduler() {
        ThreadPoolTaskScheduler scheduler = new ThreadPoolTaskScheduler();
        scheduler.setPoolSize(1);  // 단일 스레드
        scheduler.setThreadNamePrefix("recovery-");
        return scheduler;
    }

    // 일반 작업용 스레드 풀 (멀티)
    @Bean("generalScheduler")
    public TaskScheduler generalScheduler() {
        ThreadPoolTaskScheduler scheduler = new ThreadPoolTaskScheduler();
        scheduler.setPoolSize(5);  // 5개 스레드
        scheduler.setThreadNamePrefix("general-");
        return scheduler;
    }
}
```

**하지만 락을 쓰면 이런 복잡한 설정 없이도 안전합니다.**

### 4.6 DB 조회와 중복 처리 방지

#### 4.6.1 매번 DB를 새로 조회함

```java
@Scheduled(fixedRate = 10000)
public void recoverPeriodically() {
    // ...

    // ⭐ 매번 DB를 새로 조회함!
    List<PaymentIntent> targets = findRecoveryTargets();

    for (PaymentIntent intent : targets) {
        recoverSinglePayment(intent);  // 처리 완료 시 상태 변경
    }
}
```

#### 4.6.2 처리 완료된 건은 다음 조회에서 안 나옴

```sql
-- findRecoveryTargets() 쿼리
SELECT * FROM payment_intent
WHERE status = 'UNCERTAIN'
   OR (status = 'PENDING' AND expires_at < NOW())
```

```
처리 완료 = DB 상태 변경 = 다음 조회에서 안 나옴

recoverSinglePayment() 내부:
┌─────────────────────────────────────┐
│ 1. 모놀리스 확인                    │
│ 2. 환불 또는 만료 처리              │
│ 3. intent.setStatus(ROLLED_BACK)    │  ← 상태 변경!
│ 4. intentRepository.save(intent)    │  ← DB 저장!
└─────────────────────────────────────┘

다음 조회 시 이 건은 WHERE status = 'UNCERTAIN'에 안 걸림
```

#### 4.6.3 예외 발생 시 동작

```
T=0초: 100개 처리 시작
       - 1~30번 처리 완료 (ROLLED_BACK으로 변경)
       - 31번 처리 중 예외 발생! (모놀리스 연결 실패)
       - finally { isRecovering = false }

T=10초: 스케줄러 재실행
       - DB 조회: 31~100번 + 새로 추가된 건
       - 1~30번은? 이미 ROLLED_BACK이라서 안 나옴!
       - 31번부터 이어서 처리
```

#### 4.8.3 해결책 2: 시간 범위 제한

```java
// ❌ 나쁜 예: 전체 조회
@Query("""
    SELECT p FROM PaymentIntent p
    WHERE p.status = 'UNCERTAIN'
       OR (p.status = 'PENDING' AND p.expiresAt < :now)

// ✅ 좋은 예: 최근 1시간만 조회
@Query("""
    SELECT p FROM PaymentIntent p
    WHERE (p.status = 'UNCERTAIN'
           OR (p.status = 'PENDING' AND p.expiresAt < :now))
      AND p.createdAt > :oneHourAgo
    ORDER BY p.createdAt ASC
    """)
List<PaymentIntent> findRecoveryTargets(
    @Param("now") LocalDateTime now,
    @Param("oneHourAgo") LocalDateTime oneHourAgo
);
```

```
이유:
──────
- 3일 전 UNCERTAIN? 이미 다른 방법으로 처리됐을 것
- 복구 대상은 "방금 실패한 것"
```

### 4.9 PaymentIntent vs Transaction 테이블

#### 4.9.1 두 테이블의 역할

```
┌─────────────────────────────────────────────────────────────────────┐
│                                                                      │
│   QR 서버                           모놀리스                         │
│   ─────────                         ─────────                       │
│                                                                      │
│   PaymentIntent                     Transaction                     │
│   (결제 "진행 중" 상태)              (결제 "완료" 기록)               │
│                                                                      │
│   - QR 찍음 → PENDING               - 결제 완료 시 생성             │
│   - PIN 입력 중...                  - 환불 시 생성                  │
│   - 타임아웃 → UNCERTAIN            - 영구 보관                     │
│   - 성공 → APPROVED                 - 매출/내역 조회용              │
│                                                                      │
│   TTL: 3분 (임시)                   TTL: 없음 (영구)                │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

#### 4.9.2 어떤 테이블을 조회하나?

```
┌─────────────────────────────────────────────────────────────────────┐
│                                                                      │
│   매장 매출 조회:                                                    │
│   → Transaction 테이블 (모놀리스)                                    │
│   → SELECT * FROM transaction WHERE store_id = ?                    │
│                                                                      │
│                                                                      │
│   지갑 거래내역 조회:                                                │
│   → Transaction 테이블 (모놀리스)                                    │
│   → SELECT * FROM transaction WHERE wallet_id = ?                   │
│                                                                      │
│                                                                      │
│   복구 대상 조회:                                                    │
│   → PaymentIntent 테이블 (QR 서버)                                   │
│   → SELECT * FROM payment_intent WHERE status = 'UNCERTAIN'         │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

#### 4.9.3 비유

```
PaymentIntent = 주문서
─────────────────────
- "이 손님이 지금 결제 중이야"
- 결제 끝나면 필요 없음 (임시)


Transaction = 영수증
─────────────────────
- "이 거래가 완료됐어"
- 영구 보관
- 매출 집계, 거래내역 조회에 사용
```

### 4.10 인덱스 트레이드오프 (쓰기 vs 읽기)

#### 4.10.1 인덱스의 기본 원리

```
┌─────────────────────────────────────────────────────────────────────┐
│                                                                      │
│   인덱스 = 읽기 빠르게 ↔ 쓰기 느려짐                                │
│                                                                      │
│                                                                      │
│   인덱스 없을 때:                                                    │
│   ───────────────                                                   │
│   INSERT → 그냥 넣음 (빠름)                                         │
│   SELECT → 전체 스캔 (느림)                                         │
│                                                                      │
│                                                                      │
│   인덱스 있을 때:                                                    │
│   ───────────────                                                   │
│   INSERT → 넣고 + 인덱스도 업데이트 (약간 느려짐)                   │
│   SELECT → 인덱스로 바로 찾음 (빠름)                                │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

#### 4.10.2 점심시간 폭주 시 인덱스 비용

```
걱정:
- 점심시간에 결제 1000건 들어옴
- INSERT 1000번 + 인덱스 업데이트 1000번
- 느려지지 않나?

현실:
┌─────────────────────────────────────────────────────────────────────┐
│                                                                      │
│   인덱스 INSERT 비용:                                                │
│                                                                      │
│   - 1건당 약 0.1~0.5ms 추가                                         │
│   - 1000건 = 100~500ms 추가                                         │
│   - 점심 1시간 = 3,600,000ms                                        │
│   - 비율: 0.01~0.05%                                                │
│                                                                      │
│   → 거의 체감 안 됨!                                                │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

#### 4.10.3 읽기가 훨씬 많음

```
결제 1건당:

┌─────────────────────────────────────────────────────────────────────┐
│                                                                      │
│   쓰기: INSERT 1번                                                   │
│                                                                      │
│   읽기: 지갑 조회, 잔액 확인, PIN 검증, 거래 기록 조회...           │
│         → SELECT 5~10번                                             │
│                                                                      │
│   읽기가 훨씬 많음!                                                  │
│   인덱스 없으면 읽기가 느려져서 더 문제                             │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

#### 4.10.4 payment_intent는 어차피 인덱스 필요

```
복구용 인덱스 외에도 필요한 인덱스들:

┌─────────────────────────────────────────────────────────────────────┐
│                                                                      │
│   - idempotency_key 인덱스 (중복 결제 방지)                         │
│   - customer_id 인덱스 (내 결제 내역)                               │
│   - store_id 인덱스 (매장별 조회)                                   │
│   - created_at 인덱스 (기간별 조회)                                 │
│                                                                      │
│   복구용 인덱스 하나 더 추가하는 건 큰 차이 아님!                   │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

#### 4.10.5 두 방식 비교

```
방식 A: 인덱스 사용
────────────────────
장점:
- 테이블 하나로 끝남 (단순)
- 동기화 신경 안 써도 됨
- 실수할 곳 적음

단점:
- 쓰기 시 약간 느려짐 (0.1~0.5ms/건)
- 테이블 매우 커지면 효율 감소


방식 B: 별도 recovery_queue 테이블
───────────────────────────────────
장점:
- 조회 항상 빠름 (테이블 크기 무관)
- 쓰기 비용 최소화 (타임아웃 시에만 INSERT)

단점:
- 두 테이블 동기화 필요
- INSERT/DELETE 빼먹으면 복구 누락
- 코드 복잡도 증가
```

#### 4.10.6 방식 B 동기화 문제 상세

```
문제 1: INSERT 누락
────────────────────
┌─────────────────────────────────────────────────────────────────────┐
│  타임아웃 발생!                                                      │
│      │                                                               │
│      ├─ ① intent.status = UNCERTAIN (저장) ✅                       │
│      │                                                               │
│      └─ ② recovery_queue INSERT ❌ (실패 또는 빼먹음)               │
│                                                                      │
│  결과: intent는 UNCERTAIN인데 queue에 없음 → 복구 누락!             │
└─────────────────────────────────────────────────────────────────────┘


문제 2: DELETE 누락
────────────────────
┌─────────────────────────────────────────────────────────────────────┐
│  복구 완료!                                                          │
│      │                                                               │
│      ├─ ① intent.status = ROLLED_BACK (저장) ✅                     │
│      │                                                               │
│      └─ ② recovery_queue DELETE ❌ (실패 또는 빼먹음)               │
│                                                                      │
│  결과: queue에 남아서 다음에 또 처리 시도 → 중복 처리!              │
└─────────────────────────────────────────────────────────────────────┘


해결책: @Transactional로 묶기
────────────────────────────
@Transactional
public void markAsUncertain(PaymentIntent intent) {
    intent.setStatus(PaymentStatus.UNCERTAIN);
    intentRepository.save(intent);
    recoveryQueueRepository.save(new RecoveryQueue(intent.getId()));
    // 둘 다 성공하거나 둘 다 실패 (원자성)
}
```

#### 4.10.7 선택 기준

```
┌─────────────────────────────────────────────────────────────────────┐
│                                                                      │
│   방식 A (인덱스) 선택:                                              │
│   - 빠르게 구현하고 싶을 때                                         │
│   - 단순함을 원할 때                                                │
│   - 결제 건수가 적을 때 (100만 건 이하)                             │
│                                                                      │
│                                                                      │
│   방식 B (별도 테이블) 선택:                                         │
│   - 조회 속도가 항상 일정해야 할 때                                 │
│   - 결제 건수가 많을 때 (100만 건 이상)                             │
│   - 동기화 코드 작성할 여유가 있을 때                               │
│                                                                      │
│                                                                      │
│   권장 (MVP/초기):                                                   │
│   → 방식 A (인덱스) 시작                                            │
│   → 규모 커지면 방식 B 전환 검토                                    │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

### 5.1 PaymentStatus.java (수정)

**파일 경로**: `services/qr-service/src/main/java/com/ssafy/keeping/qr/domain/intent/model/PaymentStatus.java`

```java
package com.ssafy.keeping.qr.domain.intent.model;

public enum PaymentStatus {

    /**
     * 결제 대기 중
     * - PaymentIntent 생성 직후 상태
     * - 고객의 승인(PIN 입력) 대기 중
     */
    PENDING,

    /**
     * 승인 완료
     * - 정상적으로 결제가 완료된 상태
     * - 잔액 차감 및 Transaction 생성 완료
     */
    APPROVED,

    /**
     * 명확한 실패
     * - 잔액 부족, PIN 오류, 정책 위반 등
     * - 재시도 불가능한 실패
     */
    FAILED,

    /**
     * 결과 불명 (타임아웃)
     * - 모놀리스 응답을 받지 못한 상태
     * - 실제로 결제가 됐는지 안 됐는지 알 수 없음
     * - 복구 프로세스에서 확인 후 ROLLED_BACK 또는 EXPIRED로 전환
     */
    UNCERTAIN,

    /**
     * 보상 트랜잭션 완료
     * - UNCERTAIN 상태에서 모놀리스 확인 결과 결제가 되어 있어서
     * - 환불 처리를 완료한 상태
     */
    ROLLED_BACK,

    /**
     * 만료됨
     * - 3분 TTL 초과로 만료
     * - 또는 UNCERTAIN에서 확인 결과 모놀리스에 거래 없음
     */
    EXPIRED
}
```

### 5.2 PaymentRecoveryService.java (신규 생성)

**파일 경로**: `services/qr-service/src/main/java/com/ssafy/keeping/qr/domain/intent/service/PaymentRecoveryService.java`

```java

import com.ssafy.keeping.qr.acl.WalletClient;
import com.ssafy.keeping.qr.acl.dto.PaymentCheckResponse;
import com.ssafy.keeping.qr.acl.dto.RefundRequest;

import com.ssafy.keeping.qr.domain.intent.model.PaymentStatus;
import com.ssafy.keeping.qr.domain.intent.repository.PaymentIntentRepository;
import jakarta.annotation.PostConstruct;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.time.LocalDateTime;
import java.time.LocalTime;
import java.util.List;
import java.util.concurrent.atomic.AtomicBoolean;

@Slf4j
@Service
@RequiredArgsConstructor
public class PaymentRecoveryService {

    private final PaymentIntentRepository intentRepository;
    private final WalletClient walletClient;

    // ========================================
    // 피크 시간대 설정
    // ========================================
    private static final int LUNCH_START = 11;
    private static final int LUNCH_END = 14;
    private static final int DINNER_START = 17;
    private static final int DINNER_END = 19;

    // 주기 설정 (밀리초)
    private static final long PEAK_INTERVAL_MS = 10_000;    // 피크: 10초
    private static final long NORMAL_INTERVAL_MS = 60_000;  // 일반: 60초

    // 마지막 실행 시간 (시간대별 주기 조정용)
    private long lastExecutionTime = 0;

    // ========================================
    // 플래그
    // ========================================

    /**
     * 복구 대상 존재 여부 플래그
     * - true: 복구할 PaymentIntent가 있음 → DB 조회 필요
     * - false: 복구할 것 없음 → DB 조회 스킵 (부하 최소화)
     */
    private final AtomicBoolean hasRecoveryTarget = new AtomicBoolean(false);

    /**
     * 현재 복구 중 여부 플래그 (중복 실행 방지용 락)
     * - true: 복구 작업 진행 중 → 다른 스케줄러는 스킵
     * - false: 복구 작업 안 함 → 스케줄러 진입 가능
     *
     * 왜 필요한가?
     * - 복구 작업이 10초 이상 걸리면 다음 스케줄러가 실행될 수 있음
     * - 멀티스레드 설정 시 동시 실행 방지
     * - 단일 스레드에서도 방어적 프로그래밍으로 사용
     */
    private final AtomicBoolean isRecovering = new AtomicBoolean(false);

    /**
     * 외부에서 호출: "복구할 거 있어!"
     *
     * 호출 시점:
     * - FundsService.capture()에서 타임아웃 발생 시
     * - ResourceAccessException catch 블록에서 호출
     *
     * 주의: isRecovering은 건드리지 않음!
     */
    public void markRecoveryNeeded() {
        hasRecoveryTarget.set(true);
        log.info("[Recovery] 복구 대상 발생 - 플래그 ON");
    }

    /**
     * 1단계: 서버 시작 시 복구
     *
     * 목적:
     * - 서버 다운 후 재시작 시 메모리 플래그가 false로 초기화됨
     * - 하지만 DB에는 복구 대상이 남아있을 수 있음
     * - 따라서 서버 시작 시 무조건 한 번 DB 확인
     *
     * 복구 대상:
     * - UNCERTAIN 상태: 타임아웃 발생 후 상태 변경된 것
     * - PENDING + 만료: 시나리오 A (QR 서버 다운으로 상태 변경 못 한 것)
     */
    @PostConstruct
    public void recoverOnStartup() {
        log.info("[Recovery] 서버 시작 - 복구 대상 확인 중...");

        List<PaymentIntent> targets = findRecoveryTargets();

        if (targets.isEmpty()) {
            log.info("[Recovery] 복구 대상 없음 - 정상 시작");
            return;
        }

        hasRecoveryTarget.set(true);
        log.info("[Recovery] 복구 대상 {}건 발견 - 복구 시작", targets.size());

        processRecovery(targets);
    }

    /**
     * 2단계: 주기적 복구
     *
     * 동작 방식:
     * - 10초마다 실행되지만, 실제 복구는 시간대에 따라 다른 주기로 수행
     * - 피크 시간대 (11~14시, 17~19시): 10초마다
     * - 일반 시간대: 60초마다
     * - hasRecoveryTarget이 false면 즉시 리턴 (DB 부하 최소화)
     * - isRecovering이 true면 즉시 리턴 (중복 실행 방지)
     */
    @Scheduled(fixedRate = 10000) // 10초마다 체크
    public void recoverPeriodically() {
        // 1. 복구 대상 없으면 스킵 (나노초 수준 체크)
        if (!hasRecoveryTarget.get()) {
            return;
        }

        // 2. 시간대에 따른 주기 확인
        long interval = isPeakTime() ? PEAK_INTERVAL_MS : NORMAL_INTERVAL_MS;
        long now = System.currentTimeMillis();

        if (now - lastExecutionTime < interval) {
            return;  // 아직 주기 안 됨
        }

        // 3. 중복 실행 방지 (락 획득 시도)
        // compareAndSet: 현재 false면 true로 바꾸고 true 반환, 아니면 false 반환
        if (!isRecovering.compareAndSet(false, true)) {
            log.debug("[Recovery] 이미 복구 진행 중 - 스킵");
            return;
        }

        try {
            lastExecutionTime = now;
            log.info("[Recovery] 주기적 복구 시작 (interval={}ms, isPeak={})",
                interval, isPeakTime());

            List<PaymentIntent> targets = findRecoveryTargets();

            if (targets.isEmpty()) {
                hasRecoveryTarget.set(false);
                log.info("[Recovery] 복구 완료 - 플래그 OFF");
                return;
            }

            log.info("[Recovery] 복구 대상 {}건 처리 중...", targets.size());
            processRecovery(targets);

        } finally {
            // 4. 락 해제 (예외 발생해도 무조건 해제)
            isRecovering.set(false);
        }
    }

    /**
     * 피크 시간대 여부 확인
     */
    private boolean isPeakTime() {
        int hour = LocalTime.now().getHour();
        return (hour >= LUNCH_START && hour < LUNCH_END)
            || (hour >= DINNER_START && hour < DINNER_END);
    }

    /**
     * 복구 대상 조회
     *
     * 조건:
     * 1. status = UNCERTAIN: 타임아웃으로 결과 불명
     * 2. status = PENDING AND expiresAt < NOW(): QR 서버 다운 케이스
     */
    private List<PaymentIntent> findRecoveryTargets() {
        LocalDateTime now = LocalDateTime.now();
        return intentRepository.findRecoveryTargets(
            PaymentStatus.UNCERTAIN,
            PaymentStatus.PENDING,
            now
        );
    }

    /**
     * 복구 대상 목록 처리
     */
    private void processRecovery(List<PaymentIntent> targets) {
        int successCount = 0;
        int failCount = 0;

        for (PaymentIntent intent : targets) {
            try {
                recoverSinglePayment(intent);
                successCount++;
            } catch (Exception e) {
                failCount++;
                log.error("[Recovery] 복구 실패: intentId={}, error={}",
                    intent.getPublicId(), e.getMessage(), e);
                // 다음 사이클에서 재시도
            }
        }

        log.info("[Recovery] 처리 완료 - 성공: {}, 실패: {}", successCount, failCount);

        // 모두 성공했으면 플래그 확인
        if (failCount == 0) {
            List<PaymentIntent> remaining = findRecoveryTargets();
            if (remaining.isEmpty()) {
                hasRecoveryTarget.set(false);
                log.info("[Recovery] 모든 복구 완료 - 플래그 OFF");
            }
        }
    }

    /**
     * 단일 PaymentIntent 복구
     *
     * 로직:
     * 1. 모놀리스에 확인: 이 idempotencyKey로 결제 됐어?
     * 2. exists=true: 결제됐으니 환불 요청
     * 3. exists=false: 결제 안 됐으니 그냥 만료 처리
     */
    @Transactional
    public void recoverSinglePayment(PaymentIntent intent) {
        String idempotencyKey = intent.getIdempotencyKey();
        log.info("[Recovery] 복구 시작: intentId={}, idempotencyKey={}",
            intent.getPublicId(), idempotencyKey);

        // 1. 모놀리스에 결제 상태 확인
        PaymentCheckResponse checkResponse;
        try {
            checkResponse = walletClient.checkPayment(idempotencyKey);
        } catch (Exception e) {
            // 모놀리스 연결 실패 → 다음 사이클에서 재시도
            log.warn("[Recovery] 모놀리스 연결 실패, 다음 사이클에서 재시도: intentId={}",
                intent.getPublicId());
            throw e;
        }

        if (!checkResponse.isExists()) {
            // 2-A. 모놀리스에 거래 없음 → 환불 불필요
            log.info("[Recovery] 모놀리스에 거래 없음 - 만료 처리: intentId={}",
                intent.getPublicId());

            intent.setStatus(PaymentStatus.EXPIRED);
            intent.setRecoveredAt(LocalDateTime.now());
            intent.setRecoveryNote("모놀리스에 거래 없음 - 환불 불필요");
            intentRepository.save(intent);
            return;
        }

        // 2-B. 모놀리스에 거래 있음 → 환불 요청
        log.info("[Recovery] 모놀리스에 거래 있음 - 환불 요청: intentId={}, txId={}",
            intent.getPublicId(), checkResponse.getTransactionId());

        try {
            RefundRequest refundRequest = RefundRequest.builder()
                .walletId(intent.getWalletId())
                .storeId(intent.getStoreId())
                .amount(checkResponse.getAmount())
                .originalTransactionId(checkResponse.getTransactionId())
                .reason("TIMEOUT_RECOVERY")
                .idempotencyKey("REFUND-" + idempotencyKey) // 환불도 멱등성 보장
                .build();

            walletClient.refund(refundRequest);

            // 3. 상태 업데이트
            intent.setStatus(PaymentStatus.ROLLED_BACK);
            intent.setRecoveredAt(LocalDateTime.now());
            intent.setRecoveryNote(String.format(
                "환불 완료: originalTxId=%d, amount=%d",
                checkResponse.getTransactionId(),
                checkResponse.getAmount()
            ));
            intentRepository.save(intent);

            log.info("[Recovery] 환불 완료: intentId={}", intent.getPublicId());

        } catch (Exception e) {
            log.error("[Recovery] 환불 요청 실패: intentId={}", intent.getPublicId(), e);
            throw e;
        }
    }

    /**
     * 현재 플래그 상태 조회 (테스트/모니터링용)
     */
    public boolean hasRecoveryTarget() {
        return hasRecoveryTarget.get();
    }

    /**
     * 현재 복구 중 여부 조회 (테스트/모니터링용)
     */
    public boolean isRecovering() {
        return isRecovering.get();
    }
}
```

```java
    /**
     * 복구 대상 조회
     *
     * 조건 1: status = UNCERTAIN
     *   - 타임아웃 발생으로 결과가 불명확한 상태
     *
     * 조건 2: status = PENDING AND expiresAt < now
     *   - QR 서버 다운으로 상태 변경을 못 한 케이스
     *   - 3분 TTL이 지났는데 아직 PENDING인 것은 비정상

    @Query("""
        SELECT i FROM PaymentIntent i
        WHERE i.status = :uncertainStatus
           OR (i.status = :pendingStatus AND i.expiresAt < :now)
        ORDER BY i.createdAt ASC
        """)
    List<PaymentIntent> findRecoveryTargets(
        @Param("uncertainStatus") PaymentStatus uncertainStatus,
        @Param("pendingStatus") PaymentStatus pendingStatus,
        @Param("now") LocalDateTime now
    );

    /**
     * 특정 상태의 PaymentIntent 수 조회 (모니터링용)
     */
    long countByStatus(PaymentStatus status);
}
```

```java
import jakarta.persistence.*;
import lombok.*;

import java.time.LocalDateTime;

@Entity
@Table(name = "payment_intent")
@Getter
@Setter
@Builder
@NoArgsConstructor
@AllArgsConstructor
public class PaymentIntent {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    /**
     * 외부 노출용 UUID
     */
    @Column(nullable = false, unique = true)

    /**
     * 멱등성 키
     * - 클라이언트가 제공한 고유 키
     * - 동일 키로 재요청 시 기존 결과 반환
     */
    @Column(nullable = false, unique = true)
    private String idempotencyKey;

    /**
     * 결제할 지갑 ID
     */
    @Column(nullable = false)
    private Long walletId;

    /**
     * 결제 대상 고객 ID
     */
    @Column(nullable = false)
    private Long customerId;

    /**
     * 결제 매장 ID
     */
    @Column(nullable = false)
    private Long storeId;

    /**
     * 총 결제 금액
     */
    @Column(nullable = false)
    private Integer totalAmount;

    /**
     * 결제 상태
     */
    @Enumerated(EnumType.STRING)
    @Column(nullable = false)
    private PaymentStatus status;

    /**
     * 생성 시간
     */
    @Column(nullable = false)
    private LocalDateTime createdAt;

    /**
     * 만료 시간 (3분)
     */
    @Column(nullable = false)
    private LocalDateTime expiresAt;

    /**
     * 승인 시간
     */
    private LocalDateTime approvedAt;

    /**
     * 복구 시간 (UNCERTAIN → ROLLED_BACK 또는 EXPIRED)
     */
    private LocalDateTime recoveredAt;

    /**
     * 복구 메모
     * - 환불 여부, 원본 거래 ID 등 기록
     */
    @Column(length = 500)
    private String recoveryNote;

    /**
     * 결제 항목 목록
     */
    @OneToMany(mappedBy = "paymentIntent", cascade = CascadeType.ALL, orphanRemoval = true)
    @Builder.Default
    private List<PaymentIntentItem> items = new ArrayList<>();

    /**
     * 만료 여부 확인
     */
    public boolean isExpired() {
        return LocalDateTime.now().isAfter(expiresAt);
    }

    /**
     * 승인 가능 여부 확인
     */
    public boolean isApprovable() {
        return status == PaymentStatus.PENDING && !isExpired();
    }

    @PrePersist
    public void prePersist() {
        if (publicId == null) {
            publicId = UUID.randomUUID();
        }
        if (createdAt == null) {
            createdAt = LocalDateTime.now();
        }
        if (expiresAt == null) {
            expiresAt = createdAt.plusMinutes(3);
        }
        if (status == null) {
            status = PaymentStatus.PENDING;
        }
    }
}
```

### 5.5 FundsService.java (수정)

```java
package com.ssafy.keeping.qr.domain.intent.service;

import com.ssafy.keeping.qr.acl.WalletClient;
import com.ssafy.keeping.qr.acl.dto.FundsRequest;
import com.ssafy.keeping.qr.acl.dto.FundsResponse;
import com.ssafy.keeping.qr.common.exception.CustomException;
import com.ssafy.keeping.qr.common.exception.ErrorCode;
import com.ssafy.keeping.qr.domain.intent.dto.FundsResult;
import com.ssafy.keeping.qr.domain.intent.model.PaymentIntent;
import com.ssafy.keeping.qr.domain.intent.model.PaymentIntentItem;
import com.ssafy.keeping.qr.domain.intent.model.PaymentStatus;
import com.ssafy.keeping.qr.domain.intent.repository.PaymentIntentRepository;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.web.client.ResourceAccessException;

import java.time.LocalDateTime;
import java.util.List;

@Slf4j
@Service
@RequiredArgsConstructor
public class FundsService {

    private final WalletClient walletClient;
    private final PaymentIntentRepository intentRepository;
    private final PaymentRecoveryService recoveryService;

    /**
     * 자금 캡처 (잔액 차감 + 거래 생성)
     *
     * @param intent 결제 의도
     * @param items 결제 항목 목록
     * @param pin 결제 비밀번호
     * @return 캡처 결과
     */
    @Transactional
    public FundsResult capture(PaymentIntent intent, List<PaymentIntentItem> items, String pin) {
        String idempotencyKey = intent.getIdempotencyKey();

        log.info("[Funds] 자금 캡처 시작: intentId={}, amount={}",
            intent.getPublicId(), intent.getTotalAmount());

        FundsRequest request = FundsRequest.builder()
            .walletId(intent.getWalletId())
            .customerId(intent.getCustomerId())
            .storeId(intent.getStoreId())
            .amount(intent.getTotalAmount())
            .pin(pin)
            .intentPublicId(intent.getPublicId().toString())
            .items(items.stream()
                .map(item -> FundsRequest.Item.builder()
                    .menuId(item.getMenuId())
                    .menuName(item.getMenuName())
                    .price(item.getPrice())
                    .quantity(item.getQuantity())
                    .build())
                .toList())
            .build();

        try {
            // 모놀리스에 자금 캡처 요청
            FundsResponse response = walletClient.capture(request, idempotencyKey);

            // 성공: 상태 업데이트
            intent.setStatus(PaymentStatus.APPROVED);
            intent.setApprovedAt(LocalDateTime.now());
            intentRepository.save(intent);

            log.info("[Funds] 자금 캡처 성공: intentId={}, txId={}",
                intent.getPublicId(), response.getTransactionId());

            return FundsResult.success(response);

        } catch (ResourceAccessException e) {
            // ========================================
            // 타임아웃/연결 실패 처리
            // ========================================
            log.error("[Funds] 자금 캡처 타임아웃: intentId={}, error={}",
                intent.getPublicId(), e.getMessage());

            // 1. 상태를 UNCERTAIN으로 변경
            intent.setStatus(PaymentStatus.UNCERTAIN);
            intentRepository.save(intent);

            // 2. 복구 서비스에 알림 → 플래그 ON
            recoveryService.markRecoveryNeeded();

            // 3. 사용자에게 "확인 중" 응답
            return FundsResult.uncertain();

        } catch (CustomException e) {
            // 명확한 실패 (잔액 부족, PIN 오류 등)
            log.warn("[Funds] 자금 캡처 실패: intentId={}, errorCode={}",
                intent.getPublicId(), e.getErrorCode());

            intent.setStatus(PaymentStatus.FAILED);
            intentRepository.save(intent);

            throw e;

        } catch (Exception e) {
            // 기타 예외
            log.error("[Funds] 자금 캡처 중 예외 발생: intentId={}",
                intent.getPublicId(), e);

            intent.setStatus(PaymentStatus.FAILED);
            intentRepository.save(intent);

            throw new CustomException(ErrorCode.FUNDS_CAPTURE_FAILED);
        }
    }
}
```

### 5.7 WalletClient.java (수정)

**파일 경로**: `services/qr-service/src/main/java/com/ssafy/keeping/qr/acl/WalletClient.java`

```java
package com.ssafy.keeping.qr.acl;

import com.ssafy.keeping.qr.acl.dto.*;
import com.ssafy.keeping.qr.common.exception.CustomException;
import com.ssafy.keeping.qr.common.exception.ErrorCode;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.http.*;
import org.springframework.stereotype.Component;
import org.springframework.web.client.HttpClientErrorException;
import org.springframework.web.client.HttpServerErrorException;
import org.springframework.web.client.ResourceAccessException;
import org.springframework.web.client.RestTemplate;

@Slf4j
@Component
@RequiredArgsConstructor
public class WalletClient {

    private final RestTemplate restTemplate;

    @Value("${monolith.base-url:http://localhost:8080}")
    private String monolithBaseUrl;

    /**
     * 자금 캡처 (잔액 차감 + 거래 생성)
     *
     * @throws ResourceAccessException 타임아웃/연결 실패 시
     * @throws CustomException 비즈니스 에러 (잔액 부족, PIN 오류 등)
     */
    public FundsResponse capture(FundsRequest request, String idempotencyKey) {
        String url = monolithBaseUrl + "/internal/wallets/capture";

        HttpHeaders headers = new HttpHeaders();
        headers.setContentType(MediaType.APPLICATION_JSON);
        headers.set("Idempotency-Key", idempotencyKey);

        HttpEntity<FundsRequest> entity = new HttpEntity<>(request, headers);

        try {
            ResponseEntity<FundsResponse> response = restTemplate.exchange(
                url,
                HttpMethod.POST,
                entity,
                FundsResponse.class
            );

            return response.getBody();

        } catch (HttpClientErrorException e) {
            // 4xx 에러: 비즈니스 에러
            log.warn("[WalletClient] 캡처 실패 (4xx): status={}, body={}",
                e.getStatusCode(), e.getResponseBodyAsString());

            ErrorCode errorCode = mapHttpStatusToErrorCode(e.getStatusCode());
            throw new CustomException(errorCode);

        } catch (HttpServerErrorException e) {
            // 5xx 에러: 서버 에러
            log.error("[WalletClient] 캡처 실패 (5xx): status={}, body={}",
                e.getStatusCode(), e.getResponseBodyAsString());
            throw new CustomException(ErrorCode.MONOLITH_UNAVAILABLE);

        } catch (ResourceAccessException e) {
            // 타임아웃/연결 실패 → 그대로 던짐 (FundsService에서 처리)
            log.error("[WalletClient] 캡처 타임아웃/연결실패: {}", e.getMessage());
            throw e;
        }
    }

    /**
     * 결제 상태 확인 (복구용)
     *
     * @param idempotencyKey 멱등성 키
     * @return 결제 존재 여부 및 상세 정보
     */
    public PaymentCheckResponse checkPayment(String idempotencyKey) {
        String url = monolithBaseUrl + "/internal/payments/check?idempotencyKey=" + idempotencyKey;

        try {
            ResponseEntity<PaymentCheckResponse> response = restTemplate.getForEntity(
                url,
                PaymentCheckResponse.class
            );

            return response.getBody();

        } catch (Exception e) {
            log.error("[WalletClient] 결제 확인 실패: idempotencyKey={}, error={}",
                idempotencyKey, e.getMessage());
            throw e;
        }
    }

    /**
     * 환불 요청 (복구용)
     *
     * @param request 환불 요청 정보
     */
    public void refund(RefundRequest request) {
        String url = monolithBaseUrl + "/internal/wallets/" + request.getWalletId() + "/refund";

        HttpHeaders headers = new HttpHeaders();
        headers.setContentType(MediaType.APPLICATION_JSON);
        headers.set("Idempotency-Key", request.getIdempotencyKey());

        HttpEntity<RefundRequest> entity = new HttpEntity<>(request, headers);

        try {
            restTemplate.exchange(
                url,
                HttpMethod.POST,
                entity,
                Void.class
            );

            log.info("[WalletClient] 환불 성공: walletId={}, amount={}",
                request.getWalletId(), request.getAmount());

        } catch (Exception e) {
            log.error("[WalletClient] 환불 실패: walletId={}, error={}",
                request.getWalletId(), e.getMessage());
            throw e;
        }
    }

    private ErrorCode mapHttpStatusToErrorCode(HttpStatusCode status) {
        return switch (status.value()) {
            case 400 -> ErrorCode.BAD_REQUEST;
            case 401 -> ErrorCode.PIN_INVALID;
            case 402 -> ErrorCode.FUNDS_INSUFFICIENT;
            case 404 -> ErrorCode.CUSTOMER_NOT_FOUND;
            case 409 -> ErrorCode.PAYMENT_IN_PROGRESS;
            case 422 -> ErrorCode.PAYMENT_POLICY_VIOLATION;
            default -> ErrorCode.EXTERNAL_API_ERROR;
        };
    }
}
```

## 6. API 명세

### 6.1 모놀리스에 추가해야 할 API

#### 6.1.1 결제 상태 확인 API

**목적**: 특정 idempotencyKey로 결제가 처리되었는지 확인

```
GET /internal/payments/check
```

**Query Parameters**:

| 파라미터 | 타입 | 필수 | 설명 |
|----------|------|------|------|
| idempotencyKey | String | O | 멱등성 키 |

**Response (200 OK)**:

거래가 존재하는 경우:
```json
{
  "exists": true,
  "transactionId": 12345,
  "amount": 5000,
  "walletId": 100,
  "storeId": 789
}
```

거래가 존재하지 않는 경우:
```json
{
  "exists": false,
  "transactionId": null,
  "amount": null,
  "walletId": null,
  "storeId": null
}
```

**구현 예시 (모놀리스)**:

```java
@RestController
@RequestMapping("/internal/payments")
@RequiredArgsConstructor
public class InternalPaymentController {

    private final TransactionRepository transactionRepository;

    @GetMapping("/check")
    public ResponseEntity<PaymentCheckResponse> checkPayment(
            @RequestParam String idempotencyKey
    ) {
        Optional<Transaction> txOpt = transactionRepository
            .findByIdempotencyKey(idempotencyKey);

        if (txOpt.isEmpty()) {
            return ResponseEntity.ok(PaymentCheckResponse.builder()
                .exists(false)
                .build());
        }

        Transaction tx = txOpt.get();
        return ResponseEntity.ok(PaymentCheckResponse.builder()
            .exists(true)
            .transactionId(tx.getId())
            .amount(tx.getAmount())
            .walletId(tx.getWalletId())
            .storeId(tx.getStoreId())
            .build());
    }
}
```

#### 6.1.2 환불 API

**목적**: 타임아웃 복구 시 결제 취소 (환불)

```
POST /internal/wallets/{walletId}/refund
```

**Path Parameters**:

| 파라미터 | 타입 | 설명 |
|----------|------|------|
| walletId | Long | 환불 대상 지갑 ID |

**Headers**:

| 헤더 | 값 | 설명 |
|------|-----|------|
| Content-Type | application/json | |
| Idempotency-Key | REFUND-{원본키} | 환불 멱등성 키 |

**Request Body**:
```json
{
  "storeId": 789,
  "amount": 5000,
  "originalTransactionId": 12345,
  "reason": "TIMEOUT_RECOVERY"
}
```

**Response (200 OK)**:
```json
{
  "success": true,
  "refundTransactionId": 12346,
  "refundedAmount": 5000,
  "newBalance": 15000
}
```

**Response (409 Conflict)** - 이미 환불된 경우:
```json
{
  "success": true,
  "message": "이미 환불 처리되었습니다.",
  "refundTransactionId": 12346
}
```

**구현 예시 (모놀리스)**:

```java
@RestController
@RequestMapping("/internal/wallets")
@RequiredArgsConstructor
public class InternalWalletController {

    private final WalletService walletService;
    private final IdempotencyService idempotencyService;

    @PostMapping("/{walletId}/refund")
    public ResponseEntity<RefundResponse> refund(
            @PathVariable Long walletId,
            @RequestHeader("Idempotency-Key") String idempotencyKey,
            @RequestBody RefundRequest request
    ) {
        // 멱등성 체크
        Optional<RefundResponse> cached = idempotencyService.get(idempotencyKey);
        if (cached.isPresent()) {
            return ResponseEntity.ok(cached.get());
        }

        // 환불 처리
        RefundResponse response = walletService.processRefund(
            walletId,
            request.getStoreId(),
            request.getAmount(),
            request.getOriginalTransactionId(),
            request.getReason()
        );

        // 멱등성 키 저장
        idempotencyService.save(idempotencyKey, response);

        return ResponseEntity.ok(response);
    }
}
```

## 7. 트레이드오프 분석

### 7.1 얻는 것 (Benefits)

| 항목 | 설명 |
|------|------|
| **인프라 단순화** | Kafka, 공유 Redis, 별도 복구 서버 불필요 |
| **운영 비용 절감** | 추가 서버 없음, 모니터링 대상 감소 |
| **구현 복잡도 감소** | HTTP API + @Scheduled만으로 구현 |
| **데이터 정합성** | MySQL 기반으로 데이터 유실 없음 |
| **독립성 유지** | QR서버/모놀리스 각각 독립 Redis/MySQL 유지 |

### 7.2 장점 (Pros)

| 장점 | 설명 |
|------|------|
| **플래그 기반 최적화** | 복구 대상 없으면 DB 조회 안 함 (부하 최소화) |
| **3단계 안전망** | 즉시/주기/재시작 복구로 누락 없음 |
| **멱등성 보장** | idempotencyKey로 중복 환불 방지 |
| **점진적 도입 가능** | 기존 코드에 최소한의 변경 |
| **디버깅 용이** | MySQL에 상태 기록, 로그 추적 가능 |
| **테스트 용이** | 외부 의존성 없이 단위 테스트 가능 |

### 7.3 단점 (Cons)

| 단점 | 설명 | 영향도 | 완화 방안 |
|------|------|--------|-----------|
| **복구 지연** | 최대 1분 (Scheduled 주기) | 🟡 중간 | 주기 단축 가능 (30초) |
| **모놀리스 의존성** | 모놀리스 다운 시 복구 불가 | 🟡 중간 | 다음 사이클에서 재시도 |
| **폴링 방식** | 이벤트 기반보다 비효율적 | 🟢 낮음 | 플래그로 최적화 |
| **메모리 플래그 한계** | 다중 인스턴스 시 각각 플래그 관리 | 🟡 중간 | Redis 공유 플래그 (선택) |
| **DB 조회 비용** | 복구 대상 있을 때만 조회 | 🟢 낮음 | 인덱스 최적화 |

### 7.4 Kafka vs 현재 방식 비교

| 항목 | Kafka 방식 | 현재 방식 (HTTP + Scheduled) |
|------|-----------|------------------------------|
| 추가 인프라 | Kafka 클러스터 필요 | 없음 |
| 복구 지연 | 거의 실시간 | 최대 1분 |
| 구현 복잡도 | 높음 | 낮음 |
| 메시지 유실 | Kafka ACK로 방지 | MySQL로 방지 |
| 운영 부담 | 높음 | 낮음 |
| 확장성 | 높음 | 중간 |
| 학습 곡선 | 높음 | 낮음 |
| 비용 | 높음 | 낮음 |

### 7.5 권장 사항

```
┌─────────────────────────────────────────────────────────────────────┐
│                         권장 판단                                    │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  현재 규모 (MVP/초기 서비스):                                        │
│  → 현재 방식 (HTTP + Scheduled) 권장                                │
│  → 이유: 인프라 단순, 빠른 개발, 충분한 안정성                       │

│  다중 인스턴스 운영 시:                                              │
│  → Redis 공유 플래그 도입 검토                                       │
│  → 또는 리더 선출 방식으로 복구 담당 인스턴스 지정                   │
│                                                                      │
```
